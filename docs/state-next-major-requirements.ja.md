# State 次期メジャー 要件

**English**: [state-next-major-requirements.md](./state-next-major-requirements.md)

起草日: 2026-09-20。起点: 直近のリリース 2.5.1（main `6bff9f2c`）。作業ブランチ: `major/state-next`（2026-09-20 に main `6bff9f2c` へリベース済み）。

この文書は「次の major で何を変え、何を変えないか」の要件一覧である。根拠となる計測・再現例は [state-next-major-audit.ja.md](./state-next-major-audit.ja.md)（調査日 2026-09-18・対象 2.5.0）にあり、ここではそれを要件の形に落とす。§9 フェーズ 3 の試作に使う要素技術（結合の切断点・字句解析・依存グラフ機構・DOM 下限・プラットフォーム）の個別計測は [state-next-major-tech-survey.ja.md](./state-next-major-tech-survey.ja.md)（2026-09-20）にある。設計と実装計画は別文書に分ける。

**この文書は決定ではない。** 著者の決裁が要る論点は §6 にまとめ、それ以外の項は「監査で再現済みの事実」と「その事実から導かれる要件」だけを書く。§6 が埋まるまで実装に着手しない。

## 1. スコープ

- 公開パッケージ（`@wcstack/*` と `wcstack`）は lockstep で `3.0.0`。実質の変更は `@wcstack/state` に集中し、他は版数だけ追随する想定（見直しは §6 D5）。
- `packages/vscode-wcs` は別版数だが、文法と診断を変える要件（B1〜B5・B12）には追随が要る。lint・`wcs-schema` / `wcs-tsc`・`@wcstack/testing`・manifest `schemaVersion`・devtools hook `version` も同じ範囲。
- 別リポジトリ [wcstack/wcstack-skill](https://github.com/wcstack/wcstack-skill) は同じ文法契約を持つので追随対象。
- major が必要になる範囲の定義は [README のバージョニングと破壊的変更](../README.ja.md#バージョニングと破壊的変更)に従う。この文書はその定義を作り直さない。

## 2. 目標

| ID | 目標 | 現状（実測） | 根拠 |
|---|---|---|---|
| G1 | 配布サイズを実用域にする | 名前付き `index.esm.js` は非 minify で gzip 310,916 bytes。minify 実験で 71,194 bytes（**77.1% 減**）。`auto.min.js` は 68,843 bytes | 監査 §3.1 |
| G2 | 機能の結合を切る | `defineState` だけを import しても watch / stream がモジュール評価時に listener を登録し、約 27 KB gzip が残る | 監査 §3.2 |
| G3 | 更新コストを下げる | 1,000 行生成 42.85 ms・10,000 行へ 1,000 行追加 66.00 ms・10,000 行クリア 72.95 ms（中央値） | 監査 §4.1 |
| G4 | 意味論の穴を閉じる | 再現済みの不整合 9 件（引用符、readonly の抜け穴、空値、リテラル型ほか） | 監査 §5.1 |
| G5 | 既知欠陥を閉じる | [#258](https://github.com/wcstack/wcstack/issues/258)（X6/X7/X10）、[#2](https://github.com/wcstack/wcstack/issues/2)、マウント系の実穴 3 件 | §5 |

G1〜G3 は数値目標を §8 に置く。G4・G5 は「契約として文書化し、回帰テストで固定する」ことが達成条件で、挙動を変えない選択（現状を正とする）も許す。

## 3. 破壊的変更の候補

いずれも semver 上 major が要る。**採否は決めていない**。「現状」はすべて監査で再現済みの挙動。

### 3.1 文法・パーサ

| ID | 項目 | 現状 | 要件 |
|---|---|---|---|
| B1 | 引用符と区切り | `join(', ')` は通るが `join(';')` と `join('\|')` が壊れる。外側の分割が引用符解析より先 | 引用符を知る字句解析 → AST → 束縛計画の 3 段に分け、区切り文字を引用符内で無効化する |
| B2 | 不正構文の受理 | 未閉じ引用符 `join('unterminated)` が通る。`value#ro#wo` は `ro` だけ残る。`else: ignored` は右辺を捨てる | 受理しない。位置情報付きの診断を lint / エディタと共有する |
| B3 | フィルタ引数 | キャッシュキーが `args.join(',')` で `['a,b']` と `['a','b']` を同一視。`join(a,b)` のような過剰引数も通る | アリティ検証と構造的キャッシュキー |
| B4 | 修飾子とバインド種別 | `radio: x` は専用処理だが `radio#ro: x` は汎用プロパティに落ちる。構造キーワードにも同種の分岐がある | 修飾子は種別を変えない。組み合わせを明示的に受理するか拒否する |
| B5 | `on` 接頭辞 | `only: x` や `online: x` がイベント束縛として解釈され、同名の DOM / カスタム要素プロパティと衝突する | イベントの名前空間を分離する |

### 3.2 読み書きの意味論

| ID | 項目 | 現状 | 要件 |
|---|---|---|---|
| B6 | readonly の抜け穴 | 直接代入は throw するが、同じ readonly プロキシに対する `$resolve(…, 9)` と `$setAll(…, 10)` は書けてしまう。ヘルパーが `StateHandler.set` を通らず `setByAddress` を呼ぶため | 書き込み能力の検査を共有の書き込み境界 1 点に集約する |
| B7 | `$resolve` のオーバーロード | 値 7 のとき `$resolve(path, [], undefined)` は 7 のまま。undefined を書けない | 読みと書きを引数の有無で分けない |
| B8 | 空値の契約 | `undefined` は `textContent:` で前の値を保持・mustache で空・`attr.title:` で文字列 `"undefined"`。`null` は `textContent:` と mustache で空・属性で文字列 `"null"` | 「不在」「明示的な消去」「表示変換」を契約として定義し、属性の削除まで含めて 3 つの表面で揃える |
| B9 | フィルタのリテラル型 | 真偽値 `true` に `eq(true)` が false を返す。数値 1 に `eq(1)` は true。引数は文字列で、数値変換だけがある | 引数のリテラル型規則を定める |
| B10 | 真偽判定 | `0n` に対し `truthy` は true、`boolean` は false | JavaScript の真偽判定と一致させるか、差を名前で表す |
| B11 | スコープ能力 | `$scan` は root 専用。volume では拒否、マウントされたコンポーネントでは警告して無視。root / volume の ready / error 契約も一致しない | 能力マトリクスを明示し、無言の非対応をなくす |

### 3.3 語彙

| ID | 項目 | 現状 | 要件 |
|---|---|---|---|
| B12 | 名前の正典化 | `$trackDependency` は辺を足し `$untrackDependency` は一時的に追跡を止める（逆操作ではない）。`#ro` は要素→state だけを止める一方、readonly プロキシは state 側の書き込みを縛る。`inc/dec` は純粋な算術なのに変更を思わせる。`uc/lc/cap/rep/rev/fix` と `truncate/percent/datetime` が混在。`pad` は padStart のみ。`defaults` は 0・false・空文字も置き換える。`$updatedCallback` は適用済み束縛の観測で、state 更新全体ではない。宣言マップは `$streams` が複数形で `$watch` / `$scan` が単数形 | 方向（to-element / from-element / two-way）・初期権限・タイミングを別の軸として語彙に出す。フィルタは正式名＋互換エイリアス。宣言マップの単複を揃える（意味の違いは保つ） |

§6 D4 で「エイリアスを何リリース残すか」を決める。

### 3.4 配布とマウント

| ID | 項目 | 現状 | 要件 |
|---|---|---|---|
| B13 | exports と副作用 | `exports` は `.` / `./auto` / `./manifest` / `./parser` / `./wcs-manifest.json`。core→機能の静的 import があり、`sideEffects` を宣言しても初期化が残る | 分割エントリを足し、登録を明示的・冪等にする。core を各サブパスに再同梱しない（単一 core チャンク・単一レジストリ・アドレス同一性の共有） |
| B14 | マウントの実穴 3 件 | ① パーサは `state#ro: user` を受理するが `mount.ts` は修飾子を読まず、無言で read-write ② 解決順が getter → own key → ツリーなので、host が `state.name: user.name` と明示しても own key が勝つ ③ コンポーネントには注入口（`state.taxRate: user.taxRate`）があるが volume には無い | ① 修飾子をマウント記録で尊重する ② 明示した部分マウントを own key より優先する ③ volume にも注入口を用意する。いずれも書き込み翻訳の単一点に載る |

## 4. 非破壊で入れる改善

| ID | 項目 | 備考 |
|---|---|---|
| N1 | 名前付きエントリの minify | API は変わらない。Rollup 設定と同期スクリプトを変え、生成物のコピーを直接編集しない。**実装済み（2026-09-21）**: state の rollup 設定が `dist/index.esm.js` を minify する（`sync-package-configs.mjs` に記録した deviation）。336,525 → 77,605 B gzip。プロファイル用に名前を読みたいときは `WCS_STATE_UNMINIFIED=1` でビルドする |
| N2 | 副作用のないヘルパー入口 | `defineState` / 型 / version。ランタイムを引かない |
| N3 | サイズ CI | 監査が測った 4 エントリの gzip / Brotli を閾値付きで固定する。**導入済み（未コミット）**: `defineState` だけの再 export ≤ 1 KB gzip（`audit-state-tech-helper-import.mjs --check`）と、`auto.min.js` / `index.esm.js` の gzip がリリース基準 +3% 以内（`check-state-size.mjs --check`、基準は `scripts/state-size-baseline.json`、D18） |
| N4 | [#258](https://github.com/wcstack/wcstack/issues/258) の修理 | X6（SSR ハイドレーション後に行の getter が葉の更新に追従しない）・X7（再セット後に行束縛が書き込みに追従しない）・X10（getter キャッシュが `setInitialState` を越えて残る）。いずれもバグ修正で、major を待つ理由はない |
| N5 | 性能・メモリ | 世代を越えて同一のアドレスに紐づく機構のリセット、プールの上限と寿命、`PathInfo` / `ResolvedAddress` / フィルタ文字列キャッシュの無限 Map の寿命境界 |
| N6 | 鍵付き購読 `$eq` | D7 の回答候補（[調査 §10.1](./state-next-major-tech-survey.ja.md)）。`$eq(path, key)` は `path` の値が `key` に等しいかを、評価中の getter の行を `key` で購読して返す。書き込み側は旧値・新値の鍵の行だけを更新する。試作で選択変更 1 万行 20 ms → 0.2 ms、id を依存なしで鍵にすれば 1 行削除 48 → 12.7 ms・交換 1.0 ms で選択が行に付いて行く。+0.3 KB gzip、既存テスト全緑。追加 API なので 2.6.x で先行できる。書き方は `$eq(path, value)` / `$eqPath(path, keyPath)` / `$eqIndex(path, level)` の 3 形（調査 §10.10。`$eqIndex` は index に付く選択のまま削除 17.5 ms）。**`packages/state` に実装済み（未コミット。README ja/en「鍵付き選択」、型、VS Code 拡張の preamble を含む）** |

N1〜N4・N6 は 2.6.x に先行して出せる。§7 の非推奨予告も 2.6.x に載る。

major の器に載せるか、独立して進めるかを §6 で決める。

## 6. 決裁が必要な論点

| ID | 論点 | 選択肢 | 推奨 |
|---|---|---|---|
| D1 | エンジンをどうするか | (a) 局所改善 (b) core / DOM アダプタの段階置換 (c) 全面書き直しと新文法 | **(b)**。(c) は比較試作が勝ち、移行を説明できるようになってから（監査 §7） |
| D2 | 旧文法の互換層 | (a) 出さない (b) 移行期間だけ旧文法を新 AST にパースする | 破壊的変更の件数（B1〜B5・B12）次第。**(b)** を既定にし、変換できない意味変化は診断で出す |
| D3 | 分割ロードの既定形 | 自己完結の full / auto は残すか | **残す**。ゼロ設定と既存の SRI 契約（[sri.ja.md](./sri.ja.md)）がそこに乗っている。明示 ESM 合成を第 2 形式として足し、宣言からの自動分割は後回し |
| D4 | エイリアスの寿命 | 旧名を何リリース残すか | README の非推奨運用（最低 1 minor の lint / ランタイム通知）を満たす。3.x の間は残し 4.0 で外すのが既定 |
| D5 | state 以外を壊すか | router・I/O ノード・protocol に、この機会でしか直せない破壊的変更はあるか | 棚卸しが未実施。**着手前に 1 度洗う**。無ければ版数追随のみ |
| D6 | [#2](https://github.com/wcstack/wcstack/issues/2) を 3.0 に入れるか | (a) 入れる (b) 3.x の minor に回す | **(b)**。新構文は非破壊で足せる。3.0 の範囲を意味論と配布に絞る |
| D7 | 選択（selection）の契約 | 通常の getter で O(1) を約束するか | **約束しない**。最適化された選択を API で支援し、通常 getter が O(N) になる場合を公表する（監査 §4.2）。支援する API の候補は N6 の鍵付き購読 `$eq`（調査 §10.1: 選択 0.2 ms、id 鍵で削除 12.7 ms・交換 1.0 ms） |
| D8 | 鍵付き購読（N6）の出荷 | (a) 2.6.x で `$eq` / `$eqPath` / `$eqIndex` の 3 形とも出す (b) `$eq` / `$eqPath` だけ先行し `$eqIndex` は 3.0 (c) 3.0 まで待つ | **(a)**。追加 API で既存挙動に触れず、実装済み・全テスト緑（調査 §10.10）。出せば公開名になるので、名前だけは出荷前に確定する。残作業は SSR 経路のテスト・DevTools 露出（D13）・`wcstack-skill` の追随 |
| D9 | 消去の割り当てパッチ（添字ループ＋親ごとのスキップ件数）の出荷 | (a) 2.6.x (b) 3.0 | **(a)**。意味論不変・実装済み・全テスト緑（調査 §10.12 追記 2）。消去 22〜72 → 18〜20 ms で監査ベンチの消去に直接効く |
| D10 | プラン初期描画の出荷 | (a) 2.6.x に入れる (b) 3.0 の「template plan と行インスタンスの分離」（監査 §7）の器で入れる (c) 見送る | **(b)**。効果は 1 万行 −10%・warm 1,000 行 −27% だが、監査ベンチの指標（cold 1,000 行）は動かない（調査 §10.13・§10.15）。葉 slot 用の適用経路が 1 本増えるので、行インスタンスの再設計と一緒に載せる方が保守面で軽い。1 万行規模を 2.6.x で急ぐ理由があれば (a)（門付きで局所） |
| D11 | 行 record ＋ session 共有の出荷 | (a) 3.0 (b) 2.6.x | **(a)**。`BindingSession` の中核（差分 372 行）と公開面（`disposeBindings` / `destroyRow`、`getRecord` の合成ビュー、共有 session の deferred 規則）に触り、効果はヒープ −16% で時間は不変（調査 §10.7・§10.14）。3.0 の器（監査 §7）で入れる |

| D13 | S3 の readiness barrier（未 install の機能を宣言が要求したとき）の発火時点 | (a) `_state` setter（宣言の評価時）で throw (b) 最初の読み書きで throw (c) console.error に留める | **(a)**。宣言の直後に名指しで落ちる方が原因に近い。`auto` / full では起きない（要件 §10） |

| D16 | フィルタ実関数の解決時機（設計案 §9、`features/formats` の前提） | (a) 解析時に作る（現行） (b) 束縛計画の段で登録簿を引く | **(b)**。文法段だけなら 1.7〜3.2 KB gzip（調査 §4.3）で、書式フィルタ群を `features/formats` に切り出せる。解析時 throw だった「未知フィルタ」の診断は束縛計画の段へ移す |

## 9. フェーズ

1. **意味論を凍結する** — §3 の再現例を回帰テストに変え、readonly・空値・リテラル型・スコープ能力・ready / error を決める。文法の正本を 1 つにする。
2. **配布を直す** — N1〜N3。生成物のコピーではなく Rollup テンプレートと同期を変える。
3. **試作を比べる** — 改善した現ランタイム 対 新 core / DOM アダプタ（**D20 で 3.0 の前提から外した**。3.0 は改良した現ランタイムで出す — D1）。アドレス統合は独立変数として扱う。
4. **major の範囲を決める** — 利用実態を棚卸しし、標準 / 選択 / 削除 / 互換に分類する。ソースのサイズは人気の証拠ではない。
5. **移行する** — §7。

1 のうち挙動を変えない部分（再現例の回帰テスト化）と 2 は 2.6.x で出せる。3.0 のタグは、1 の壊す修正（D20）・2・4 が終わってから切る。

## 10. リスクと未計測

- 監査は 1 台・1 リビジョンの探索的計測。古い `bench-run.json` との差は退行率ではない。長時間のリーク、モバイル、SSR の全挙動、全ワークロードの比較は未計測。
- 分割は要求数とレイテンシを増やし圧縮率を下げる。極小チャンクから始めない。base / 時間系 / コンポーネント / SSR の群で測る。
- エントリの SRI は動的に読み込むチャンクを覆わない。full と split で契約を分けたまま扱う（[sri.ja.md](./sri.ja.md)）。
- 宣言やフィルタから機能を読み込む設計には readiness の関門が要る。同期の getter / setter 評価の中で読み込まない。遅延 DOM・`setInitialState`・再接続・SSR ハイドレーションにも同じ関門が要る。
- 全機能を同じ意味のまま別実装へ移すと、サイズと複雑さは戻る（監査 §1）。
