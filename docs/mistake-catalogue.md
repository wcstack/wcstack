# Mistake catalogue

**日本語版**: [mistake-catalogue.ja.md](./mistake-catalogue.ja.md)

This catalogue lists the mistakes an app author can make with wcstack and, for each one, what tells the author. It is the record behind the 4.x goal in [v4-direction-2026-10.md](./v4-direction-2026-10.md) (ja): **no silent failure**. Either a page does what its author meant, or something says it does not.

The defects found after 4.0.0 were almost all silent. They sat between two packages and showed up only over time ([seam-apps.md](./seam-apps.md)). A fix usually added a lint rule. This catalogue keeps count of what is still silent, so each fix can be weighed against the others.

## What tells the author

Four layers, strongest first:

1. **The design.** The mistake cannot be written, or it does no harm. Nothing has to report it.
2. **The runtime.** The running page throws, or writes to the console: an error or warning, with or without a `wcs/` code. A page on `@wcstack/state/core` without the diagnostics add-on gets only the message number (`#47`), and that still counts. The author sees it while trying the page.
3. **The lint.** `wcs-validate`, `wcs-tsc` and the VS Code extension. Only lint reports it, so this is a **conditional silence**: an author who does not run the lint never hears of it. In the 2026-07 cold-start runs, AI authors ran it in none of 9 runs. That includes the runs that had read the command on the landing page.
4. **The documents.** A README, the skill or a design note says so, and nothing else does. This is a **silence**.

The 4.x goal is no entry in layer 4. The second goal is to move entries in layer 3 up to layer 1 or 2 where the information exists.

The runtime column describes the full entries (`/auto` and `.`, which install every add-on), because those are what the documents tell authors to load. When `/core` behaves differently, the entry says so.

## What an entry records

| Field | Meaning |
|---|---|
| `id` | Kebab-case name, unique |
| `mistake` | What the author writes, in one sentence (en, ja) |
| `effect` | What goes wrong for the user, or how the runtime reports it (en, ja) |
| `harm` | `data-loss`, `security`, `wrong-place` (content missing or in the wrong place), `stale`, `broken`, `degraded` |
| `lint` | The lint codes that report it, each with its severity (`varies` when the detection path decides). A code can appear in several entries when its cases behave differently at runtime |
| `runtime` | `designed-out`, `same` (the runtime reports the same `wcs/` code), `loud` (it throws or logs without the code), `silent` |
| `evidence` | For `same` and `loud`: a file and a text it contains, the runtime's message. Optional for `silent` |
| `disposition` | For a mistake the runtime does not report: see below |
| `breaking` | For `design-out`: would the change affect pages that are correct today |
| `note` | Anything a reader needs to weigh the entry (en, ja) |

Some lint codes are listed separately and not counted. Those that check the tools' own inputs (the sidecar manifest, the drift between a manifest and a live declaration), JSDoc types, and codes reserved but never emitted are not app mistakes.

## Dispositions

A mistake that only the lint or only the documents report carries one of these:

- **design out**: change a default or a behavior so the mistake cannot happen or does no harm. If that changes correct pages, it is **breaking**. It does not go into 4.x; it is on the **5.0 agenda**, which is built from these entries. If it is not breaking, it can go into 4.x.
- **runtime report**: the runtime has the information to say so in development, and 4.x adds the report. For `@wcstack/state` the check goes in the diagnostics add-on, unless it costs nothing in the core (536 B of room under the 20 KiB limit).
- **lint rule**: a mistake only the documents mention that a static check can see. 4.x adds the rule.
- **stays with the lint**: the runtime cannot see it. Lint is the strongest layer this mistake can reach.
- **nothing can see it**: neither a static check nor the runtime can tell. The documents are the only defence.

## Adding an entry

Add an entry when a seam app, the site tutorial, an issue or a review finds a mistake. A new lint code also needs an entry. Edit [scripts/mistake-catalogue.json](../scripts/mistake-catalogue.json), then run:

```bash
node scripts/sync-mistake-catalogue.mjs           # render the tables below
node scripts/sync-mistake-catalogue.mjs --check   # what CI runs
```

`--check` fails when:

- a code in the lint's registry (`packages/vscode-wcs/src/core/diagnostics.ts`) is missing from the catalogue;
- an entry's evidence file no longer contains its text, so the runtime message it relies on may be gone;
- an entry the runtime does not report has no disposition;
- the tables below are out of date.

## Found while cataloguing (2026-10-17)

Not all of the lint's text and severities have caught up with the 4.0 runtime. These are not in the tables above, which record what the runtime and the lint do today. Each one is a fix for the lint or its documents:

- **Messages that describe 3.x.**
  - `wcs/script-order` says the ledger is not captured live. 4.0 hands a late DevTools every binding.
  - `wcs/scan-declaration-invalid` says the runtime throws at load. Only the diagnostics add-on does.
  - `wcs/declaration-alias-read` tells the author to read `$stream` / `$renderedCallback` instead. Those also read `undefined` through `this`.
  - The registry's comments on `wcs/tag-member-unknown` ("silently ignored") and `wcs/getter-cycle`, and the header of `wcs/named-state-deprecated` (the runtime fails on `name=`), are 3.x too.
- **The `/core` message format.** The vscode-wcs README says `/core` prints `[wcs/template-syntax] #203 "outerHTML"`. Since 4.0.0-rc.3 it prints `#203 "outerHTML"`.
- **Checks narrower than the runtime.**
  - `wcs/mount-path-invalid` misses whitespace and a `*` inside a segment (`mount="a b"`, `mount="a*"`).
  - `wcs/tag-member-unknown` skips common DOM properties (`title`, `hidden`, `id`) on `wcs-*` tags. The runtime refuses them with `#38`.
  - `public/filterMeta.ts` says `lt`, `le`, `gt` and `ge` accept strings. The runtime throws `#28` on a string.
- **Warnings where the runtime fails.** For these, the page's initialization or a binding fails, but the lint only warns:
  - `wcs/filter-arg-type`, `wcs/tag-member-unknown`, `wcs/getter-cycle`, `wcs/index-arity`
  - `wcs/token-misconfigured` (`#1201`), `wcs/token-undeclared` (`command.`)
  - `wcs/recursion-unsupported` (an undeclared `**` getter key), `wcs/binding-path-missing` (a missing top-level key)
  - `wcs/input-nested-write` loses data and is only a warning, so it passes the skill's `--errors-only` gate.
- **A rule left from 3.x.** `wcs/binding-type-expectation` asks for a boolean in `if:` with `else:`. 4.0 tests truthiness.
- **Not verified.** `wcs/array-index-assign` may report `this.items[0] = x; this.$postUpdate("items.0")`, which the runtime supports.
