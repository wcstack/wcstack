## 付録: 統合戦略案 全文（2026-08-02 提示・見出しレベルのみ調整・本文は原文まま）

#### ― Web APIを、フレームワークをまたいで配線できるHTMLノードへ ―

### 1. 戦略結論

wcstackは、**ReactやVueに代わる新しいフロントエンドフレームワークとして売り込まない。**

主戦場を「フレームワーク選定」から外し、

> **Web APIを、フレームワークをまたいで配線・再利用できるHTMLノードへ変えるブラウザI/O基盤**

として市場に提示する。

wcstackの本当の差別化は、WebSocket、Fetch、Storage、Camera、GeolocationなどをCustom Elementsでラップしていることそのものではない。

重要なのは、

> **共通のbinding contractを持つI/Oノードを、状態・UI・別のI/Oノードへ統一的に接続し、HTML上にアプリケーションの実行グラフを構成できること**

である。

React、Vue、Svelte、Solidなどからも同じI/Oノードを利用できるため、特定フレームワーク専用のhook、composable、storeとして非同期処理を作り直す必要がない。現在のREADMEでも各I/Oノードがwc-bindable-protocolを実装し、複数フレームワークから薄いadapter経由で接続できる構造が示されている。

したがって目指す位置は、

> **「新しいフレームワーク」ではなく、「複数のフレームワークが共有できるブラウザI/Oエコシステム」**

である。これは戦略案2の「ReactでもVueでもSvelteでも使われる共通I/O層になる」という方向を継承する。

---

### 2. なぜこのポジションなのか

#### 2.1 フレームワークとして売ると不利になる

wcstackを「41パッケージからなる新しいフロントエンドフレームワーク」として提示すると、利用者は自動的にReact、Vue、Svelte、Alpineなどと比較する。

その場合の判断基準は、

* 利用者数
* GitHub Stars
* 求人数
* UIライブラリ
* 外部事例
* コントリビューター数
* 長期保守への安心感

となる。

現状では技術資産の量に対して外部利用の証拠が不足しているため、この比較軸では非常に不利である。戦略案3でも、外部issueが存在せず、npm download数も実採用を示す指標として扱えないことが指摘されている。

したがって、

> 「Reactより優れているからwcstackへ移行してください」

という戦略は採らない。

---

#### 2.2 単なるWeb APIラッパーとしても売らない

一方、

> WebSocketをCustom Elementにしました
> CameraをCustom Elementにしました

だけでも十分な差別化にはならない。

戦略案4が指摘するように、個別Web APIをCustom Elements化した先行例は既に存在する。したがって「Web APIをタグにしたこと」そのものを新規カテゴリとして主張するのは危険である。

wcstackが前面に出すべきなのは、

> **多数のI/Oノードが同一プロトコルを持ち、互いに合成でき、状態管理や複数フレームワークとも接続できること**

である。

つまり、

**TagではなくNode。
WrapperではなくWiring。
Framework-independentだけでなくFramework-shared。**

という位置づけにする。

---

### 3. 商品の構造

wcstackを一つの巨大なフレームワークとして説明せず、4層に分ける。

#### Layer 1 ― Bindable I/O Nodes

最初の入口。

代表例：

* Fetch
* WebSocket
* SSE
* Storage
* Upload
* Timer
* Worker
* IntersectionObserver
* ResizeObserver
* Geolocation
* Camera
* Notification
* Clipboard
* Sensor系API

利用者は既存システムを置き換える必要がない。

最初は、

```html
<wcs-ws></wcs-ws>
```

のように1ノードだけ導入できる。

---

#### Layer 2 ― Wiring / Composition

ここをwcstackの中核的差別化とする。

単一ノードではなく、

```text
Web API
   ↓
I/O Node
   ↓
State / Path
   ↓
I/O Node
   ↓
UI
```

という接続をHTML上に記述する。

たとえば、

```text
Intersection
    ↓
Fetch
    ↓
State
    ↓
UI
```

による無限スクロールや、

```text
Timer
   ↓
Geolocation
   ↓
WebSocket
```

といった非同期処理の組み合わせを、各コンポーネント内部に命令的な接着コードを書き散らさず構築する。

**複数ノードが組み合わさった瞬間に、wcstackは「便利タグ集」から「アプリケーション基盤」に変わる。**

---

#### Layer 3 ― Framework Interoperability

I/Oノードをwcstack専用資産にしない。

同じノードを、

* Vanilla HTML
* wcstack/state
* wcstack/signals
* React
* Vue
* Svelte
* Solid

などから利用できる構造を維持する。

この価値は、

> Reactからwcstackへ移行できる

ことではない。

> **Reactで作ったI/O資産を、次のVueプロジェクトでも使える**

ことである。

戦略案2で提案された「フレームワークごとに重複していた非同期処理を共通資産化する」という経営向けメッセージは、この層の価値を端的に表している。

---

#### Layer 4 ― HTML-first Application Stack

wcstackを気に入った利用者だけがここまで進む。

* `@wcstack/state`
* path getter
* router
* autoloader
* SSR / hydration
* signals
* DevTools
* lint

を使えば、wcstack単独でもアプリケーション全体を構築できる。

stateやrouterは「格下げ」するのではなく、

> **wcstack I/Oエコシステムを最も直接的に利用できる純正ホスト**

として位置づける。

---

### 4. 導入モデル ― Land and Expand

導入順序は次のようにする。

##### Step 1

**ノードを1個使う**

Fetch、WebSocket、Cameraなど、既存コードで面倒になっている箇所を1個だけ置き換える。

##### Step 2

**ノードを2個以上接続する**

stateまたは既存FWとのbindingを利用してI/Oノードを組み合わせる。

ここで初めてwcstack固有の価値を体験させる。

##### Step 3

**I/O実装を複数画面・複数プロジェクトで共有する**

React用、Vue用と書き直すのではなく、同じノードを再利用する。

##### Step 4

**必要であればstate/routerへ拡大する**

新規管理画面、小規模アプリ、マイクロフロントエンドなどから採用する。

##### Step 5

**組織の共通基盤へ昇格する**

社内固有API、認証、ファイル処理などを独自I/Oノードとして実装し、Node Catalogとして共有する。

---

### 5. 最初に狙う市場

#### 第一優先 ― HTML-first / buildlessな既存システム

対象例：

* サーバーサイドレンダリング中心の業務システム
* CMS
* 管理画面
* 静的サイト
* 小規模Webアプリ
* jQueryが残る保守システム
* ビルド環境を追加しにくいシステム

この市場では、

> scriptタグ1行＋Custom Element

という導入コストがそのまま競争力になる。

特に、

> **全面的なSPA化はしたくないが、非同期処理だけ現代化したい**

という問題への回答として訴求する。

---

#### 第二優先 ― 複数フレームワークを抱えるチーム

対象：

* ReactとVueが混在
* プロダクトごとにFWが異なる
* マイクロフロントエンド
* デザインシステム・フロントエンド基盤担当

売るものはUI統一ではない。

> **Fetch、WebSocket、Storage、Worker、Camera等の非同期処理を共通資産化する。**

という話にする。

---

#### 第三優先 ― Web標準志向の開発者

* Vanilla JS
* Web Components
* Lit
* buildless
* zero dependency
* 長寿命なWebアプリ

この層は初期支持者として重要だが、この市場だけに閉じない。

---

#### React/Vue開発者への位置づけ

Reactユーザーを主戦場にはしない。

Reactには既に豊富なhookライブラリが存在するため、

> React用WebSocket hookより短い

といった比較を主張する必要はない。

Reactデモの役割は、

> **wcstackのI/Oノードがwcstack自身にロックインされていない**

ことを証明することに置く。

---

### 6. AIの位置づけ

AIを独立した「顧客市場」として扱わない。

AI coding agentは、

> **wcstackを発見・理解・生成・検証する新しい開発チャネル**

として扱う。

そのため全体を、

1. Human-readable
2. Machine-readable
3. Machine-verifiable

にする。

既に存在する、

* AGENTS.md
* wcstack skill
* manifest
* `@wcstack/lint`
* stable diagnostic code
* DevTools

を活用する。

訴求は、

> AIならwcstackを簡単に書ける

では弱い。

> **AIが生成したコードを機械的に検査し、失敗してもgenerate → validate → fixループで収束できる**

ことを価値にする。

---

### 7. 最重要デモ

機能数ではなく、「何が違うのか」が30秒で分かるものを優先する。

```text
     ↓

     ↓
UI
```

として構築する。

ここではコード量比較より、

ことを見せる。

という一点である。

ことを示す。

### 8. Webサイトの再構築

現在の最優先課題の一つは、製品思想と実際の体験導線を一致させることにある。

戦略案3では、buildless/CDN一発を訴求しているにもかかわらず、LPから動くデモへ直接進めない点が重大な欠陥として挙げられている。

#### Hero

思想としての

> **What if the browser had these built in?**

は残してよい。

ただし直下で必ず実利を説明する。

##### 推奨コピー

> **Composable Web APIs as bindable HTML nodes.**

日本語：

> **Web APIを、フレームワークをまたいで配線できるHTMLノードへ。**

補足：

> Fetch、WebSocket、Storage、Camera、Sensors。
> HTMLで接続し、React・Vue・Svelte・Vanillaから同じノードを再利用できます。

---

#### Hero直後

「41 packages」の説明ではなく、30秒で操作できるLive Demoを置く。

その後、

##### Compose

複数I/Oノードを配線できる。

##### Reuse

複数フレームワークから同じI/Oノードを使える。

##### Verify

lintとDevToolsで配線を検証できる。

##### Expand

state、router、SSRまで拡張できる。

という順序にする。

### 17. 戦略上の仮説と撤退条件

この戦略も仮説である。

特に検証すべき仮説は、

> **単体Web APIラッパーではなく、統一プロトコルによる複数I/Oノードの合成可能性に需要がある**

という一点である。

したがって半年後に、

* 単体タグしか使われない
* 2ノード以上の合成事例が生まれない
* framework横断再利用が発生しない
* 第三者ノードが作られない

のであれば、

「ブラウザI/Oエコシステム」という商品定義を再検討する。

逆に、

> 別々の利用者が複数ノードを組み合わせ始める

ことが確認できれば、wcstack最大の独自性が市場でも成立したと判断できる。

---

### 18. 最終メッセージ

wcstackの売りは、

> WebSocketがタグになった

ことではない。

> path getterが珍しい

ことだけでもない。

> buildlessである

ことだけでもない。

最も重要なのは、

> **ブラウザの非同期機能を共通プロトコルを持つI/Oノードへ変換し、それをHTML上で配線し、さらにそのノードをReact、Vue、Svelteなどからも共有できること**

である。

そのため最終的な戦略を一文にすると、

> **wcstackを新しいフロントエンドフレームワークとして売るのではなく、Web APIを共通プロトコルでHTMLノード化し、複数ノードを配線・合成し、複数フレームワークから共有できる「ブラウザI/Oエコシステム」として普及させる。単一ノードから導入させ、合成、再利用、state、router、SSRへ段階的に拡張する。AIは顧客ではなく、このエコシステムを発見・生成・検証する流通チャネルとして組み込む。**

これをwcstackのGTM戦略の中心とする。
