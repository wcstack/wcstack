# state エンジン再設計 — アドレッシングの見直し

調査日 2026-09-24。対象 `@wcstack/state` 3.3.0（main `a796d712`）。作業ブランチ `research/state-engine`。前提は [scope-classification.ja.md](./scope-classification.ja.md) の決定状況（mount・volume・コンポーネントの mount はコア外）。

著者の問い「パス＋インデックス（＋state）の台帳作成に時間がかかっていないか」に、3.3.0 の実測で答える。そのうえで、新エンジンのアドレッシングを提案する。**提案は未決定。** 決めてほしい点は §5。

## 0. 要約

1. **かかっている。** 10,000 行の作成では、1 行あたり（プロファイラ下）次のとおり。
   - 台帳への書き込み 8.0µs＋アドレスの生成・検索 3.7µs＋行の初期化とセッション 2.2µs＝**約 14µs**
   - 比較: DOM のネイティブ呼び出し 5.7µs とテンプレート処理 1.9µs の合計の約 1.8 倍
   - GC の 5.9µs も、多くはこの記帳の割り当てから来る
2. **行を作らない操作でも重い。** 10,000 行で選択を普通の getter で切り替えると、アドレスの生成・検索に 5.2ms かかる（プロファイラ下 JS 時間の約 17%）。読むたびに行ごとのアドレスを作り直すため。
3. **原因は構造にある。**
   - 現行は「パス × 行 × state」の組を身元オブジェクトとして intern（同じ組には同じオブジェクトを返す仕組み）し、それをキーに大域の台帳（WeakMap など）へバインディングやキャッシュを登録する。
   - 行とバインディングが増えるたびに、身元の生成と台帳への登録が掛け算で増える。
   - 台帳が大域で複数のツリーにまたがるので、state 次元も外せなかった。
4. **新エンジンでは「身元＋大域台帳」をやめ、「所有の木＋直接参照」に置き換える。**
   - パスはテンプレートの計画時に一度だけ解決する。
   - 行は 1 つのオブジェクトで、自分のデータ・添字・バインディング・キャッシュを直接持つ。
   - エンジンの実例をルート（`<wcs-state>`）ごとに持つので、state 次元は構造的に消える。mount/volume がコアから外れたことで可能になった。
5. **過去の統合検討が閉じた理由は、新設計では前提ごと消える。**
   - 2026-09 の統合は「素の読みが 1〜5ns 遅くなる」ので閉じた。原因は、読みの経路に節点が 1 段増えることだった。
   - 新設計のバインディングの読みは、行が持つデータへの直接アクセスで、身元の引き当て自体がない。
6. **次は小さな試作で数値を確かめる。** 範囲と合否基準を先に固定する（§4）。

### 1.3 10,000 行での選択の切り替え（普通の getter、1 回あたり ms、プロファイラ下）

実時間は 30.1ms。アドレスの生成・検索は 5.2ms。
- 内訳: `createAbsoluteStateAddress` 1.1、`createStateAddress` 1.1、`getTreePath` 0.5、`at` 1.2、ほか
- 比べて、読みは 4.4ms、反映は 6.1ms。

3.0 の計数（[tech survey](../state-next-major-tech-survey.ja.md) §8.4）では、この操作は 1 行につき次を行っていた。
- アドレスの生成 6 個（state 2・absolute 2・tree 2）
- getter の読み 2 回、get トラップ 3 回、バインディングの検索 1 回、反映 1 回

同じ形の仕組みを最小限に作った模型では、1 行あたり評価 1 回・割り当て 0 回で、現行とは約 50 倍の差があった。**計算量の形ではなく、1 行あたりの定数が問題**である。

## 2. 現行の構造と、そうなる理由

**アドレスの表現は 8 種類ある**（パス文字列・`ResolvedAddress`・`PathInfo`・`ListIndex`・`StateAddress`・`LoopContext`・`TreePath`・`AbsoluteStateAddress`）。
- 読み書きのたびに「文字列 → Resolved → StateAddress → AbsoluteStateAddress」と持ち上げる。
- 各段は入れ子の WeakMap で intern される。
- `ListIndex` は行ごとに uuid 文字列・親へのポインタ・遅延の添字配列・WeakRef の連鎖を持つ。

**バインディングとキャッシュの所在は、大域の台帳で引く。**
- 主な台帳（すべてモジュール直下の WeakMap/WeakSet/Map）:
  - アドレス → バインディング（アドレス台帳・パターン台帳）
  - ノード → ループ文脈
  - ノード → 登録済みの印
  - セッション → 関心のあるバインディング
  - 行 → 既知のバインディング
  - アドレス → キャッシュ
  - アドレス → 描画の基準値
  - 配列 → ListIndex 群
- モジュール直下の WeakMap/WeakSet は、src 全体で 118 個ある。
- 行を 1 つ作るたびに、ノードごと・バインディングごとにこれらへ登録する（§1.1 の「台帳への書き込み」）。
- 行を捨てるときも、登録を外す（または GC に任せる）。

**なぜ大域の台帳なのか。**
- 行・バインディング・キャッシュの間に所有の参照がなく、どれも「身元をキーにした表引き」でつながっている。
- 依存の伝播はパス文字列の依存グラフを歩き、行ごとのアドレスを作り、台帳からバインディングを引く。
- updater はモジュールに 1 つで、束ねも台帳も複数のツリーにまたがる。そのため身元に state 次元（どのツリーか）が要り、外せなかった（[統合設計](../state-address-unification-design.md) の確定事実）。
- 同じ配列を 2 つの state に入れると `ListIndex` がツリー間で共有される。これも大域の表（配列 → ListIndex）に由来する。

**過去の見直しとの関係。**
- 2026-09 の統合検討（案 A）は、この 8 種類のうち絶対側を統合しようとした。現行構造の中で素の読み（約 42ns）に節点を 1 段足すことになり、1〜5ns の悪化が床を超えて閉じた（設計書 §12）。
- 閉じたのは「現行構造の中での統合」であって、台帳と身元という構造そのものは残っている。

## 3. 新しいアドレッシングの提案

### 3.1 原則

1. **パスは計画時に解決する。**
   - テンプレートの計画（行の設計図）を作るとき、各バインディングのパス `users.*.name` を「どのリストの行の、どの欄か」に翻訳しておく。
   - 実行時に文字列を解析したり、身元オブジェクトを作ったりしない。
   - パス文字列は作者向けの約束（文法は変えない）として残し、内部では番号（パターン ID）で扱う。
2. **所有の木で持つ。**
   - 形: ルート → リストの実例 → 行 → バインディング。
   - 行は 1 つのオブジェクトで、自分のデータ（要素の値）・添字・親の行・バインディングの配列・getter キャッシュを直接持つ。
   - 行を捨てれば、配下はまとめて GC される。登録と解除の台帳はない。
3. **エンジンの実例はルートごと。**
   - `<wcs-state>` ごとに、依存グラフ・更新の待ち行列・キャッシュを持つ実例を作る。
   - マイクロタスクの束ねは、待ちのある実例を順に処理するだけにする。
   - 身元に state 次元が要らなくなる。同じ配列を 2 つのルートに入れても、ルートごとに別の行になる（正しさが構造で決まる）。
4. **`ListIndex` を行そのものに置き換える。**
   - 添字は行のフィールドで、並べ替えのときに書き換える。
   - `$1`・`$2` は親の行をたどって得る（深さはふつう 2 以下）。
   - uuid・WeakRef の連鎖・遅延の添字配列は持たない。
5. **購読はパターンの粒度、配り先は木の粒度。**
   - 依存グラフはパターン ID 間の辺として持つ。静的な辺は計画時、getter の読みから来る動的な辺は初回評価時に張る。
   - トポロジカル順位はグラフが変わったときだけ計算し直す（現行は伝播のたびに計算し直している）。
   - 書き込みの配り先は、リストの実例の `rows` 配列から該当する行を直接たどる。
6. **キャッシュは行の上に置く。**
   - ワイルドカード getter の値は `row.cache[スロット]` に、ワイルドカードのない値はルートの表に置く。
   - 絶対アドレスをキーにした大域キャッシュは持たない。
7. **イベントの行は閉包で持つ。**
   - 行のイベントハンドラは行オブジェクトを閉包で捕まえる（またはリスト単位の委譲で、ノードから行を 1 回引く）。
   - 現行の「`await` の後で `$1` が失われる」（`poc.asyncOnLoopContext`）も構造的に解消する。

### 3.2 データ構造の素描（型は説明用）

```ts
interface Engine {            // <wcs-state> ごとに 1 つ
  data: object;               // 状態の木（作者のオブジェクト）
  patterns: PatternTable;     // パス文字列 ⇄ パターン ID、親子・ワイルドカード深さ・getter 印・依存辺
  rootCache: Map<PatternId, CacheCell>;  // ワイルドカードを含まないパスのキャッシュ
  lists: Map<PatternId, ListInstance>;   // ルート直下のリスト（例: users）
  dirty: Queue;               // 束ねの待ち行列（エンジンごと）
}
interface ListInstance {      // 1 つの for バインディング（とその親の行）ごとに 1 つ
  pattern: PatternId;         // 例: users
  parentRow: Row | null;      // 入れ子リストなら親の行
  rows: Row[];                // 添字順。配り先はここから直接引く
}
interface Row {               // 1 行 = 1 オブジェクト
  list: ListInstance;
  index: number;              // 並べ替えで書き換える
  item: unknown;              // 行の値（users[index]）
  bindings: Binding[];        // 計画から一括で作る
  cache?: CacheCell[];        // スロット番号で引く getter キャッシュ（遅延）
  children?: ListInstance[];  // 入れ子の for
}
```

### 3.3 操作ごとの流れ

- **行の作成**: 計画のテンプレートを複製し、計画のノード位置で節点を取る。`Row` を 1 つと、`bindings` を計画のスロット数ぶん作る。台帳への登録はない。
- **行の中の読み**:
  - `users.*.name` のバインディングは `row.item.name` を読む（計画済みのアクセサ）。
  - getter の中の `this["users.*.first"]` は、文脈の行から `row.item.first` を読む。
  - `this.$1` は `row.index`。
- **書き込み**: `this["users.3.name"] = v` の流れは次のとおり。
  1. パターン ID と添字の組 `[3]` を得る。
  2. データを書き換える。
  3. 依存辺をたどる。
  4. `lists[users].rows[3]` の該当スロットのバインディングを汚す。
  5. 同じ深さの依存 getter（`users.*.fullName`）は、同じ行のキャッシュを汚す。
  6. 深さの違う依存（`$getAll` による集計 `total`）は、ルートのキャッシュを汚す。
- **選択の切り替え（普通の getter）**: 依存 getter の評価は各行で 1 回ずつで、O(N) のまま（普通の getter の限界。O(1) にしたいときは `$eq` を使う）。行ごとのアドレスの生成・台帳の検索はなくなる。
- **並べ替え・削除**: 値に基づく差分で行を動かし、`row.index` を書き換える。添字を読む getter だけを汚す（現行の movedRows と同じ考え）。
- **全消去**: `rows` を空にして DOM を外す。台帳の登録を外す処理はない。

### 3.4 守るべき制約（設計の宿題）

| 制約 | 内容 | 新設計での扱い（案） |
|---|---|---|
| 書いた直後に読むと新しい値が見える | `s.n=5; s.d===50` が成り立つ（過去に遅延伝播の案を潰した制約） | 書き込み時に依存キャッシュへ汚れ印を付ける（行やルートのセルの旗を立てるだけなので軽い）。または版番号で読み時に検証する。どちらかを試作で決める |
| 描画されていない行の読み | `$getAll`・明示的な添字の `$resolve`・描画なしの購読（`$watch` の土台）・`$eq` | 行オブジェクトを描画とは独立に持てるようにする（状態側の行）。DOM の行はそれを参照するだけ。描画されていない行は、必要になったときに遅延で作る |
| 差分をまたいだ行の同一性 | `$eq` の購読や `$listKeys`（後付け）が行の同一性に依存する | 差分の間だけ `Map(値 → 行)` を作り、行を引き継ぐ |
| GC | 大域の強参照の表を持たない | 所有の木に閉じる。ノード → 行の引き当てがどうしても要る所だけ、リスト単位の WeakMap にする |
| 要素書き込みの位置モデル | 第 3 回の決定（§9.3） | 行の `item` を差し替えて配下を汚すだけで済む。所有の木と相性がよい |

### 3.5 期待値（仮説）

- 行の作成で記帳に使う 1 行あたり約 14µs（プロファイラ下）を、行オブジェクト 1 つ・バインディング配列 1 つ・バインディングの小オブジェクト数個・イベント登録に縮める。
- 目標は、記帳を DOM 側（約 7.6µs）より十分小さくすること。
- これは決定済みの性能目標（ウォーム 1,000 行作成 ≤ 7.8ms、コールド 10,000 行作成 ≤ 74ms）に届くかどうかの主因になる。
- **これは仮説で、未計測。** §4 の試作で確かめる。

## 4. 確かめ方（試作の提案）

**範囲**
- 新パッケージの骨格に、アドレッシング・所有の木・リスト描画・テキスト／クラス／イベントのバインディングだけを実装する。
- 目的はアドレッシングの検証で、機能の網羅ではない。
- 計測ページは現行と同じもの（`packages/state/__e2e__/benchmark`）を使う。

**計る操作**
- 作成 1,000（ウォーム・コールド）、作成 10,000（コールド）、追加 1,000、10 行ごとの更新、入れ替え、1 行削除、全消去
- 選択の切り替え 2 種（普通の getter と `$eq`）

**比べる相手**
- 現行 3.3.0 と DOM 直接（`clone-path`）。
- 同じページのままバンドルを差し替える（`e2e/bench/jsfb-verify.mjs --bundle`）。
- 同じバンドル同士を 2 回測り（A/A）、その差をノイズの床とする。

**合否（数字を見る前に固定する）**
- 決定済みの 2 指標（ウォーム 1,000 行 ≤ 7.8ms、コールド 10,000 行 ≤ 74ms）
- それ以外の操作は現行より悪化しない
- 書いた直後の読みの一貫性を検証するテストが通る

**費用の見込み**: 数日規模の捨てブランチ。合格すれば新エンジンの土台として育てる。不合格なら、どの記帳が残ったかを群別に測って設計へ戻す。

## 5. 著者に決めてほしいこと

**決定（2026-09-24 第 4 回）**: 1・2 は提案どおり。3 は「両方測って速度を検証し、同程度なら複雑性が少ないほうを採用」。→ 試作の結果は [spike-results.ja.md](./spike-results.ja.md)（dirty を採用）。

以下は決定前の問い（記録として残す）。

1. **方向。** 「身元＋大域台帳」をやめ、「所有の木＋直接参照」「ルートごとのエンジン実例」にする方向で試作に進むか。
2. **試作の範囲と合否基準。** §4 のとおりでよいか。
3. **書いた直後の読みの実現方式。** 汚れ印（書き込み時）と版番号（読み時の検証）を、試作で両方測って選ぶか、先にどちらかに決めるか。
