# 4.0 エンジンの規模の検証

作成 2026-10-06（branch `research/state-engine`、4.0.0-rc.5 の後）。

## 0. 要約

- **問い**: 4.0 のエンジン（`packages/state`）は、大規模なアプリでも破綻しないと示せるか。
- **答え**: 示せる。「破綻しない」を 4 つの検証できる性質（局所性・線形性・有界性・限界の明示）と規模での正しさに分け、規模を何段か変えて費用の伸び方を測る。試験的な計測とスイートで、ほとんどの軸は費用が規模に依らないことを確かめ、破綻する箇所を 3 つ見つけた（§3）。
- **決定**: 3 つとも直した（core +396B）。検証は `packages/state/bench/scale/` のスイートにし、happy-dom で仕事の回数と伸びの指数を、Chromium で絶対時間とヒープを取る（§4）。

## 1. 「破綻しない」の分解

| 性質 | 主張 | 判定 |
|---|---|---|
| 局所性 | 1 回の更新の費用は、それが届く範囲だけで決まり、アプリの残りの大きさに依らない | 仕事の回数が無関係な規模に対して一定。時間の指数 k ≈ 0 |
| 線形性 | 全体に触れる操作（マウント・一覧の作成や置き換え・全行が読む値の書き込み）は O(n) か O(n log n) | 仕事の回数が n に比例。k ≤ 1.25 |
| 有界性 | 長く使っても、保持するメモリと内部の表が頭打ちになる | 繰り返しの回数に対して表の大きさとヒープが横ばい |
| 限界の明示 | 上限（getter の入れ子 128 段、`$1`〜`$128`、drain 32 パス、描画の連鎖 100）を超えると、スタック溢れでなく診断を出して止まる | 決まった番号のエラーが出る。`RangeError` が出ない |
| 規模での正しさ | 大きな状態にランダムな操作を流しても、DOM が状態どおり | 参照モデルとの食い違いが 0 |

k は「費用 ∝ n^k」の指数で、規模を変えた点の log-log の傾き。時間は機械とノイズに左右されるので、判定の主役は仕事の回数（エンジンの関数が呼ばれた回数、DOM の変更の数）にし、時間の k は補助にする。

## 3. 見つかった問題と修正

### 3.1 同じ値が並ぶ一覧の reconcile が O(n²) になる

- **形**: 0 / 1 のセルを平らな一覧に並べた盤面（ライフゲーム、ピクセル、座席表）、タグや数値の一覧。値が重複するプリミティブの一覧を、先頭と末尾の両方が変わる形で置き換える。
- **原因（1）計算量**: `reconcile`（`src/list.ts`）は中央の区間で、古い行を値ごとのバケットに入れ、新しい位置に前から渡す。重複のバケットは配列で、`shift()` で取り出していた。`shift()` は配列全体を詰めるので、バケットが V8 の大きいオブジェクトの領域に入る大きさ（約 3 万要素）を超えると、1 回ごとに要素数に比例する。バケットの取り出しだけを切り出して比べると、90,000 個で `shift()` 4,200 ms、カーソル 7 ms。
- **原因（2）DOM の移動**: 前から順に渡すと、1 セル変わっただけで、その後ろの同じ値の行がすべて 1 つずつずれる（行の位置が全部変わり、DOM がほぼ全部動く）。
- **修正**:
  - バケットを末尾から詰め、`pop()` で取り出す（取り出す順は前からのまま）。
  - 中央の区間で、同じ位置に同じ値がある行をまずその場に残し、残りを前から渡す。オブジェクトの一覧では、同じ位置の同じオブジェクトはもともとその行なので、結果は変わらない。
- **結果**: P8 の reconcile は 90,000 セルで 4.6 s → 6.4 ms（k 0.85）。書き込み＋drain は 40,000 セルで 1.26 s → 9 ms（2 セルの行だけを作り直す）。
- **振る舞いの変化**: 重複した値の一覧の全体の代入で、どの行（DOM）を使い回すかが変わる。`$watch("items.*")` は「一覧に入った行」で発火するので、発火する位置が変わることがある。`regression-3x-list-baseline.test.ts` の #359 は `[[3, 2], [4, 3]]` → `[[3, 0], [4, 3]]` になり、3.x と同じになった。`coverage-engine.test.ts` の再利用のテストを新しい方針に直し、方針のテストを 2 件足した。

### 3.2 動的なキーのパターンが増え続ける

- **形**: データから組み立てたパスで読み書きする。`get view() { return this["usersById." + this.selectedId]; }`、`this["log." + id] = entry`、`$resolve("dict." + key, [])`、オブジェクトの数値のキー（`users.123.name`）。
- **原因**: エンジンはパスのパターンを 1 度作ると消さない（`PatternTable`）。さらに getter の source は「これまでの評価で読んだもの全部」の和集合で、減らない。そのため、使った id の数だけパターンと依存の辺が残る。`dict` を置き換える書き込みは下のパターンを全部辿るので、「今ある key の数」ではなく「これまでに使った key の数」に比例する（#389 と同じ仕組み）。`parsePath` の `literalCache`（モジュール全体で 1 つ）も同じく増え続ける。
- **修正**（`src/engine.ts`・`src/pattern.ts`）:
  - **pin**: `Engine.pattern(path)` は既定でパターンを pin する（バインディング・一覧・add-on が持つもの）。`childList` も一覧のパターンを pin する。パスの読み書き（プロキシの get / set、`resolve`、`$resolve`・`$getAll`・`$setAll`、`mirror`）は pin しない。
  - **prune**: root の getter（深さ 0）は、評価が投げずに終わったら、今回読まなかった source との辺を外す（`Engine.prune`）。root の getter の出現は 1 つなので、最後に読んだものがそのまま依存になる（signals と同じ動的な依存）。行の getter は行ごとに読むものが違うので、和集合のまま。
  - **配列を持つ source は残す**: 配列の共有オブジェクトへの書き込みを、その配列を読んだことのある getter が返すリストの行にも届ける仕組み（`mirror`、F26・3.x #362）は、和集合の辺に頼っている。そこで、今回読まなかった source でも、配列を持つもの（データの配列、配列を返す getter）は辺を残す。
  - **sweep**: drain の終わりに、作られたパターンと辺を外されたパターンを見て、何も持たないものを表から外す（`Engine.sweep`）。外すのは、pin されておらず、トップレベルでなく、子も依存も `$eq` の購読も無く、アクセサが無い（またはエンジン自身の添字パスのアクセサで、キャッシュの枠を持たない）パターン。子を外した親は次の周でもう一度見るので、何段でも回収される。
  - **`literalCache`**: 4,096 件を超えたら空にする。
- **結果**: P5 は使った id が 10,000 個でもパターン 4 個・getter の source 2 個（今の key と `cur`）。前の key への書き込みは getter を評価し直さない。
- **残る形**（文書に書く制限）:
  - 行の getter（`get "items.*.label"() { return this["items.*.byId." + this.sel] }`）の動的な読み取りは、和集合のまま残る。行の中の添字パスのアクセサは、キャッシュの枠（slot）を持つので回収しない。
  - root の getter が配列を持つ動的なキーを読む形（`this["messagesByRoom." + this.roomId]` が配列）は、F26 のために辺が残る。部屋の数のように有界な key なら問題にならない。
  - `$eq` の source にした動的なパス、mount した部品から書いた動的なパス（scopes がホスト側で pin する）は残る。
- **#389**: 主な形（`$resolve` や root で読んだ動的なキー、`items.*.m.<key>` の下のパターン）は drain の後に回収されるので、要素の書き込みの費用が K に比例しなくなった。行の getter が動的なキーを読む形（#389 の参考 (a)）は残る。
- **テスト**: `__tests__/pattern-sweep.test.ts`（13 件）。回収される形、pin されて残る形、投げた評価、配列の source、getter の下のパス、数値のキー、行の中の添字パス、`$eq`、`literalCache` の上限。

### 3.3 happy-dom で、一覧を空にするのが O(n²) になる

- **見つけ方**: スイートの N2c（全削除）が 600 秒で終わらなかった。切り分けると、500 行で 3.4 s、1,000 行で 15 s、2,000 行で 63 s（行数の 2 乗、MutationObserver の有無に依らない）。全行の置き換え（全部消して全部作る）は 16,000 行でも 1.1 s で、空にするときだけが遅い。
- **原因**: 一覧が空になるとき、`if:` の分岐を替えるとき、複数ノードの行を消すとき、エンジンは `removeContiguous`（`src/dom/view.ts`）で `Range.deleteContents()` を使っていた。happy-dom の実装はこれが 2 乗で、エンジンを通さずに比べても、1,000 ノードで 13.4 s（1 つずつ `remove()` するループは 3 ms）。ブラウザでは起きない。
- **影響**: happy-dom は `@wcstack/testing`（アプリのテスト）と `@wcstack/server`（SSR）の DOM。利用者のテストで、数百行の一覧を空にするだけで数秒〜数十秒かかっていた。
- **修正**: Range をやめた。
  - 一覧が空になるとき、親の子が行とアンカーとテキストだけなら（`<tbody>` や `<ul>` の中が一覧と、その前後の改行・空白だけ）、`parent.replaceChildren(アンカーとテキスト)` の 1 回で空にし、アンカーとテキストを付け直す。テキストノードは状態を持たないので、付け直しても害が無い（同じノードのままなので、mustache のバインディングも切れない）。
  - それ以外（親にほかの要素もある一覧、`if:` の分岐、複数ノードの行）は、ノードを順に `remove()` する。要素を付け直すと、カスタム要素の再接続や iframe の再読み込みが起きるため。
  - 経緯: 1 つずつ消すだけにすると、Chromium で 1 万行の全削除が約 5% 遅くなった（Range 7.5 ms、ループ 7.9 ms、`replaceChildren` 7.4 ms。A/B の clear10k は 1.046 倍）。初めは「行とアンカーだけ」のときに `replaceChildren` を使ったが、整形した HTML ではテンプレートの前後に改行と空白のテキストがあるので、ベンチマークのページでも効かなかった（clear10k 1.046 倍のまま）。テキストを付け直す形にして、clear10k は HEAD（Range）の **0.861 倍**（185.9 → 160.0 ms、CPU 4 倍の減速、各 200 サンプル）になった。
  - `replaceChildren` は happy-dom でもループと同じく線形（16,000 行で 173 ms）。1,000 行を空にするのが 15 s → 5 ms。
- **テスト**: `coverage-engine.test.ts` に、3,000 行の一覧を空にする時間の上限（2 秒、いまは数十 ms）、前後の空白のテキストが同じノードのまま残ること、親にほかの要素もある一覧を空にしてもその要素が残ること。

### 3.4 サイズと性能

- `core.min.js` 19,525 → 19,921B（+396B、上限 20,000B まで 79B）。split の core 23,674 → 24,118B、`index.esm.js` 50,306 → 50,689B、`auto.min.js` 47,329 → 47,744B（どれも基準値 +3% の内）。内訳の大半は sweep と prune、次が全削除の速い形（54B）。
- 全テスト 3,020 件、カバレッジ 99.79 / 99.29 / 100 / 99.95、lint・型検査・カップリングの検査は通る。
- ホットパスへの変更: `track` に root の getter の分岐、`evalGetter` に root の getter の prune、drain の終わりに sweep（候補が無ければ配列の長さを見るだけ）、`reconcile` の中央の区間に 1 周、ノードの削除がループ、一覧の全削除で親の子を 1 周。
- 性能の A/B（`bench/inpage-ab.mjs`、公式のベンチマークのページ、CPU 4 倍の減速、HEAD = rc.5 の dist）:

|---|---|---|---|
| clear10k（1 万行の全削除） | **0.861** | 0.872 | 各 200 |
| update10k（1 万行の 10 行ごとの更新） | 1.016 | 1.033 | 各 160 |
| create1k | 1.013 | 1.000 | 各 160 |

## 4. 検証スイート

### 4.1 置き場所と動かし方

- `packages/state/bench/scale/`。単体テストからは外す（数分かかり、時間は機械に依る）。
  - `npx vitest run --config bench/vitest.scale.config.ts`（happy-dom、src）
  - `node bench/scale/browser.mjs`（Chromium、`dist/index.esm.js`。e2e の Playwright を使う）
  - `node bench/scale/report.mjs <out>`（JSON から表と判定を作る）
- 軸の定義は 1 か所（`bench/scale/probes.mjs`）に置き、happy-dom と Chromium の両方で同じ定義を流す。定義は素の JS（状態・マークアップ・書き込みの関数）で、エンジンの内部に触れない。
- 結果は `docs/research/state-engine/scale/<日付>/` に置く（`happy-dom.json`・`chromium.json` と、`report.mjs` が作る `README.md`）。

### 4.2 計測の方法

- **仕事の回数**（happy-dom のみ）: 計測とは別にもう 1 回書き込み、その間だけエンジンのプロトタイプのメソッドを包んで、呼ばれた回数を数える（包むのはその 1 回だけなので、時間には響かない）。数えるのは次の 7 つ。
  - `enqueue`（キューに入れたバインディング）
  - `applyBinding`（当てたバインディング。行を作るときのバインディングは、行を組み立てながら当てるので、ここには入らない）
  - `evalGetter`（getter の評価）
  - `visitGetter`（変更が届いた getter の出現）
  - `forSubtree`（辿ったパターン）
  - `rowRemoved`（捨てた行）
  - `indexChanged`（位置が変わった行）
- **DOM の変更**: MutationObserver の追加・削除・属性・文字の記録の数。計測した書き込みの間だけ集める（集め続けると、記録が削除したノードを握り続けて、有界性の計測でヒープが周回ごとに増える）。drain の後の配送は、計測が戻る前に起きることがあるので、コールバックで受けた分と `takeRecords()` の分を合わせる。
- 仕事の回数と DOM の変更は決定的なので、判定は等号か「規模の関数」で書く。
- **時間**: 書き込み＋drain（その後の microtask まで）の時間の、中ほど半分の平均（ばらつきに強く、時計の刻みにも引きずられない）。規模を 3 段変え、log-log の最小二乗で k を出す。仕事の回数で判定する軸では、k は警告に留める。
- **時計**: Chromium は分離されていないページの `performance.now()` を 100 µs に丸める。`browser.mjs` はページに COOP / COEP のヘッダを付けて分離し、5 µs で測る。
- **表の大きさ**（happy-dom のみ）: パターンの数、getter の source の数、root のバインディングの数、行の数。
- **ヒープ**: GC を 3 回走らせた後の `heapUsed`（happy-dom、`--expose-gc`）と `performance.memory.usedJSHeapSize`（Chromium、`--js-flags=--expose-gc` と `--enable-precise-memory-info`）。有界性の判定は表の大きさで行い、ヒープは 1 周あたりの増分を記録する。
- 機械とノイズ: 書き込みは 1 点につき 5〜200 回。順番は小さい規模から。2 つのビルドの比較は `bench/inpage-ab.mjs` の ABBA に任せる。

### 4.3 軸

| ID | 性質 | 変えるもの | 操作 | 判定 |
|---|---|---|---|---|
| L1 | 局所性 | root のキーとバインディングの数 N | 1 個への書き込み | 仕事の回数が一定 |
| L2 | 局所性 | root の一覧の数 L | 無関係なスカラーへの書き込み | 同上 |
| L3 | 局所性 | 一覧の行数 N | 無関係な書き込み / 1 行の 1 フィールドへの書き込み | 同上（当てるバインディング 1 個） |
| L4 | 局所性 | 無関係な root の getter の数 G | 1 個の getter が読む値への書き込み | 評価 1 回 |
| L5 | 局所性 | 入れ子の一覧の行の総数 N（外 × 内） | 葉の 1 フィールドへの書き込み | 仕事の回数が一定 |
| L6 | 局所性 | `<wcs-state mount>` のボリュームの数 V | 1 つのボリュームの値への書き込み | 同上 |
| L7 | 局所性 | `bind-component` の部品の数 C | 1 つの部品の値への書き込み | 同上 |
| L8 | 局所性 | 選択の `$eq` を読む行数 N | 選択の書き込み | 評価 2 回（前と今の行） |
| N1 | 線形性 | root のバインディングの数 N | 初回のマウント | k ≤ 1.25 |
| N2a〜g | 線形性 | 一覧の行数 N | 作成・置き換え・全削除・末尾への N/10 行の追加・逆順・2 行の入れ替え・1 行の削除 | DOM の追加と削除の数、捨てた行と位置が変わった行の数が、操作の分だけ（入れ替えと削除は N に依らない）。k ≤ 1.25 |
| N3 | 線形性 | 0/1 の盤面のセル数 N | 2 セルの変更 | 作り直す行 2、DOM の変更が N に依らない |
| N4 | 線形性 | 1 つの値を読む root の getter の数 F | その値への書き込み | 評価 F 回 |
| N5 | 線形性 | getter の連鎖の段数 D | 根元への書き込み | 評価 D 回 |
| N6 | 線形性 | 全行の getter が読む root の値（`$eq` なし）、行数 N | その値への書き込み | 評価 N 回（設計どおりの比較の基準） |
| N8 | 線形性 | `$getAll` で集める行数 N | 集計の getter が読む行への書き込み | k ≤ 1.25 |
| B1 | 有界性 | root の getter が読む動的なキーの数 K | key を替え続ける | パターンの数が一定 |
| B2 | 有界性 | コードから書いた動的なキーの数 K | 書き続ける | 同上 |
| B3 | 有界性 | 一覧の置き換えの回数 K | N 行を K 回置き換える | 行・バインディングの数とヒープが横ばい |
| B4 | 有界性 | `if:` の出し入れの回数 K | バインディングを含む部分木の出し入れ | 同上 |
| B5 | 有界性 | 部品の出し入れの回数 K | `bind-component` の部品を `if:` で出し入れ | 同上 |
| B6 | 有界性 | ページの差し替えの回数 K | `<wcs-state>` ごと DOM を入れ替える | ヒープが横ばい |
| X1 | 限界 | getter の連鎖 127 / 128 段 | 描画 | 127 段は描き、128 段は番号付きのエラー |
| X2 | 限界 | 一覧の入れ子の深さ | 描画と葉への書き込み | 深さに比例、`RangeError` なし |
| X3 | 限界 | 自己再帰の部品（`for: children` の行に `state: .`）の細長い木の深さ 10 / 50 / 150 | 描画と葉への書き込み | 描けて、葉に届く。`RangeError` なし |
| C1a / C1b | 正しさ | 100 行 / 1,000 行の状態（入れ子の一覧、絞り込みの getter、`$eq` の選択、件数の集計） | 種を固定したランダムな操作 2,000 回 / 500 回（書き換え・挿入・削除・移動・逆順・絞り込み・選択・入れ子への追加） | 1〜4 個のまとめ書きごとに、DOM が参照モデルと一致 |

### 4.4 実ブラウザ

- happy-dom の DOM は実ブラウザと費用の形が違う（P8 の DOM 込みの時間は、happy-dom の `insertBefore` の費用を含んでいた）。公開する数値は Chromium で取る。
- `bench/scale/browser.mjs` は `probes.mjs` の定義をページの中で流し、時間とヒープだけを取る（ビルドの内部名は縮められているので、仕事の回数は取らない）。

### スイートの実装と結果（2026-10-07）

- `packages/state/bench/scale/`: `probes.mjs`（33 軸の定義）、`run.mjs`（両方の環境の実行と判定）、`scale.test.ts`（happy-dom）、`browser.mjs`・`env-browser.mjs`・`page.html`（Chromium）、`report.mjs`（表）、`bench/vitest.scale.config.ts`。
- スイートを作る途中で、問題 3（§3.3、happy-dom で一覧を空にするのが 2 乗）を見つけて直した。
- 計測側で直したこと（同じ道具を作る人のために）:
  - MutationObserver の記録を集め続けると、記録が削除したノードを握り続け、有界性の計測でヒープが周回ごとに増えた（B3 で 1 周 20 MB）。計測した書き込みの間だけ集める。
  - drain の後の MutationObserver の配送が、計測が戻る前に起きて、記録が空のコールバックに捨てられていた。コールバックで受けた分も数える。
  - 正しさの検証で、1 回のまとめ書きの操作を、まとめ書きの前のモデルから作っていたため、添字がずれた。操作は 1 つずつ作って、エンジンとモデルに同時に当てる。
  - Chromium は分離されていないページの `performance.now()` を 100 µs に丸めるので、µs の書き込みの k が意味を失った（N5・N8 が見かけの FAIL）。COOP / COEP で分離し、時間は中ほど半分の平均にした。
  - 行を作るときのバインディングは `applyBinding` を通らない。一覧の操作の回数は、DOM の追加と削除、`rowRemoved`・`indexChanged` で判定する。
- 正しさの検証（C1）で、絞り込みの getter が配列しか読まない形（`this.items.filter((t) => t.done)`）は、まだ含まれていない行の `done` の変更で評価し直されず、DOM がモデルと食い違った。これは既知の制限（移行ガイド §3、配列を読んでもオブジェクトは読んでいない）なので、C1 は文書が勧める形（getter の中で `$getAll("items.*.done")` を読む）にした。
- 結果（[docs/research/state-engine/scale/2026-10-07/](../research/state-engine/scale/2026-10-07/README.md)）: **happy-dom 33 / 33、Chromium 33 / 33 が PASS**。
