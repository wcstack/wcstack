## 0. 要約

1. **wc-bindable・command token・event token は事実上のコア。** 37 デモ中 25・17・15 が使い、README は「Web Components 同士の結線」を他との二大差異の一つに挙げる。wc-bindable は双方向入力・スプレッド・行プランのコア経路に入り込んでいる。暫定のコア範囲に入っていないので、昇格を提案する（現行で合計約 3.2KB gzip）。
2. **「mount」は 2 つある。** volume（`<wcs-state mount="p">`）とコンポーネントの mount（`bind-component` の `state: path`）。実装は共有され（`webComponent/mount.ts`）、own-key の優先・`#ro`（B14）はコンポーネント側のコードにしかない。README の第一原則は両方を本質として扱う。**コンポーネントの mount をコアに含めるかを決める必要がある。**
3. **決定済みコアの mount/volume と `$eq` は、使われ方に比べて重い。** 使用デモはそれぞれ 1 件、e2e は `$eq` が 0 件。mount/volume は現行実装で約 7.1KB gzip あり、機能群では最大。20KB 目標の中で成り立たせるには、別の層として積むのではなく、アドレスモデルの「パスの接頭辞の付け替え」として設計する必要がある。
4. **組み込みフィルタ 48 個のうち、動くコードで使われているのは 13 個。** 残り 35 個は README と skill の説明にしか出てこない。文法を変えずに、コアの小集合と `formats` 後付けに分けられる。
5. **比較に使えるテストは少ない。** 新エンジンにそのまま、または薄いアダプタで流せるのは 1,582 件（38%）で、コア機能に限ると約 510 件。残りは内部関数を直接呼ぶ白箱テスト。「常に比較する」には、契約を外から検証するテストへの書き直しが前提になる。
6. **目標値は測り方の定義が要る。** DOM 直接の基準は作り方で 2.2〜6.3ms（1,000 行）とぶれ、1,000 行単独では計時分解能とノイズの範囲に入る。基準の変種と、warm／cold・行数を固定する必要がある。

## 2. 方法と限界

- **軸 1: 機能タグ。** テスト・README の節・デモを、守っている契約の機能で分類した。語彙は [taxonomy.md](../research/state-engine/taxonomy.md)。`C.*` はコア前提、`X.*` は未決、`T.tooling` は実行時でない道具、`I.internal` は現行エンジンの内部機構だけを検証するもの。
- **軸 2: 持ち運び可能性。** BB（DOM と公開 API だけで動かす）、GB（外から動かすが準備や確認に内部モジュールを使う、薄いアダプタで移植可）、WB（内部関数を直接呼んで戻り値や構造を検証する、移植不可）。BB と GB の境界はバッチ間で解釈が揺れた（`bootstrapState` を src から import する場合）ので、本書では **BB+GB を「持ち運び可」として一括で扱う**。
- **データ源。**
  - テスト: vitest の JSON 出力（336 ファイル・4,164 件、全件緑）を 5 並列で分類した。
  - README: README.md と `packages/state/docs/*.md` の 256 節（5,089 行）。
  - 実利用: デモ 37 件、e2e フィクスチャ 38 件、wcstack-skill（コードブロック 72）、`packages/wcstack/README.md`。
  - サイズ: `dist/auto.min.js` のソースマップを使い、ファイル単位で帰属させた。
- **限界。**
  - 分類は AI エージェントの判断で、タグ件数はファイル単位の概算。
  - サイズの gzip 値は minified バイトの比例配分による推定で、足し算は近似にとどまる。
  - 実利用はこのリポジトリ内のデモに限られ、外部利用者のアプリは分からない。
  - 1 台の機械（Intel Core Ultra 9 275HX）での計測。

## 4. 決定ごとの所見

### 4.1 決定 1「新しい文法は取り入れない」

- **パーサは共有できる。** 文法テスト 242 件のうち 214 件はパーサ（`bindTextParser/`・フィルタ引数解析）を直接呼ぶ WB。新パッケージがパーサを共有（またはそのまま移植）すれば、この 214 件がそのまま使える。3.0 の調査では、3 段文法（字句→AST→計画）に作り直してもバイトは減らなかった（[tech survey](../state-next-major-tech-survey.ja.md) §1-2）。書き直す価値があるのはランタイムで、文法ではない。
- **「従来通り」の範囲を固定する必要がある。** 3.x は旧名を互換エイリアスとして残している（`$streams`・`$updatedCallback`・`$trackDependency`/`$untrackDependency`・旧フィルタ名 `inc dec fix uc lc cap pad rep rev null`）。どれも 4.0 で削除予定（B12・D4）。新エンジンは別パッケージなので、4.0 相当の範囲で始めれば**エイリアスを持ち込まずに済む**。互換テストは 24 ファイルに散在する（stream のテスト 9 ファイルは旧名 `$streams` で書かれている）。
- **3.3 で固まった構文判断を引き継ぐ。** 引用符を意識した分割（B1）、不正構文の拒否（B2）、型付きリテラル（B9）など。これらを固定するテスト（`semantics.majorCandidates` など）は契約として引き継ぐ。

**改訂案**: 「3.3 の文法と 3.2 の正式名。パーサは現行を共有する。互換エイリアスと v2 移行用の fail-fast（`name=`・`@`）は持ち込まない」。

### 4.2 決定 2「コアは mount・volume、`$eq`」

**(a) 「mount」の範囲が曖昧。**
- volume（`mount=`）の注入 `state.taxRate: settings.taxRate` は、README 自身が「コンポーネントの部分 mount と同じ形」と書き、実装も同じ機構（`webComponent/mount.ts`）を使う。own-key の優先と `#ro`（B14）はコンポーネント側のコードにしかない。
- README の第一原則はコンポーネントの mount（`state: path`）と volume の両方を本質として扱う。
- 利用は、コンポーネントの mount がデモ 1・e2e 16・skill の SKILL.md（常時読み込まれる早見表）で教示。bind-component を後付けにすると、volume は注入の機構を自前で持つことになる。→ **§6 問 1**。

**(b) 事実上のコアが 3 つ漏れている。**
- **wc-bindable** はデモ 25/37 で使われ、I/O ノードと state をつなぐ本体。コア経路への入り込みも深い。
  - 双方向入力（`twowayHandler` のテスト 52 件中 23 件）
  - スプレッド（`wcBindable` がないと展開できない）
  - 行プランの適格判定
  - `#init=`/`#sync=` の意味
- **command token**（17/37）と **event token**（15/37）も I/O デモの標準の配線。`$command` は proxy の API の一部になっている。
- **binder**（router が後から挿入するノードを state に結線させる）と **transition-runner** の受け口は、どちらも 0.4KB 程度。中身は他パッケージにあり、state に要るのは大域シンボルを引く受け口だけ。
- → **§6 問 2**。

**(c) 決定済みコアの利用実態。**
- mount/volume はデモ 1 件（router-i18n）、`$eq` はデモ 1 件（devtools-playground の `$eqIndex`）で e2e 0 件。どちらも skill は教えており、判断を覆す材料ではない。
- ただし mount/volume は現行実装で約 7.1KB gzip あり、次の 4 ファイルが中心。
  - `mount.ts` 8.3KB（minified、以下同）
  - `volume.ts` 6.3KB
  - `volumeLifecycle.ts` 3.4KB
  - `volumeShared.ts` 2.8KB
- 20KB 目標の 3 分の 1 に当たる。新設計では「volume・mount＝アドレスの接頭辞の付け替え」をアドレスモデルの一部として最初から入れ、別層として積まないことを設計要件にする。
- `$eq` の 41 件は全件が持ち運び可（GB）で、比較の土台として最も整っている。

**(d) フィルタ。**
- 動くコード（デモ・e2e・skill のコード例・ガイドのコード例）で使われているのは 13 個。
  - デモでの使用数: `eq` 15、`not` 13、`locale` 10、`toFixed` 6、`gt` 4、`percent` 4、`lt` 2、`truthy` 2
  - 各 1 件: `ge`・`add`・`slice`・`date`・`number`
- 未使用の 35 個は次のとおり。どれも README と skill の説明・表には登場する。
  - `ne le sub mul div mod abs clamp`
  - `upper lower capitalize trim substr padStart padEnd repeat reverse truncate join`
  - `int float round floor ceil unit time datetime ymd hms`
  - `falsy defaults coalesce boolean string nullIfEmpty`
- 現行の分割エントリでも、コアに残るフィルタは `not` だけで、他はすべて `features/formats` にある。
- **文法を変えずに**、コアは比較・論理・算術の小集合、書式系は後付けにできる。

**(e) 後付けにする場合、コアが用意すべき受け口。** 分類の過程で、後付け機能がコアの契約に食い込んでいる箇所が見えた。新コアはこれらを最初から受け口として持つ必要がある。
- **getter を動かす起点（demand root）。** README は getter が評価される起点を 3 つ挙げ、うち 2 つが `$watch` と `$stream`。コアに「描画なしで購読する」一次機能が要る。
- **volume 相対のパス解決。** volume は `$watch`・`$listKeys`・`$renderedCallback` を自分の mount パス相対で動かす（README の能力表）。後付け機能にスコープ相対の解決を渡す口が要る。
- **更新の束ねへの割り込み。** `$watch`・`$scan`・`$stream`・DevTools は updater の後段にリスナとして入る。束ねの 1 回ごとに通知する順序付きの口が要る。
- **再セット時の後始末順序。** `integration.stateGenerationReset`（43 件）は 8 つの後付け機能にまたがり、失敗する再セットでどの宣言が世代の前後どちらで失敗するかまで固定している。後付け機能のリセット手順を規約にする必要がある。
- **失敗の封じ込め。** 「1 つのバインディングの失敗はそこに閉じる」の記述は `$watch`/`$stream` が走り続けることを前提にしている。

**(f) 廃止候補（新エンジンに持ち込まないもの）。**
- **リスト要素への書き込みの入替同一性**（#4 系、`X.elemwrite`）: 利用 0 件、テスト 35 件の多くが回避策を固定している。新エンジンでは要素書き込みの意味を単純な置換として定義し直す候補。
- **因果伝播コンテキスト**（`enablePropagationContext`、`X.propagation`）: 利用 0 件。双方向のこだま抑止は、新エンジンでは構造で解くべきもの。
- **設定フラグのオフ側の経路**: `sameValueGuard`・`enableDirectionalInitialSync`・`enablePropagationContext` は両経路をテストしている。新エンジンは既定の挙動だけにする。
- **分割エントリ・フックの受け口**（`X.split`）: 現行の配布機構。新パッケージは最初から疎結合に設計する。
- **既知の欠陥を固定したテスト**: `integration.recursionKnownDefects` の `DEFECT:` 約 22 件や、`elementSwapIdentity` の「現状の記録」などは、移植せず正しい期待値に反転させる。
- **重複・空のテスト**: `bindings.replaceToComment` は `replaceToReplaceNode` とバイト単位で同一。`applyChangeToWebComponent` は中身が空の目印関数。`updater.updater.coverage` はカバレッジ埋めだけ。

**改訂案**: 次の 3 群に分けて固定する。
- **コア**: 文法・状態・getter・リスト・条件・DOM 反映・イベント・更新の束ね・初期化・ライフサイクル・フィルタ小集合・volume・`$eq`・wc-bindable・command/event token・binder と transition の受け口
- **後付け**: temporal（`$watch`/`$scan`/`$stream`）・`$recursion`・SSR・DCC・`$listKeys`・formats（ロケール込み）・診断・DevTools
- **要決定**: コンポーネントの mount

### 4.3 決定 3「別パッケージで常に比較」

- **持ち運び可は 1,582 件。コアに限ると約 510 件。**
  - 内訳: `$eq` 41・リスト 93・getter 82・volume 81・状態 72・初期化 36・文法 28・条件 18・ライフサイクル 17・DOM 反映 16・フィルタ 16・イベント 7・更新の束ね 5
  - DOM 反映（105 件中 89 件）、フィルタ（186 件中 170 件）、文法（242 件中 214 件）は大半が WB。
- **比較の土台を 4 層で作ることを提案する。**
  1. **エンジン中立のハーネス。** GB の大半は次の差し替えだけで動く（エージェント 5 体の見立てが一致）。この口を 1 つ定義し、BB/GB を両エンジンに流す。
     - `bootstrapState`
     - `getStateElement`（`querySelector('wcs-state')` で代替可）
     - `createState` / `setInitialState` / `connectedCallbackPromise`
  2. **パーサの共有。** 決定 1 の改訂案どおりパーサを共有すれば、文法の WB 214 件はそのまま効く。
  3. **契約の抽出。** コアの WB テスト（約 890 件）が守っている利用者向けの契約を、外から検証するテストに書き直す。フィルタの WB は関数単体のテストなので、フィルタ実装を共有すれば移植は機械的。
  4. **ページ単位の比較。** 性能は `e2e/bench/jsfb-verify.mjs --bundle` で同じページのままバンドルを差し替える。`e2e/tests` は 9 つのデモを直接動かすので、同じくバンドル差し替えで両エンジンに流せる。
- **持ち込まないもの**: `I.internal` 685 件と `X.split` 53 件。性能の主張（perf シグナルのあるファイルの 484 件）は、新エンジンでは別の形の計測に置き換える。

### 4.4 決定 4「core 20KB 以下、1,000 行作成を DOM 直接の 2 倍以内」

**サイズ。**
- §4.2 の改訂案のコア範囲を現行実装で合算すると、gzip 約 53KB（比例配分の推定。コンポーネントの mount を入れると約 57KB）。3.0 で実測した分割 core（volume と DCC を除く）は 43.2KB。
- **20KB は同じ範囲で現行の 4 割以下**。参考として `@wcstack/signals` の core+dom は約 7KB（機能範囲は別物）。
- 測り方を固定する必要がある。提案は「コア範囲だけを含む単一ファイル、minify、gzip -9」で、現行の `check-state-size.mjs` と同じ方式で CI に載せること。
- 予算配分の目安（未検証の仮置き）は次のとおり。どこかが溢れたときに、どこを削るかを早く議論するための叩き台。

| 部分 | 目安 |
|---|---:|
| 反応核とアドレス | 5KB |
| リスト・条件の描画 | 4KB |
| DOM 反映（双方向・radio・checkbox 込み） | 3KB |
| 文法とフィルタ小集合 | 2.5KB |
| 初期化・要素・読み込み | 2KB |
| volume／mount | 1.5KB |
| wc-bindable・token・受け口 | 1.5KB |
| `$eq` | 0.5KB |

**性能。**
- **「DOM 直接」の基準の変種を固定する必要がある。**
  - 2026-09-20 の実測（Chromium 149・無スロットル、[dom-floor.json](../research/state-next/dom-floor.json)）では、1,000 行作成の中央値が変種によって 2.2〜6.3ms にばらつく。
  - テンプレート複製＋ノード位置解決の `clone-path` と、複製＋行記録の `clone-records` はどちらも 3.9ms。
  - 10,000 行では `clone-path` 37.0ms、`clone-records` 23.5ms。
- **1,000 行単独で比を主張しない。**
  - 計時分解能と GC のノイズの範囲に入る（3.0 の受け入れ基準 A4 と同じ規律）。
  - 現行の計測ページはサンプルごとに再読込する cold 計測で、エンジンのコンパイルと暖機が入る。DOM 直接の計測スクリプトは極小なので、cold と warm の差がほぼない。
- **提案**: 基準は `clone-path`（テンプレートエンジンが最低限やる仕事と同じ）。判定は下表の 2 指標で、cold 1,000 行は回帰確認に使う。4× スロットルも併記する。

| 指標 | 現行（3.0 実測） | DOM 直接 | 現在の比 | 2 倍以内の目標 |
|---|---:|---:|---:|---:|
| warm 1,000 行作成 | 15.7ms | 3.9ms | 4.0× | ≤ 7.8ms |
| cold 10,000 行作成 | 302.3ms | 37.0ms | 8.2× | ≤ 74ms |

- **作成以外の操作にも下限を付ける。** 更新・追加・削除・選択・入替・全消去が「現行より悪化しない」を最低条件にする。現行でも DOM 直接との差は大きい。
  - 1,000 行の追加: 40.6ms 対 2.4ms
  - 10,000 行中 1,000 行の更新: 13.1ms 対 1.9ms
- **計測ページの修正。** 現行の計測ページは選択を `$untrackDependency` と手動通知で最適化している。新エンジンの比較では `$eq` に置き換える。

## 8. フィルタの分け方（第 2 回）

**前提となる事実。**

- **サイズの効果は小さい。** 組み込みフィルタは 48 個で合計約 4.9KB（minified。gzip 推定で約 1.5KB）。どう分けても、コアから削れるのは gzip で最大約 1KB。したがって分け方は、バイト数より「コアに常にある名前の集合として意味が通るか」で選ぶ。
  - フィルタごとの内訳はソースマップから算出した（引数検証の共通関数と名前表 915B は按分外）。
- **全部入りの `auto` ではすべて使える。** 分け方が効くのは、コアだけを読み込む構成の利用者に限られる。コアにないフィルタを使えば、バインディング計画の時点で「formats を入れてください」と名前付きで失敗させる（3.0 の D16 と同じ方式）。
- **`not` は必ずコア。** エンジンは `else:` の実装に `not` を差し込む。
- **ロケールに依存するのは 4 つ**（`locale`・`date`・`time`・`datetime`）。`config.locale` と `<html lang>` の扱いも、これらと一緒に移る。

**案の比較。**

| 案 | コア | 後付け（formats） | 実使用 13 個のうちコアに入る数 | コアのフィルタ（gzip 推定） | 評価 |
|---|---|---|---:|---:|---|
| **A 意味で分ける（推奨）** | 条件・算術・型変換・欠損値の 24 個 | 数値の表示・文字列の加工・日時の 24 個 | 8 | 約 0.55KB | 「バインディングの論理に要るもの」と「表示の整形」で線が引ける |
| B ロケール依存だけ外す | 44 個 | 4 個 | 11 | 約 1.4KB | 移行は楽だが、コアに未使用の 30 個以上が残る |
| C 実使用の 13 個だけ | 13 個 | 35 個 | 13 | 約 0.35KB | `gt` はあるのに `le` がない、など線に意味がない |
| D 現行の分割エントリと同じ | `not` のみ | 47 個 | 1 | ≈0 | 15 デモが使う `eq` すら後付けになり、コア単体では実用にならない |

**案 A の内訳。**

| 区分 | コア（24） | formats（24） |
|---|---|---|
| 条件 | `eq ne not lt le gt ge truthy falsy boolean` | |
| 算術 | `add sub mul div mod abs clamp` | |
| 型変換 | `number string int float` | |
| 欠損値 | `defaults coalesce nullIfEmpty` | |
| 数値の表示 | | `toFixed round floor ceil percent unit locale` |
| 文字列の加工 | | `upper lower capitalize trim slice substr padStart padEnd repeat reverse truncate join` |
| 日時 | | `date time datetime ymd hms` |

- 実使用 13 個のうち、コアに入るのは `eq not gt lt ge truthy add number`、後付けになるのは `locale toFixed percent slice date`。
- 後付け側を使うデモは 8 件（`C.filter-format`）。どれも `auto` で読み込んでいるので影響はない。
- 判断が分かれうる境目は 2 つ。
  - `round`/`floor`/`ceil`: 桁数引数を取る表示用途として formats に置いた。
  - `abs`/`clamp`: 算術としてコアに置いた。

## 9. 廃止の可否（第 2 回）

判定の基準は著者の方針「廃止しても機能上の問題がないなら廃止も検討する」。候補ごとに、廃止すると何が起きるか、何で代替できるかを調べた。

- 因果伝播とリスト要素書き込みは、コピーしたソースを変異させて全テストを流す実験で確かめた（リポジトリは無変更）。
- 機能の重複は、コード・README・実利用から判定した。

### 9.2 因果伝播を外したときに要る最低保証

変異実験の結果は次のとおり。
- 既定をオフにし、結合テストもオフで強制しても、全スイートで追加の失敗は 0 件だった。
- 利用者向けの約束（エコー・正規化・増殖する正規化の結合テスト 4 件）は、既存の同値ガードと要素側の比較 `current !== newValue` で守られていた。

機構がオフのときだけ差が出たのは、次の 3 事例。

1. setter が同じオブジェクトを同期的にエコーすると、書き込みが 1 回余計に起き、`$watch` が 2 回発火する。
2. getter が毎回新しいオブジェクトを返す要素では、無限ループになる。
3. 正規化が衝突する 2 要素（小文字化と大文字化）を同じパスに束ねると、無限に往復する。

新エンジンはこの 3 つを次の小さな仕組みで止める。
- **同期の受領抑止**: state→要素の書き込み中に、同じ（ノード・メンバー）から `Object.is` で同値の通知が来たら無視する。
- **更新連鎖の上限**: `$watch` の 32 段上限と同じ形で上限を設け、超えたら `console.error` で止める。
- **例外**: `semantics: "event"` の通知は重複除去しない。

### 9.3 リスト要素書き込みを位置モデルに変える影響

**現行の約束**
- README に規範として書かれている。
  - 「要素の書き込みで入れ替えると、描画された行が値と一緒に動く」（README の `$resolve` 節、1281 行）
  - 「リストになかった値を書けば、その行をその場で置き換え、入力中のフォーカスを保つ」
- 同一性モデルを採ったために副作用が生じ、それを塞ぐ補修が積み重なっている。例: 打鍵ごとのフォーカス喪失、`$watch` の prev 消失（コミット `1476a9dc`）。

**位置モデルに変えたときの実験結果**
- 変わる挙動: 次の 7 件のテストが、モデルが変わる以上当然に落ちた。
  - 行ブロックが値と一緒に動く（6 件）
  - バインドしていない状態が値に付いていく（1 件）
- 保たれる挙動（テストが通った）:
  - フォーカスの維持
  - 入れ子の for/if を持つ行の置き換え
  - `$watch` の prev
- 本物の欠陥 4 件: バインドしていない行 getter と再帰集計が古い値のまま残る。
  - 「行の配下の派生値をすべて無効化する」処理を足すと 4 件とも解消した。
  - 新エンジンでは、キャッシュが親の解決チェーンに依存する設計にすれば自然に満たせる。
- 現行が「現状の記録」として固定していた既知の穴（入れ替えた行の入れ子リストに `$watch` が発火しない）は、位置モデルでは閉じる。

**新エンジンの約束（案）**
- 要素の書き込みは「その位置の値の置き換え」とする。
- 行の配下の派生値はすべて無効化する。
- 同一性を保った並べ替えは配列代入で行う。

これは README の約束の変更にあたる。決定 3（別パッケージ）なので新パッケージ側の README に書けば足りるが、**著者の判断が要る**。

### 9.4 著者に決めてほしいこと（第 2 回）

1. §8 のフィルタの分け方は案 A（意味で分ける）でよいか。
2. §9.1 の「廃止可」「最低保証つきで廃止可」を採るか。特に次の 2 つ。
   - #6: 要素書き込みの約束を位置モデルに変える
   - #7: `$scan` を廃止する（4.6KB・1 デモ・skill は 3 か所で教示）
3. `bind-component` の扱い。後付けの mount の器に限定し、単体の機能としては持たない、でよいか。
