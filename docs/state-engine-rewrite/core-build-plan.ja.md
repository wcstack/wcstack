# state エンジン再設計 — コア構築の計画（第 2 段階）

作成 2026-09-24。前提は次の 3 つ。

## 1. 進め方

試作 `packages/state-next` を土台に、コアの機能を段ごとに足す。各段の終わりに、次の 3 つを必ず回す。

| 検査 | 内容 | 合否 |
|---|---|---|
| 単体・契約テスト | 足した機能の約束（README の記述）をテストに書く | 全件緑 |
| 現行との突き合わせ（ゴールデン） | 同じシナリオ（HTML・状態・操作）を現行 3.3.0 で流して DOM を記録し、新エンジンの DOM と比べる | 差分ゼロ。意図した差（廃止・位置モデルなど）は、シナリオ側に理由付きで明記する |
| 性能とサイズ | 現行×2（A/A）・新エンジン・DOM 直接（コールド／ウォーム）を同じセッションで交互に計測する | 下記のとおり |

性能とサイズの合否は次のとおり。
- ウォーム 1,000 行作成とコールド 10,000 行作成が、同条件の DOM 直接の 2 倍以内。
- 他の操作は現行より悪化しない（A/A の揺れを超えて遅くならない）。
- `auto` の gzip サイズを記録し、core ≤ 20KB を見張る。

**結果**

### 段 6（2026-09-25・性能の余裕づくり）

段 3〜5 の後、コールド 10,000 行が 2 倍の境界上だった。後付け機能を足す前に余裕を作った。

**決めたこと**
- イベントの委譲を既定にした（著者承認）。バブリングするイベントの `on*:` ハンドラでは、`event.currentTarget` がルート（`document` または shadow root）になる。`config.delegateEvents` は廃止。
- version 方式（試作の比較対象）のコードを消した。dirty 方式だけを残す。

**部品ごとの費用を測った（`stage-6/ablation/`）**
計測用ビルドで機能を 1 つずつ外し、コールド 10,000 行を比べた（2 周・各 12 サンプル）。

| 外したもの | コールド 10,000 行 | 差 |
|---|---:|---:|
| なし | 86.8ms | — |
| 行の中のイベント | 83.4ms | −3.4 |
| getter の評価（`class.danger` の `.selected`） | 81.8ms | −5.0 |
| class バインディングごと | 78.8ms | −8.0 |
| イベントと class（テキストだけ） | 74.3ms | −12.5 |
| テキストも Binding を作らず直接書く | 70.7ms | −16.1 |

- 最小構成でも 70.7ms（DOM 直接は 44ms）。残りは行ごとの骨組みと、最適化前の実行（JIT）の分。
- 同じページで 10,000 行作成を繰り返すと、1〜2 回目は 60〜80ms、4〜6 回目は 26〜36ms まで下がる。DOM 直接のウォーム（28〜35ms）と同程度。つまり十分に最適化された後の行ごとの費用は DOM 直接に近く、コールドとの差は、最適化される前に走る分と割り当て・回収で生じている。
- 実ブラウザで V8 の最適化の取り消し（deopt）を記録した。立ち上がり時の型の一般化とループ出口の 1 回だけで、性能に効くものはなかった。
- 計測の非対称: 状態のメソッドは `buildData(10000)` をクリック処理の中で呼ぶので、新エンジンの計測に含まれる。DOM 直接の床はタイマーの外で呼んでいた。コールドの `buildData(10000)` は約 6.2ms（`bench` 外のプローブで実測）。→ 著者承認（2026-09-25）で条件をそろえた（段 7 の「計測」）。この段の表は従来の床での比。

**入れた変更**
1. **行のスロット**（`RowView.slots`）: 行と同じ位置を読む単純なバインディング（text・class・attr・style・html と、双方向でない素のプロパティ）は、行の作成時に Binding を作らず登録もしない。ノードと最後の値だけを行の描画に持たせ、変更が初めて届いたときに Binding にする。変更は行の描画（`row.view` と、同じリストの 2 つ目以降の for の表）からたどる。コールド 10,000 行 78.8 → 71.7ms（`stage-6/slots-vs-base/`）。
2. **イベントの委譲を計画に持たせた**: ブロックの先頭要素にブロックへの参照を 1 つ置き、イベントが通ったら計画からハンドラの要素を割り出す（`Block.dispatch`）。行の作成時は、イベント専用の要素を探さず、要素にプロパティも書かない。73.7 → 70.1ms（`stage-6/events-vs-slots/`）。
3. プロキシの読み取りで、既知のトップレベルのキーはパスの解析を省く。
4. **内部のプロパティ名を短くした**（`mangle.mjs`、esbuild の `mangleProps`）: core −0.76KB gzip。外部（DOM・プロトコル・wc-bindable の宣言・設定・公開メソッド・DevTools）と接する名前は対象外。`__tests__/bundle.test.ts` が、同じ設定で作ったバンドルに全シナリオを流す（わざと `name` を混ぜると wc-bindable 系の 8 シナリオが落ちることを確認済み）。別バンドルの後付け機能は、公開の受け口を通すか、同じ短縮表で作る必要がある。

**直した不具合（新エンジン）**
- 同じリストを 2 つの `for:` で描くと、後から作った方しか更新されなかった（リストが描画を 1 つしか持てなかった）。2 つ目以降は自分の表で行の描画を持つ。
- 行の中の wc-bindable 出力専用メンバーが、状態からの更新を受け取っていた（行の登録一覧と描画の Binding 一覧を共有していたため、登録しないはずの Binding が登録扱いになった）。Binding の後始末用の一覧と、変更を探すための登録を分けた。
- 行の作成中に、要素の初期同期（wc-bindable）が状態へ書くと、まだノードを受け取っていないスロットが Binding になっていた。スロットのノードと初期値を先に埋める。

**ゴールデンで見つかった現行 3.3.0 の不具合（2 件・Chromium でも再現）**
- **出力専用メンバーを持つ要素を `for:` の行に置くと、一覧ごと描画に失敗する**（`No state tree found on this root for initial binding sync.`）。行を文書に入れる前の断片の上で初期同期を行い、状態の木を見つけられない。クラスが定義済みの I/O ノード（出力専用のプロパティを持つもの）を行に置く書き方で起きる。
- 同じリストを別の `for:` も描いているとき、`if` で消して戻した `for:` は、消えている間に増えた行を描かず、その後の並べ替えにも追従しない（`for:` が 1 つなら起きない）。
- どちらもシナリオで意図した差分として宣言した。

**ゴールデンの強化**
- 直列化に、wc-bindable 要素の宣言済みメンバーの値（`:status` など）を加えた。状態が要素へ書いたか（書かなかったか）が見える。
- シナリオを 4 つ足した（同じリストを 2 つの for で・行の中の双方向メンバー・行の中の出力専用メンバー・イベントの入れ子と `#stop` と行の中の if と先頭要素が複数の行）。イベントのシナリオは現行と完全一致。

**結果**
- テスト 532 件（うちゴールデン 45 シナリオを、ソースと縮めたバンドルの両方で）がすべて通過。
- サイズ（gzip）: コアだけ 18.7KB（短縮前 19.5KB）。formats 込みの `auto` は 19.5KB。
- 性能（`stage-6/targets-2/`、同じセッションの DOM 直接と比較、各 18 サンプル、DOM 直接は前後 2 回）:

| 指標 | 新エンジン | DOM 直接（同条件） | 比 | 段 6 の前 |
|---|---:|---:|---:|---:|
| ウォーム 1,000 行作成 | 6.25ms | 3.65ms | **1.71 倍** | 1.77 倍 |
| コールド 10,000 行作成 | 74.55ms | 44.7ms | **1.67 倍** | 1.99 倍 |

- 全操作の計測（`stage-6/full/`、2 周、現行×2 と交互）でも 1.49 倍／1.76 倍。現行との比較は全操作で速い: 作成 −69〜−86%、置き換え −68%、追加 −81〜−85%、更新 −51%、選択（tracked／`$eqIndex`）−83%／−75%、削除 −73〜−85%、入れ替え −62%、全消去 −8〜−17%。
- スロット方式は Binding を作る費用を初回の更新へ回すが、選択・更新・削除も現行より速いまま。

**残り（コア）**
- binder の受け口（ルーターが後から入れたノードを束ねる）と transition-runner の受け口（描画の変更を遷移の調停役に渡す）。
- 初期化済みの要素への `setInitialState`（状態の丸ごと置き換え）。

### 段 7（2026-09-25・コアの残り）

著者の承認（段 6 のコミット、現行の不具合の Issue 化、計測条件の統一、内部名の短縮の続行）を受けて、コアの残り 3 つを足した。これでコアの範囲（scope-classification の決定表）はすべて実装済み。

**計測条件をそろえた**
- DOM 直接の床に「データ生成をタイマーの中で行う」版を足した（`bench/dom-floor-cold.mjs` の `withData`）。新エンジン側は状態のメソッドがクリック処理の中でデータを作るので、これが同条件になる。目標の比はこの床で出し、従来の床での比（`ratioExcl`）も並べる（`targets.sh`・`summarize.mjs`）。
- 同じセッションの床: コールド 10,000 行 50.0〜50.3ms（従来 44.6〜45.0ms）。ウォーム 1,000 行はデータ生成がほぼ 0 なので同じ（4.0〜4.15ms）。

**足したもの**
1. **transition-runner の受け口**: drain の各回で、DOM の変更（リストの更新とバインディングの反映）を `runTransition("state", …)` に渡す。
   - 反映するものが無い回（バインドの無いパスへの書き込みだけ）は渡さない。空の遷移で本物の遷移を止めないため（現行と同じ）。
   - 反映を後回しにされた場合、その間の書き込みは待っている反映に合流する（最新の値で 1 回だけ入る）。反映の失敗はその後で報告する。
   - 初回の描画は渡さない。
   - `naming="auto"` のとき、行と `if` の中身の先頭要素に `view-transition-name`（`wcs-row-N`／`wcs-branch-N`）と `view-transition-class` を振る。上限と一度だけの警告、文書ごとの台帳（`Symbol.for("wcstack.state.view-transition-naming")`）は現行と共有する。
2. **binder の受け口**: `bootstrapState`（`define`）で `Symbol.for("wcstack.binder")` に載せる。渡されたサブツリーを、その根のエンジンで同期に結線する。
   - 冪等: ルート直下の結線済み要素は記録して飛ばす。行とブロックは、計画の断片から `data-wcs` 属性を外してあるので、描画済みの一覧を渡されても結線するものが無い。
   - 起動時: エンジンの初期構築の前に渡されたもの（binder へ直接・プロトコルの保留キュー）は、構築の直後に結線する。
   - プロトコル定義は `scripts/sync-protocol-types.mjs` の配布先に `state-next` を足して、生成されたコピーを使う。
3. **初期化済みの要素への `setInitialState`（再セット）**: 状態を丸ごと差し替え、戻る前にすべてのバインディングを新しい状態で反映し直す。
   - 書き込みではないので `$renderedCallback` を呼ばない。
   - 古い状態から学んだもの（アクセサ、依存関係、キャッシュ、`$eq` のキー）は捨てる。リストの行は、配列が同じインスタンスなら保たれる。
   - command token は、同じ名前なら同じトークンのまま（要素の購読が切れない）。event token と `$on` は新しい状態から作り直す。
   - 初期化に失敗した要素では throw する。
   - 現行との差（意図した差分として宣言）: 新しい状態に無いパスは undefined として読み、空値の約束（B8）で空にする。現行は失敗（`wcs/binding-path-missing`）として報告し、古い値を表示に残す。パスの欠落の診断は後付けの「診断」に入る。
   - 未対応（現行との差）: 切り離し中の要素への再セットも、その場で反映する（現行は再接続まで待つ）。state-next のバインディングは `<wcs-state>` の接続と独立しているため。

**確かめたこと**
- 単体テスト（`__tests__/protocols.test.ts`、14 件）: 偽のアービターで run の回数・後回し・命名・上限、binder の同期結線・冪等（描画済みの一覧を含む）・起動前の保留、再セットの同期反映・`$renderedCallback` なし・トークンの同一性・失敗した要素。
- ゴールデン: 再セットのシナリオを 4 つ足した（丸ごと差し替え・同じ配列のまま・トークンと `$on`・無いパス）。無いパスの 1 件以外は現行と完全一致。
- **実ブラウザでの結合**（`bench/protocols-browser.mjs`）: 公開済みの `@wcstack/router` と `<wcs-view-transition naming="auto">` を同じページに載せ、現行 state と新エンジンで同じ操作をした。結果は完全に一致した。
  - 後から入るルート内容と `<wcs-head>` の `title` が結線される。
  - ルートを出て戻っても二重に結線しない。
  - 行に名前が付き、行の追加が `startViewTransition` を通る（呼ばれた回数も同じ）。

**内部名の短縮を広げた**
