# 長い一覧

**English**: [long-lists.md](./long-lists.md)

一覧が数千行になるときにページがすること: 1 ページずつ読み込む、行 1 つの費用、画面の近くの行だけを描くのはいつか、一覧の元の場所へ戻る方法。継ぎ目アプリ `town-archive`（12,000 件の写真アーカイブの無限スクロールと、同じ 12,000 件をメモリに持つ職員の表）から書いた（[seam-apps.ja.md](./seam-apps.ja.md)）。数字は Chromium・Firefox・WebKit で測った。4.24 と書いたものは、4.23.0 の次のリリースに入る。

## 1. 長い一覧の費用

`@wcstack/state` は一覧が長くなっても遅くならない。3,000 行のうち 1 行を書く（`$update("photos.*.fav", [i], …)`）のはスクリプトで約 1 ミリ秒、60 枚のカードのページを足すスクリプトの部分は 5〜10 ms のまま、`this.photos` 越しに 12,000 行を回す getter は 0.1 ms 未満 —— getter が読む配列は、配列そのものである。

増えるのは、ブラウザが文書に対してする仕事。要素が 10 個ほどのカードで、60 枚のページが出るまで（書き込みから次のフレームまで）にかかる時間:

| | カード 120 枚 | 3,000 枚 | 3,000 枚で、各カードを `<wcs-intersect>` 2 つで包む |
|---|---|---|---|
| Chromium | 21 ms | 30〜34 ms | 40〜48 ms |
| Chromium（CPU を 4 倍遅く） | 37 ms | 113 ms | 183 ms |
| Firefox | 9〜12 ms | 18〜19 ms | 32〜52 ms |
| WebKit | 19〜31 ms | 49〜95 ms | 105〜145 ms |

すべての行を文書に置く一覧は、数百行なら問題なく、数千行で目に見えてくる。行ごとに包む要素も効く。一覧の `<wcs-intersect>` で `IntersectionObserver` を 1 つ共有する形も測ったが、効かなかった（Chromium で 40 → 36 ms、WebKit では遅くなった）: 費用は要素とレイアウトで、observer ではない。

## 2. 1 ページずつ読み込む

**`<wcs-infinite-scroll>` を使う**（`manual` の `<wcs-fetch>` と一緒に）。例の全体は [fetch の README §5](../packages/fetch/README.ja.md#5-wcs-infinite-scroll-による無限スクロール) にある。4.24 から、state が url を書いたときに最初のページを読み込み、ページが番兵を画面に残す間（背の高いウィンドウ、縮小表示）は続け、失敗した要求は繰り返さず、何も足さなかった応答で止まる。ページの仕事として残るもの:

- **url は state から書く**（`url: nextUrl`）。1 ページ目の URL を静的な属性で書かない。
- **進めるのは応答の後、成功したときだけ。** 失敗ではページ番号をそのままにする。番兵がもう一度画面に入るか、`trigger` を書く再試行ボタンで、同じページを取りに行く。
- **終わりを判定し**（短いページ、またはサーバーの返す総数）、`disabled` に束ねる。
- **番兵はリストの直後、スピナーやメッセージより上に置く。** 番兵を動かすのは行だけにする: 要求の開始とともに番兵の上に差し込まれるスピナーは番兵をマージンの外へ押し出し、続いているスクロールが戻す。これは番兵がもう一度画面に入ったことになり、その間に失敗した要求をもう一度取りに行く。
- **絞り込みは一覧を最初から始め、取りに行っているページを中断する。** `manual` の `<wcs-fetch>` は `url` が変わっても中断しないので、前の絞り込みで頼んだページは届き、その行が新しい一覧に入る。`<wcs-fetch>` に `command.abort: $command.cancelPage` を束ね、最初に emit してから一覧を空にする:

```js
setFilter(event) {
  this.$command.cancelPage.emit(); // 取りに行っているページは、前の一覧のもの
  this.filter = event.target.value;
  this.items = [];
  this.page = 1;
  this.noMore = false;
},
```

新しい一覧の最初のページは、番兵が自分で取りに行く。利用者がずっと下にいたなら、先頭へのスクロールもする。

**`<wcs-intersect target="self">` を使う**のは、端がほかのことを意味するときや、端の意味をページが決めるとき —— 両端に伸びる一覧は、それぞれの端に番兵を持つ。そのときは `<wcs-infinite-scroll>` がすることをページがする（[intersection の README](../packages/intersection/README.ja.md#2-無限スクロールセンチネル)、[`examples/state-intersect-fetch`](../examples/state-intersect-fetch)）:

- 報告（`eventToken.intersecting:`）で動く。取っておいたフラグでは動かない: フラグは、ページが番兵を動かした時点で古い。
- ページが届くたびに `reobserve()` する —— observer が報告するのは可視性の変化だけ。失敗の後にはしない。
- 取りに行くページは一覧の長さから決める。報告のたびに `page++` しない: 報告は入るときにも出るときにも来る。
- 何も指していない `root` は viewport になり、スクロールしない root（`root="main"`）は中にあるものをすべて画面内として数える。4.24 から、前者は知らせる（`[wcs/intersect-root]`）。

## 3. 行

- **行のオブジェクトを保つ。** 行はそのオブジェクトである: `items.concat(page)` は描かれた行を保ち、写しとして作り直した一覧（`map((p) => ({ ...p }))`、JSON の往復）は文書の行をすべて作り直す —— フォーカスは `<body>` に落ち、画像はもう一度デコードされ、どの `<wcs-intersect>` も最初からになる。行を置き換えるしかないなら、一覧にキーを付ける（[state の README](../packages/state/README.ja.md)）。
- **1 行だけ書く。** `this.$update("photos.*.fav", [index], (v) => !v)` は 1 行に触る。新しい配列を代入すると、state は全部を比べる。
- **行ごとに探さず、行ごとにフラグを持つ。** 「この行の id はお気に入りにあるか」を行の getter（`this.favorites.some(…)`）で書くと、お気に入りが変わるたびに全行で走る。行に `fav` を持たせ、ページが届いたときに立て（行ごとに `Set` の検索 1 回）、お気に入りが変わったら id の変わった行だけ書く。`$eq` は「この行は選ばれた 1 つか」に答えるもので、集合の形は無い。
- **画像**: 遅延読み込みだけなら、ネイティブの `loading="lazy"` で足りる。カードには写真の形（`aspect-ratio`）と色を与え、画像が届いても何も動かないようにする。
- **行ごとの observer**（各カードを包む `<wcs-intersect>` —— 「見た」の記録や、`loading="lazy"` にできないこと）の費用は §1 のとおり。`threshold="1"` は、root より背の高いカードを決して報告しない —— 横向きに持った電話では、ほとんどのカードがそうなる。`0.5` か、複数のしきい値と ratio を使う。
- **イベント**は委譲されるので、ハンドラ 2 つずつの 3,000 行でもリスナーは増えない。ハンドラは、イベントの後に行の添字を受け取る（`star(event, index)`）。`event.currentTarget` はルートで、行ではない。リンクであるカードの ★ は、ボタンをリンクの中でなく隣に置く: `<a>` の中のボタンのクリックはリンクをたどり、`stopPropagation()` が止めるのはハンドラで、リンクではない。4.24 から、行の中で `<wcs-link>` の後ろにあるボタンは自分のハンドラが動く（それまでは動かないか、隣のものが動いた）。`<wcs-link>` そのものに書いたハンドラは決して動かない —— lint が知らせる。

## 4. 画面の近くの行だけを描く

画面の一覧が数千行に届きうるとき —— 全件の表、誰も離れないフィード —— は、その窓だけを描く。継ぎ目アプリの公開側の一覧は、3,000 件を読み込んだ状態で文書にカード 60 枚を持ち、ページは 5〜14 ms で出る。職員の表（`@wcstack/signals`）は 12,000 行のうち約 45 行を持ち、CPU を 4 倍遅くしても、絞り込みの 1 打鍵に約 50 ms、並べ替えに約 100 ms で応える。

- **行の高さが、文書なしで分かること**: 固定（表: 32 px）か、データから計算できる（カード: 文字の部分＋その列の幅での写真の形）。
- **一覧は、切り出す getter**: `for: shown` の下の `get shown() { return this.items.slice(this.first, this.end); }` を、一覧全体の高さを持つ箱の中に置き、窓の始まる位置へ動かす。
- **スクロール位置は要素ではない。** wcstack にそれを報告する要素は無い。`$connectedCallback` で passive な `scroll` リスナーを 1 つ足し、1 フレームに 1 回読んで state に書く。`first` と `end` はその上の getter。
- **入れ物の大きさは要素**: `<wcs-resize target="self" round data-wcs="width: gridWidth">`。隠れた入れ物は `0` を報告する: 無視する（setter が最後の本当の幅を保つアクセサの組）。そうしないと、一覧が隠れている間に列が潰れる。4.24 から、その幅の上の getter の `$watch` は最初の幅でも発火する。それまでは Chromium と Firefox で発火しなかった。
- **スクロールの錨を誰が持つか決める。** 継ぎ目アプリの窓だけ描く一覧は、`overflow-anchor: none` を付け（Chromium では `html` と `body`、Firefox ではすべての要素）、上に行が届いたときの位置を自分で置くまで、下に張り付いたままページを次々に読み込んだ。すべての行を文書に置く一覧には要らない。
- **`@wcstack/signals` では**: `key` 付きの `For`、変わるものは `current()` で読む、今の行は `selector()`、表を作る前に `delegateEvents()`、イベントの連発は 1 フレームに 1 回の更新へ畳む。

費用: ページ内検索は文書にある行しか見ない。フォーカスのある行が窓の外へスクロールすると、フォーカスを失う。コードはページのものになる。画面に数百行までなら、割に合わない。

## 5. 戻る

- **「戻る」**はスクロール位置を復元する: 一覧がルートの中身なら、行・位置・番兵は元のまま（Chromium・Firefox・WebKit）。一覧が行を持ち続けていること —— state に置く。
- **ルートの外に置いた一覧**（[router の README](../packages/router/README.ja.md) の例外）: 「戻る」はこれも復元する。自分のリンクで戻るのは push のナビゲーションで、終わったときに先頭へスクロールする —— `$watch` の後で。代わりに行へ遷移する: `navigateUrl = "/#photo-" + id`。ブラウザはその id の要素へスクロールし、フォーカスも移る。
- **再読み込み**はページの仕事: 場所を決めるもの（絞り込み、画面の最初の行）を `<wcs-storage type="session">` で持ち、そこから読み込み、行が描かれたらスクロールする。

## 6. wcstack に無いもの

設計の問いとして記録した（予定は無い）: スクロール位置を報告する要素、`$eq` の集合の形（「この行のキーはこの集合にあるか」）、端末のピクセル比の要素（今は `<wcs-media-query>` の `resolution` のしきい値で書く）。
