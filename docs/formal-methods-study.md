# Extracting the specification from the code and refuting it — a study

- **Status**: study, 2026-11-03. The author took the recommended decisions the same day (§6); the work they call for is planned in §7.
- **Source**: mizchi, [実装コードから仕様を吸い出して Z3 / TLA+ でバグを払い出す — 実践プレイブック](https://gist.github.com/mizchi/db7817e6fc077d567c41cd9d41bb1c53) (Japanese), called *the playbook* below.
- **日本語版**: [formal-methods-study.ja.md](./formal-methods-study.ja.md)

The playbook treats the implementation as the de-facto specification: extract what the code claims and what it decides without saying so, let a machine attack each claim over every input or every ordering, and take each counterexample to someone who knows the domain — intended, and it is written down; not intended, and it is a bug. Its end product is not a pile of proofs but a ledger: the implementation's claims, what the machine found, the questions for the author.

This document asks whether that method fits wcstack, tries it on two pieces of the code, and records what was decided.

## 1. What wcstack already has

Most of the method is here already, under other names. What is missing is the machine: every existing check is a case someone chose.

What the playbook adds is to generate the cases: every sequence of operations up to a length, every combination of a predicate's inputs, run against the code, with the claims as laws.

## 2. Tools: no Z3, no TLA+

wcstack does not need either.

- **Z3** answers "for every input". The predicates worth checking here — a link's current state, a route's priority, the release workflow's refusals — take a handful of attributes over a few representative values. A product of a few thousand cases runs in milliseconds and needs no solver.
- **TLA+** answers "for every ordering", but over a model written by hand. The playbook's own warning (§6, §7) is the gap between that model and the code, and a model built from memory proves the wrong thing. The stateful parts of wcstack are small enough to drive directly: replay every sequence of operations on the real object and check the laws after each step. There is no model to drift.
- **The playbook's own rule** (§1): when the state space is finite and deterministic, plain enumeration is cheapest. A bounded sequence of calls on one object is both.
- **The project's rules**: no runtime dependencies is not at stake (these are tests), but a Java model checker or a large WASM solver in CI is the kind of setup the project avoids. Bounded enumeration is a few dozen lines of TypeScript in an ordinary Vitest file, and runs in the CI jobs that exist.

Bounded is not a proof for every length. It is enough in practice: most defects have a small counterexample (the small-scope hypothesis), and both found below are five steps or fewer. TLA+ stays an option for one place, the router under view transitions (§5), if driving the real code there proves impractical.

## 3. How a check is written

1. **The real code, not a model.** Only the platform is faked (a view transition, the Navigation API, a guard's promise), as the pattern-testing plan does.
2. **Laws in domain words, taken from the documents.** A README sentence, a contract section, a source comment — not the current output. The pattern-testing plan's rule holds: do not establish semantics from what the implementation happens to do.
3. **The ghost.** Beside the real object, the check keeps what the laws need in their own terms — which requests were issued, which settled, which generation — and compares each return value with what the law says it should be.
4. **Shortest witness.** Sequences are generated by length, so the first failure of a law is its shortest counterexample, printed as the sequence of calls.
5. **A broken variant on the test side.** Each suite wraps the real object so that it breaks one rule on purpose, and asserts that the check fails. Never a switch in `src/`.
6. **A counterexample goes to the author before it becomes an expectation**, with a recommendation, as a seam app's findings do. A law that holds is pinned as it is.

## 4. Two trials

### 4.1 `io-core/operation-lane.ts`

The lane is the request bookkeeping that `fetch`, `upload`, `credential` and `eyedropper` use as `latest`, and `contacts` and `share` as `exhaust`; `queue` and `overlap` are implemented and unused. It runs no promise itself, which makes it a small state machine.

- **Alphabet**: `begin`, `disposeOwner`, `abortActive`, and for each ticket issued so far `claimTerminal`, `finalize`, `retry`, `canCommit`.
- **Laws**, from the file's comments and [async-execution-model.md](./async-execution-model.md) §4–§5:
  - *CommitOnlyWhenEligible* — a ticket claims its terminal at most once, and only while it may commit: the newest request (`latest`), the head of the queue (`queue`), the one let in (`exhaust`), any live one (`overlap`), never one issued before a dispose.
  - *GuardAgrees* — `canCommit` says the same.
  - *RetryOnlyWhilePending* — a retry is granted only to a ticket that may still commit and has not claimed.
  - *ExhaustAdmits* — `exhaust` refuses a request exactly while one is live.
  - *LatestAbortsSuperseded*, *DisposeAbortsAll* — the superseded request's signal is aborted; a dispose aborts every live signal.
  - *InFlightCounts* — `inFlightCount` is the number of live requests of the current owner.
- **Size**: all four policies, every sequence up to 7 calls — 667,424 sequences per policy, 45 s in total; up to 5 calls, 6,036 per policy, under a second.
- **Broken variant**: a lane whose `finalize` leaves the active slot taken fails several laws under `latest`, `exhaust` and `queue` (`overlap` has no single slot to leave taken).

Two laws break, both at their shortest at depth 5 and nothing new up to 7:

1. *InFlightCounts*: `begin` → `claimTerminal(A)` → `disposeOwner` → `begin` (B) → `finalize(A)` leaves `inFlightCount` at 0 with B in flight. `disposeOwner` settles every live operation as stale except one already claimed, which it leaves `committing`; the later `finalize(A)` then counts down the new owner's request. Only tests read `inFlightCount`, so nothing a page sees changes. The same path reports A to the trace twice — `io:stale-dropped` from the dispose and again from the finalize — against the trace conformance law that a terminal outcome is reported at most once per operation (§6.3), and the test that pins it says the finalize settles A as `success`, which the code does not do.
2. *RetryOnlyWhilePending*: `retry` grants a fresh, unaborted signal to a superseded `latest` request and to a request waiting behind the head of a `queue`. No Core calls `retry` today.

Reading the file for the laws found a third thing, which no law covered: the lane remembers every finished operation in a map it never empties — 100,000 entries after 100,000 fetches. On a page left open for a shift ([long-lived-pages.md](./long-lived-pages.md)), a polled `<wcs-fetch>` grows it without bound.

### 4.2 `<wcs-link>`'s current state

`_updateActiveState` in `packages/router/src/components/Link.ts` decides `aria-current` from `to`, `match` and `query-keys`, a predicate refined in 4.10.0, 4.10.1, 4.11.0 and 4.12.0. The trial copied it line for line (the query helpers in `searchParams.ts` are the real ones) and ran 80 configurations — eight `to`, five `query-keys`, with and without `match="prefix"` — over 30 URLs.

Two claims hold everywhere: the README's "each current on every page of their category, one tab at a time" for tabs with `query-keys`, and `match="prefix"` only ever widening what is current. Two findings:

3. With a repeated key, `?cat=b&cat=a`, the router's `searchParams` is `{ cat: "a" }` (last wins, [router-state-contract-design.md](./router-state-contract-design.md) (ja) §3.5) while a link to `?cat=a` is not current: the link compares the repeated values as a set. Two parts of one package read the same URL two ways.
4. `to="/n?cat=a" query-keys="page"` is current (`"true"`) on `/n?cat=b`: a key that `to` sets and `query-keys` does not name is not compared. That is what the README says `query-keys` does, but nothing tells the author who wrote it expecting `cat` to count, and the lint does not read `query-keys`.

## 5. Where it fits

In the order of what it would catch, with the defects that show the shape:

1. **The router's navigations under `<wcs-view-transition>` and guards.** 4.11.2 fixed a Forward within a frame of a Back that compared itself with the routes before the Back, whose swap still waited in the transition, and placed nothing — the URL was the Forward's, the page the Back's. It is the playbook's "decision separated from the record" (a check at one time, applied at another), and it reproduced 18 times in 20. A seam app found it; enumerating navigations, guard settlements and frames against the real router finds that shape directly. The law: once nothing is pending, the routes on screen are the URL's, each once, and a refused guard redirects only for the navigation still current.
2. **The lane and the I/O Cores.** The trace conformance laws (§6) are the invariants; §4.1 is the first suite.
3. **`transition-runner`'s "applied exactly once"** under `latest` / `queue` / `exhaust`, with transitions that skip, abort or reject.
4. **`@wcstack/state`'s list reconcile.** Finite and deterministic: every permutation, with repeats, of a small list against the DOM order and the row identities. 4.13.0 claims a swap "moves the same rows as before"; that is an equivalence to enumerate.
5. **Predicates**: `<wcs-link>` (§4.2), routes that a higher-priority route always shadows (a lint rule), `scripts/compute-next-version.mjs`'s refusals.

The playbook's list of defect shapes (§2) also reads as a review checklist for I/O nodes. 4.7.0 fixed one of them — a `<wcs-guard-handler>` without a script opened its route, fail-open where a failed script closed it.

It does not fit size, performance, screen readers or a browser's own behavior, and the reactive core of `@wcstack/state` as a whole is too large to drive this way; signals' property test is the shape for that.

## 6. Decisions (2026-11-03)

The author took each recommendation.

| # | Finding | Decision | Lands in |
|---|---|---|---|
| ① | §4.1-1: `inFlightCount` wrong after a dispose during a commit; reported twice | The lane keeps the set of live operations instead of the finished ones. A dispose settles every live operation as stale, a claimed one too, reported once; a later `finalize` does nothing | step 2 |
| ② | §4.1-2: `retry` grants a request that may no longer commit | `retry` refuses it | step 2 |
| ③ | §4.1: the map of finished operations grows without bound | Nothing is kept for a finished operation (falls out of ①) | step 2 |
| ④ | §4.2-3: repeated query keys read two ways | Documented in the router README (en/ja) | #611 |
| ⑤ | §4.2-4: a key of `to` that `query-keys` does not name is not compared | A lint rule, `wcs/link-query-key-ignored` (warning) — reported where **none** of `to`'s keys is named: leaving some out is meant (a category tab to page 1, `to="?cat=a&page=1" query-keys="cat"`, is current on every page of its category) | #611 |

In the mistake catalogue, ⑤'s disposition is *runtime report*: the router reads both attributes and could warn for a bound `to` too. The author kept it so on 2026-11-03, with no runtime warning scheduled.
| ⑥ | §8-6: the binder protocol's pending queue keeps every route placed on a page without a binder | The queue holds what is in the document, each subtree once, and a late binder is handed only that (decided 2026-11-03, after steps 2 and 3) | #610 |

## 8. Results of steps 2 and 3 (2026-11-03)

**Step 2, the lane** (#608). The lane keeps its live operations, and ①–③ follow. Reading the unit test that pinned the dispose-during-commit path found a second claim the code did not keep: the test said the later `finalize` settled the operation as `success`; the code settled it as stale and reported it twice. The test now says what happens — stale, reported once, the next request's count untouched; the author approved the change of claim on 2026-11-03. `packages/fetch/__tests__/operationLane.exhaustive.test.ts` runs the §4.1 laws over every sequence of up to 5 calls (6,036 per policy, about a second) and reports the shortest counterexample per law; five lanes broken on purpose, as test-side subclasses, fail it, and so does the lane before the fix, under all four policies.

**Step 3, the router** (#609). `packages/router/__tests__/navigation.exhaustive.test.ts` drives the real `<wcs-router>`, `<wcs-route>` and `<wcs-outlet>` in happy-dom. Only the platform is faked: a transition arbiter that applies the swaps it is handed in order, one per frame, and a guard on one route whose promise the test settles. The alphabet is a link to each of three pages, back or forward to two of them (the URL, then `popstate` — the router's path without the Navigation API), a query-only navigation, a frame, and allowing or refusing the oldest or the newest pending guard. The laws: at most one page on screen at any time; once nothing is pending, the URL is where the reader went, a refused guard sending to `/` only for the navigation still current; the screen is that URL's page; the router's `path` is that URL.

- At depth 4 (2,516 sequences, about 1.5 s, the CI depth) the router of 4.11.0 fails with both defects 4.11.2 fixed, each at its shortest: `link(/b), link(/a)` leaves page b under `/a`, and `link(/g), link(/g), refuse(oldest)` sends an overtaken navigation to `/`. A seam app found the first, at 18 runs in 20 in a real browser.
- The current router holds every law up to depth 6 (160,363 sequences, about 6 minutes).

The first run at depth 6 ran out of memory, which is the next finding:

6. On a page without a binder (no `@wcstack/state`), `bindSubtree` in `protocol/binder.ts` puts every route the router places after the first render on a global pending queue that only a binder's arrival empties. After 100 navigations between two routes the queue holds 100 entries, of 2 distinct nodes; a binder arriving then is handed the hidden route's content, detached from the document, 50 times — and `showRouteContent.ts` says a binder must not take a detached subtree. `@wcstack/state` 4.x passes over such a subtree (a 3.x binder bound it), so what a page sees is the growth: a router-only page grows the queue by one entry per placed element per navigation, `<wcs-head>`'s clones included, for as long as it is open.

**⑥, decided as recommended** (#610): `bindSubtree` drops queued subtrees that have left the document and does not queue one twice; `flushPendingBinds` hands over only what is still in the document; a route placed again is offered again by the router. state's core gains 4 B gzip. Run without its queue reset, the enumeration at depth 5 keeps the queue at one entry (239 MB of heap, 3,550 MB before); the reset stays in #609 until #610 is on main.
