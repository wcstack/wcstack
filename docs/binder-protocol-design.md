# 設計: binder プロトコル — 後から DOM に入ったノードをバインドする

- **状態**: **実装済み・main 着地（2026-08-27）**。§0 の決定レコードが正本。実装で判明した差分は §9。着手前に潰すとした論点（`<wcs-head>` は移動で済むか）は実測で決着（§8）。
- **対象**: `@wcstack/state`（binder の提供側）、`@wcstack/router`（最初の利用側）。正本の型は `/protocol/` に置き、`scripts/sync-protocol-types.mjs` でパッケージへミラーする。
- **一言で**: 「**DOM を差し込んだ側が、それをバインドする側へ手渡す**」ための最小のプロトコル。`transition-runner` の双対で、あちらが「変更をアニメーションする者へ渡す」なら、こちらは「新しいノードをバインドする者へ渡す」。
- **動機**: `data-wcs` のバインドは、state がバインドを構築した時点で document に居たノードにしか存在しない。非活性ルートの内容も `<wcs-head>` のクローンもその時点に無いので、**書いたバインドが黙って何もしない**（[i18n-impl-plan.md](./i18n-impl-plan.md) §3-0 に実測）。
- **経緯**: 先に応急処置（router が気づいた時点で警告・PR#190）を入れ、続いて本プロトコルで実際に動くようにした。警告は「state を読み込んでいないページ」向けの診断として残る。

## 0. 決定レコード

| ゲート | 論点 | 決定（提案） |
|---|---|---|
| **D1** | 何を作るのか | **「このサブツリーをバインドして」を渡す 1 関数**。ライフサイクル管理でも DI でもない |
| **D2** | 発見方法 | **グローバル symbol 上の registry**（`transition-runner` と同形）。`router` は `state` を import しない |
| **D3** | 未インストール時 | **何もしない**。今日と同じ挙動に戻るだけで、警告（応急処置）はそのまま残る |
| **D4** | 冪等性 | **同じノードを二度渡しても二重バインドしない**。これが最大の実装リスク（§4） |
| **D5** | 呼ぶ側 | **DOM を挿入した側**。router では `showRoute` の挿入後と `<wcs-head>` の反映後 |
| **D6** | 同期・非同期 | **同期**。挿入直後に初期値が入っていないと 1 フレーム空が見える |

| **D8** | 適用範囲 | ルート内容と `<wcs-head>`。**リスト行のような state 自身の挿入は対象外**（既に自分で扱っている） |

## 1. なぜプロトコルなのか

素朴な代案は 2 つある。どちらも採らない理由がある。

### 案 A: state が未知の追加サブツリーを走査する

`BindingOwner` の MutationObserver は今も全追加ノードを見ているので、「関心のある session が無いノードだったら `[data-wcs]` を探して束ねる」と書ける。**プロトコルは要らない。**

採らない理由は**コストの置き場**である。この走査は **DOM 挿入すべて**に乗る。state 自身のリスト描画は `observerSkip` で除外できるが、アプリや他のライブラリが行う挿入はすべて `querySelector` を払う。リスト描画の最適化に費やしてきた経緯（`docs/list-replacement-dependency-scaling.md` 系）に照らすと、**バインドを 1 個も使っていない挿入が最も多い**のに全員が払う形は逆行している。

加えて意味論が緩い。「DOM に入ったものは何であれバインドされる」は、`innerHTML` で外部由来の文字列を入れた瞬間に `data-wcs` が発火することを意味する。これは [csp.md](./csp.md) / Trusted Types の方向と噛み合わない。

### 案 B: router が state を import する

パッケージ間の依存が生まれる。`@wcstack/router` は state 無しでも成立する（`examples/router-spa` の About ページは state を使わない）。**依存の向きを作らずに済むなら作らない**、が既存の判断で、`transition-runner` がまさにその形で解かれている。

### 決定: 既存の前例に乗せる

`transition-runner` は「DOM を変更する側（state の drain / router のルート差し替え）が、遷移を裁定する側へ変更を手渡す」。**binder はその双対**で、「DOM を挿入した側が、バインドする側へノードを手渡す」。同じ形なので、規範も後始末の作法もそのまま流用できる。

## 2. 形

```ts
// /protocol/binder.ts（正本）
export interface IBinder {
  /**
   * サブツリーをバインド対象として取り込む。同期。
   * 既にバインド済みのノードは無視する（D4）。
   * options.range: 呼ぶ側が範囲を持ち運ぶ宣言（下の契約、§9-5）。
   */
  bind(subtree: Node, options?: { readonly range?: boolean }): void;
}

export const BINDER_SYMBOL = Symbol.for("wcstack.binder");
```

利用側（router）:

```ts
const binder = (globalThis as any)[BINDER_SYMBOL] as IBinder | undefined;
binder?.bind(node, { range: true });  // 居なければ今日と同じ挙動（D3）。range は範囲を持ち運ぶ router だけが渡す
```

提供側（state）は `bootstrapState` で登録する。

第 2 引数 `options`（`IWcsBindOptions`。省略できる。2026-10-02 に足した）は、呼ぶ側がサブツリーについて宣言すること。

- `{ range: true }` は「呼ぶ側はサブツリーが置かれた範囲を持ち運ぶ」の宣言。外すときは自分の開始の印から終了の印までをまとめて持ち出し（提供側がサブツリーの横に描いたもの — ルートの内容の直下の構造テンプレートがアンカーの前に描いた行・枝 — を含む）、戻すときはそのまま戻す。
- 根が構造のテンプレート（`for:`／`if:`／`elseif:`／`else:`）のサブツリーを提供側が描いてよいのは、この宣言があるときだけ。宣言が無いと、描いた行や枝に呼ぶ側の手が届かず、外したときに残る。
- 版は 1 のまま。追加の引数で、知らない提供側は無視し、省略すれば従来の契約になる。
- 提供側が居ない間に保留したサブツリー（§9-1）は宣言を持ち越さない。後から来た提供側の最初の走査が、その場で束ねるため。
- 宣言を渡すのは router（ルートの内容と、`<wcs-layout-outlet>` が置いた中身。§3）。`<wcs-head>` は要素 1 つだけを追うので渡さない。
- 3.x（@wcstack/state 3.x）の提供側は第 2 引数を読まない。根が構造のテンプレートのサブツリーは、宣言があってもなくても描かず、束縛の適用の失敗として報告する。

## 3. 呼ぶ位置

| 位置 | 契機 | 備考 |
|---|---|---|
| `showRoute` | ノードを挿入した直後 | 初回描画のルートは既に document に居るので二度目の呼び出しになる → **D4 の冪等性が必須**。文書に入っていないノード（読み込み待ちのレイアウトの中）は渡さない（§9-5） |
| `Head._reapplyHead` | head に入れた直後 | 毎回新しいクローンなので常に未バインド。**元の子も未バインド**なので、クローンをやめても解決しない（§8-2） |
| `LayoutOutlet._initialize` | レイアウトのテンプレートと子を outlet に置いた直後（2026-10-02） | 遷移で入ったレイアウトの中のルートの内容は、`showRoute` の時点ではレイアウトの読み込み待ちで文書の外にあり、レイアウトのテンプレート自身の束縛もここでしか渡せない。binder が居なければ渡さない（保留キューに溜めず、後から来る state の最初の走査が拾う）。shadow root の中は対象外（§9-5） |

`<wcs-head>` 側には固有の問題がある。head のクローンは**再適用のたびに作り直される**ので、バインドも毎回張り直しになり、古いクローンのバインドは破棄されなければならない。`BindingOwner` の削除検知に乗るかは要確認（§6-2）。

なお `bind()` を**挿入のたびに**呼ぶ必要はない。§8-3 の実測どおり、一度バインドされたノードは `<head>` へ移動しても追従する。呼ぶべきなのは「まだ誰も知らないノード」だけである。

---

## 4. 冪等性が最大のリスク

`showRoute` は「初回描画で既に document に居るノード」にも呼ばれる。ここで二重にバインドすると、1 回の変更で 2 回 DOM に適用される（実害は少ないが、リストや `if` では構造が二重に作られうる）。

**判定の候補**

1. ノードごとの「バインド済み」マーク（WeakSet）— 単純だが、`_state` 再 set でバインドを作り直す既存経路と整合が要る
2. 既存の「関心のある session を持つか」判定（`forEachInterestedSession` の裏にある台帳）を再利用する — 台帳が既にあるので追加コストが小さい
3. 呼ぶ側が「初回描画では呼ばない」— **採らない**。呼ぶ側に不変条件を負わせる設計は破られる

**推奨は 2。** ただし bind の入口から参照できる形になっているかは未確認（§6-1）。

## 5. 非目標

- **破棄のプロトコル化**（D7）。切り離しは既存の MutationObserver が扱える
- **state 以外の binder**。プロトコルは 1 つの実装しか想定しない（`transition-runner` の arbiter が 1 つなのと同じ）
- **バインド以外の初期化**（カスタム要素の upgrade 等）はブラウザの仕事
- **`innerHTML` で入れた任意の DOM の自動バインド**（§1 案 A の意味論）。**明示的に渡されたものだけ**を束ねる

## 8. 実測: `<wcs-head>` は「クローンをやめて移動」で済むか（2026-08-27）

初稿は §6-3 に「実ノードを移動すればバインドが付いていくので、`<wcs-head>` にはプロトコルが要らないかもしれない」と書いた。**実コードで確かめた結果、単独では成立しない。** ただし過程で 1 つ有用な事実が確定した。

### 8-1. 測ったこと

`<wcs-head>` を body 直下（ルートの中ではない）に置き、バインド付きの子を持たせたページを実ブラウザで観測した。

```html
<p id="direct" data-wcs="textContent: pageTitle"></p>   <!-- 対照 -->
<wcs-head id="h">
  <title data-wcs="textContent: pageTitle"></title>
  <meta name="description" data-wcs="content: pageDesc">
</wcs-head>
```

| 観測点 | 結果 |
|---|---|
| 対照（body の普通のバインド） | `"BOUND TITLE"` ＝ state は正常 |
| `<wcs-head>` の子（`childElementArray`） | `connected: false` / `parent: null` / `textContent: ""` |
| `<wcs-head>` の子要素数 | `0` |
| `document.title` | `""`（head には未バインドのクローンが居る） |

### 8-2. 結論 1: 元ノードがそもそもバインドされていない

`_initialize()` は `connectedCallback` の中で**子を `<wcs-head>` から `removeChild` して配列に退避する**。これは router の auto バンドルが実行された時点、すなわち **state がバインドを構築するより前**に起きる。したがって子は走査対象に一度も入らない。

**クローンをやめて移動しても、移すのは「バインドされていないノード」である。** 症状は何も変わらない。

さらに独立した第 2 の障害がある。`buildBindings` は `initializeBindings(document.body, null)` で **body しか走査しない**（[buildBindings.ts:15](../packages/state/src/buildBindings.ts#L15)）。仮に子を `<head>` に置いたままにしても、そこは走査範囲の外である。

### 8-3. 結論 2（副産物）: **バインドは `<head>` への移動に耐える**

こちらは初稿の想定どおりだった。body でバインドされた `<title>` / `<meta>` を `document.head` へ `appendChild` で移し、その後に state を書き換えると、**値は届く**。

```
bound in body      : {"stay":"FIRST","mover":"FIRST","metaContent":"FIRST"}
after move + write : {"stay":"SECOND","moverInHead":"SECOND","metaInHead":"SECOND"}
```

理由は `BindingOwner` の削除判定が `if (this.root.contains(node)) return;` であること。移動後も document は当該ノードを含むので「削除」とみなされず、バインドは生き続ける。

**プロトコル設計にとっての意味**: `bind()` は **挿入・移動のたびに呼び直す必要がない**。一度バインドされたノードは、その後どこへ移動しても追従する。プロトコルの責務は「**まだ誰も知らないノードを 1 回だけ登録する**」ことに限定できる（D4 の冪等性がそのまま効く）。

なお副次的な注意として、移動した `<title>` は head 内の**先頭の** `<title>` でなければ `document.title` にならない（実測で `documentTitle: "ORIGINAL"` のまま）。`_reapplyHead` は既にキー一致で `replaceWith` しているので、この点は現行の実装で満たされている。

### 8-4. `<wcs-head>` を動かすなら、成立条件は 2 つ同時

`<head>` に居着くノードが「state がバインドしたノード」であればよい。そのための道は 3 つある。

| | 案 | 評価 |
|---|---|---|
| **1** | **binder プロトコル** — head へ入れた後にそのノードを `bind()` に渡す | 順序に依存しない。§8-3 より、渡すのは 1 回でよい |
| **2** | 移動 ＋ **state の走査範囲を `documentElement` へ広げる** | `_initialize` の切り離しもやめる必要がある。しかも `_reapplyHead` が state の走査より先に走れば結局間に合わない ＝ **順序レースが残る** |
| **3** | 移動 ＋ router が「state の準備完了」を待つ | router → state の依存が生まれる。§1 案 B で棄却した形 |

**したがって `<wcs-head>` もプロトコルの対象から外れない。** §6-3 の期待（対象が半分になる）は外れたが、代わりに §8-3 によってプロトコル自体が単純になった。

### 8-5. この確認から得た手順上の教訓

「移動すればバインドが付いていく」という仮説は**半分正しかった**。正しかったのは検証しにくい後半（移動への耐性）で、外れたのは自明に見えた前半（元ノードはバインドされている）だった。**前提のほうを先に測る。**

## 9. 実装で判明した差分（2026-08-27）

設計は概ねそのまま通ったが、**タイミングの前提が 3 つ外れた**。いずれも実装前には見えず、実ブラウザで初めて出た。

### 9-1. 「同期で束ねる」だけでは足りない（D6 の補足）

D6 は「同期。挿入直後に初期値が入っていないと 1 フレーム空が見える」とした。挿入**後**に呼ぶ規約はそのままだが、**起動時だけは同期に束ねられない**。

`<wcs-head>` はクローンを `connectedCallback` の中で head へ入れる。その時点では

- router の auto バンドルが先に走るなら **binder がまだ居ない**
- state の auto バンドルが先に走っても、`<wcs-state>` の登録は `connectedCallback` の `await` より後なので **state がまだ居ない**

つまり読み込み順をどちらにしても早すぎる。そこで**初期バインド構築の完了を唯一の合図**にし、それ以前に差し出されたものは 2 段の保留で預かる。

| 保留 | 置き場 | 誰が流すか |
|---|---|---|
| binder がまだ居ない | プロトコル側のグローバルキュー（`Symbol.for` 共有） | `drainPendingBinds` |
| binder は居るが構築前 | state 側の binder モジュール | 同上 |

どちらも `buildBindings` 完了直後（`markBindingsBuilt` の後）に流す。**まだ描画されていない時点なので、遅らせても「空の 1 フレーム」は生じない。**

初稿は「進行中か」を `bindingsReadyByNode` のエントリ有無で測ろうとしたが、これは**読み込み順によって逆の答えを返す**（登録前は「エントリ無し＝構築しないページ」に見える）。判定は**完了の側**（`areBindingsBuilt`）で持つ。

### 9-2. TreeWalker はルート自身を返さない

`getSubscriberNodes` の TreeWalker は `nextNode()` から始めるので、**渡したルート要素そのものは走査されない**。`buildBindings` は `document.body` を渡すので今まで露出しなかったが、binder には宣言をルートに持つノードが来る（`<title data-wcs="…">`）。

当初は、ルートが宣言を持つときだけ**親から走査する**ことで解決した（兄弟の重複登録は `registeredNodeSet` が弾く、という前提）。この前提は、まだ集めていない兄弟の構造テンプレートには成り立たなかった（#409、§9-5）。

**現在（#409 の修正）**: 親からは走査しない。**渡されたサブツリーの中だけを、ルートを含めて束ねる。** ルートが宣言を持てばルートを列の先頭に置き、`getSubscriberNodes(subtree)` の結果と合わせて `initializeBindings` に渡す（SSR のハイドレーションがブロックのノード列を集めるのと同じ形）。mustache の変換と構造テンプレートの収集（`collectStructuralFragments`）も同じサブツリーの中だけなので、束ねる範囲と集める範囲が一致し、渡されていない兄弟には届かない。あわせて次のことを決めた。

- **ルートが Light DOM のマウント**（直下に配線された `<wcs-state bind-component>` を持つコンポーネント要素）なら、束ねるのはルート自身の宣言（ホストのスコープ）だけ。中身（mustache・構造テンプレート・子孫の宣言）は、配線の後にコンポーネントのスコープが自分で集める（[ADR-15](./architecture-hardening/15-state-component-mechanism-consistency.md) §1.13 の除外を、走査のルートにも当てる。`getSubscriberNodes` は走査のルートをコンポーネントとして数えない）。以前は中の構造テンプレートをホストのスコープで集めてしまい、適用に失敗していた。
- **binder の束縛は binder 専用の session に入れる**（ルートで引ける session には入れない）。ルートで引く session は、スコープが丸ごと破棄する単位である。サブツリーをキーにすると、ルートが Light DOM のマウントのとき、ホスト側の束縛（`class.…`・`attr.…`・`onclick`）がマウントのスコープの session（コンポーネントがキー）に入り、コンポーネントが中身を描き直す再初期化で一緒に破棄されていた（修正の途中で見つかった。3.5.0 は宣言を持つルートを親で引いていたので起きない）。
- **文書に無いサブツリーは束ねない**（`isConnected`）。`bind()` を呼ばれた時点で外れているものは預からない（預かると、来ない構築を待ち続ける）。構築の完了まで預かった間に外れたもの — 構築の走査がアンカーに置き換えた、渡された構造テンプレート — も飛ばす。4.0 の提供側も `isConnected` を見る。
- **すでに束ねたノードには触らない**（#414）。`initializeBindings` は、この呼び出しで新しく集めたノードにだけループ文脈を張る。以前は渡された列の全ノードに張り直していたので、束ね直されたサブツリーの中の行のノード（行の中の `if:` のアンカー）のループ文脈が空に戻り、行の中の `if:` が次の切り替えで失敗していた。SSR のハイドレーションは列を `collectNodesAndBindingInfosOf` に直接渡すので、この絞り込みを通らない。

### 9-3. 診断の遅延に `setTimeout` は使えない

応急処置の警告は「binder が現れるかもしれない」ぶん判定を遅らせる必要がある。当初 `setTimeout(0)` にしたが、**deferred な module script はパース完了後に実行されるため、タイマーのほうが先に発火しうる**（実測）。`document.readyState` も deferred script の実行中は既に `"interactive"` なので「まだ loading か」では判別できない。

`window` の `load` を待つ形に落ち着いた。必ず発火し、全 deferred script より確実に後に来る。診断なので多少遅くて構わない。

**この 3 つはいずれも「いつ走るか」の話で、設計の骨格（誰が誰に渡すか）は変わっていない。** プロトコルの形が単純だったぶん、タイミングだけを直せば済んだ。

### 9-4. 残る非目標の確認

- `<wcs-head>` の**クローン再生成**（§6-2）は問題にならなかった。`bind()` が冪等なので、再適用で新しいクローンが来ればそれを束ね、捨てられたクローンは `BindingOwner` の削除検知に乗る
- 警告は**消していない**。state を読み込んでいないページでは今も出る（実測で確認）。binder が居るページでは出ない

### 9-5. ルートの範囲（2026-10-02）

**症状**: 着地のルートで、`<wcs-route>` の直下に置いた `for:`／`if:` のテンプレートを state がページの走査で描く（router が先にルートを挿入し、state が後からマウントする — CDN の auto でふつうの順序）と、描いた行・枝とアンカーはルートの元のノード（`childNodeArray`）の横に並ぶ。`hideRoute` は元のノードだけを外していたので、退場しても行が残った。戻ると、元のテンプレートはアンカーに置き換わって文書に無く、3.x は束縛の適用に失敗していた。

**修正**（router）:

- `showRoute` は初めての表示で、内容の後ろに終了の印 `<!--@@wcs-route-end:<absolutePath>-->`（SSR の終了マーカーと同じ文面。`route.endMarker`）を置く。
- `hideRoute` は placeholder から終了の印までをまとめて `route.held`（DocumentFragment）へ移し、次の `showRoute` がそれを戻す。範囲の外へ移された自分のノード（body へ移したダイアログ）は元の順の位置で持ち、アンカーに置き換えられたテンプレート（親の無い元のノード）は戻さない。終了の印が placeholder の後ろに無い（他のコードが動かした・取り除いた）ときは、placeholder の後ろに残っている最後の自分のノードまでを範囲とする（その間に描かれたものは持つが、その後ろに描かれたものは範囲と見分けられないので残る）。ただし、ほかのルートの印（隣のルートの placeholder、親の終了の印。自分の子孫の印は除く）を越えては伸ばさない。その先にある自分のノードは、範囲の外へ移されたノードとして 1 つずつ持ち帰る。一度置いたルートは、終了の印が無くなっても、書かれたノードから置き直さない（state がアンカーに置き換えた template が戻ってしまうため）。すでに隠しているルートをもう一度隠しても（重なったナビゲーション）、持っている内容は保つ。
- 移すノードとその順は、どれかを移す前に決める。移すたびに disconnectedCallback が走り、範囲を書き換えうるため（`<wcs-link>` は自分の anchor を外す）。その後で 1 つずつ移し、先の移動の callback が別の場所へ動かした・外したノードは、そのままにする。
- 表示中のルートをもう一度表示すると（パラメータの変化）、隠すときと同じく `route.held` へ持ち出し、すぐに戻す（範囲の外へ移された自分のノードも戻る）。範囲を持つ前の router と同じく、カスタム要素が再接続し、`connectedCallback` が新しいパラメータを読む。並びは保つ。以前は元のノードを placeholder の直後へ 1 つずつ戻していたので、`H2,P,FOOTER` が `P,FOOTER,H2` に並べ替わっていた。
- 出すルート（新しいもの、パラメータの変わったもの、その下のすべて）は二相で出す（`showRouteContent`）。まず全部にパラメータを割り当て、それから置く。親を持ち出して戻すと子の内容も一緒に動くので、子の `connectedCallback` はその時点で新しいパラメータを読む必要がある。もう一度表示するルートの下でもう一度表示するルートは、親と一緒に動いたので、もう動かさない（子の要素は 1 回だけ再接続する。以前は、子が親の内容の要素の中にあると、親の再挿入で古いパラメータのまま 1 回、子の再挿入でもう 1 回再接続していた）。
- 戻すのは持ち出したものなので、作者のコードが取り除いた直下のノード（閉じたお知らせ）は次の入場で戻らない。以前は元のノードを全部挿し直していたが、それでは state がアンカーに置き換えたテンプレートも戻ってしまう。
- `childNodeArray` は書かれたままのノード列で、binder に渡すのはこちら（§2 の宣言付き）。
- SSR は、`showRoute` が置いた終了の印をサーバーの終了マーカーとしてそのまま使い、採用したクライアントは範囲の終わりとして残す（docs/ssr-router-design.md §4）。

**3.x との組み合わせ**: 3.x の提供側は宣言を読まないので、範囲が効くのは state の最初の走査が描いたもの（着地のルート）である。遷移で入ったルートの直下の構造テンプレートは、従来どおり描かれない（束縛の適用の失敗として報告する）。要素で包めば描かれる。

**レイアウト**: 遷移で初めて入ったレイアウトでは、レイアウトのテンプレートの束縛と、その中のルートの内容が束ねられていなかった（3.x も）。ルートの内容を `showRoute` の後に渡す時点では、内容はまだ `<wcs-layout>` の中（文書の外）にあり、レイアウトのテンプレートはまだ読み込まれていないため。`LayoutOutlet` が中身を置いた後で、範囲の宣言付きで渡すようにした（§3）。着地のルートでは、state の走査が束ねた同じノードをもう一度渡すことになるが、3.x の `bind()` は冪等（`alreadyBound` と `registeredNodeSet`）で、二重には束ねない（`packages/router/__tests__/layoutOutlet.state3x.test.ts` がイベントの束縛のクリック数で確かめる）。#414 の修正からは、束ね済みのノードのループ文脈も保つ（§9-2）。3.5.0 までは、渡し直されたサブツリーの中の行のノードのループ文脈を空に戻し、行の中の `if:` が次の切り替えで失敗していた。渡し直しは着地に限らず、遷移でルートに入るたびに起きる（`bindRouteContent`）。回帰テストは `packages/state/__tests__/integration.binder.test.ts`（state だけ）、`integration.binder.router.test.ts`（遷移で出て戻る）、`integration.binder.rowContextLanding.test.ts`（構築の前に router が着地する）。

**文書に無いノードは渡さない**: router は、文書に入っていない（`isConnected` が偽の）ルートの内容を binder に渡さない（着地の `_offerInitialContentToBinder` と遷移の `bindRouteContent`）。読み込み待ちの `<wcs-layout>` の中のルートの内容がこれに当たり、置かれた後で `LayoutOutlet` が渡す（binder が居なければ、後から来る state の最初の走査が拾う）。以前は渡していたので、state を router より先に読み込むページ（binder が居て構築前）で、レイアウトのテンプレートが state の初期構築より後に届くと（`<wcs-layout src>` の取得が遅いとき）、3.x は構築の完了時にそれを文書の外のまま束ね、イベントの束縛が「切断された束縛」の未処理の拒否になり、その要素は以後束ねられなかった。binder が居ないときは、そうした内容を保留キューに溜めず（後から来る state が文書の外のまま束ねないように）、束縛が効かない警告の対象にだけする。4.0 の提供側は文書に無いサブツリーを自分でも無視し（`isConnected` を見る）、3.x の提供側も #409 の修正から、渡された時点と束ねる時点で同じ判定をする（§9-2）ので、どちらと組んでも同じ結果になる。

**#409（修正済み。提供側の `bindNow`）**: 3.5.0 までの 3.x は、宣言を自分に持つ要素を §9-2 の当初の形どおり親から走査していた。ルートの内容の直下でそうした要素がテンプレートを含む兄弟より前にあると、親（outlet）からの走査が、まだ構造フラグメントとして集めていない兄弟のテンプレートに届き、束縛の適用の失敗として報告して、そのテンプレートは以後描かれなかった。遷移で入ったルート、state の構築の後に router が着地したルート（`_offerInitialContentToBinder` も内容を 1 つずつ渡す）、shadow root のレイアウトの light DOM（`LayoutOutlet` が子を 1 つずつ渡す）で起きた。いまは渡されたサブツリーの中だけを束ねる（§9-2）ので起きず、この形のためにルートの本文を 1 つの要素で包む必要は無くなった。直下の構造テンプレートそのものは、上の「3.x との組み合わせ」のとおり、従来どおり着地のルートでしか描かれない。回帰テストは `packages/state/__tests__/integration.binder.test.ts` と、本物の router（`packages/router/dist`）で流す `integration.binder.router.test.ts`。router が先に着地し、state が後から構築する順は `integration.binder.routerLanding.test.ts` が守る（修正前も通る）。4.0 の提供側は渡されたサブツリーだけをルートを含めて走査する（`mountSubtree`）ので、もともと起きない。
