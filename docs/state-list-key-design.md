# リストキー（`$listKeys`）設計 — キー一致行のオブジェクト値展開

/ 対象: `@wcstack/state` / 状態: 実装完了（branch `feat/state-list-keys`、2026-08-05）

## 1. 問題

`for` の行同一性は「配列要素の値そのもの」（オブジェクトなら参照、プリミティブなら値）で
固定されている（`list/createListDiff.ts`）。並べ替え・挿入・削除はこれで正しく keyed に
動くが、**データ層が同一性を捨てた場合**に破綻する。

```js
this.items = await (await fetch("/api/items")).json();
```

JSON ラウンドトリップは全行を新しいオブジェクトにするため、旧行と一致しない。実測
（`__tests__/integration.listKeys.test.ts` の pin テスト）:

| 観測 | 結果 |
|---|---|
| 旧行 DOM の再利用先 | `[2, 1, 0]` — content プールが LIFO で逆順に再配布する |
| `<details>` の開閉 | 行 0 で開いた状態が**行 2 に現れる** |
| `document.activeElement` | `null`（フォーカス消失） |

バインドされていない DOM 状態（フォーカス、IME 変換中の文字列、`<details>` の開閉、
行内スクロール、`<canvas>` の描画、`<video>.currentTime`、非バインド `<input>`）は
「消える」のではなく**行間でシャッフルされる**。これは表示の誤りである。

### 1.1 既存の回避策が成立しない

id で突合して行オブジェクトを in-place 更新すれば DOM は保存される（実測で確認済み）。
しかしその綴りは、**行の追加・削除が同じ代入に混ざると更新を取りこぼす**。
`dependency/walkDependency.ts` の `selectExpansionIndexes` が、`addIndexSet` 非空時に
展開対象を追加行・移動行へ絞るためで、
[list-replacement-dependency-scaling.md §7.0](list-replacement-dependency-scaling.md) が
「診断不能」と明記した既知の契約穴である。fetch リフレッシュはほぼ常に構造変化を
伴うため、回避策として機能しない。

したがって論点は 2 層に分かれる。

| | 問題 | 層 |
|---|---|---|
| ① | 参照が変わると行 DOM の対応が壊れる | `for` の同一性 |
| ② | 参照を保つ回避策が構造変化と両立しない | 依存展開 |

## 2. 方針: キー一致行の「オブジェクト強制・値展開」

`$listKeys` で宣言されたリストパスへの配列代入時、キーが一致する行については
**新しいオブジェクトを捨て、旧オブジェクトを据え置いたまま、変化したフィールドだけを
per-path 書き込みで流し込む**。

```
1. $listKeys を引く（未宣言なら以降の経路に一切入らない）
2. キー突合 → 一致行は旧オブジェクトを採用したハイブリッド配列を構築
3. ハイブリッド配列を list として格納（通常の書き込み経路）
4. createListDiff で listIndex を確定
5. 一致行の変化フィールドだけを setByAddress で per-path 書き込み
```

### 2.1 なぜこれで両方解けるか

- **①** — 配列要素の参照が変わらないので `for` は行を再利用する。
- **②** — フィールド更新が `setByAddress` 経由の per-path 書き込みになる。これは §7.0 が
  「常に正しいイディオム」と規定したもので、行追加・削除と混在しても取りこぼさない。
- **`listExpansion: "diff"` を失わない** — 一致行は diff 上「無変化」のままで、変わった
  フィールドだけが正確に dirty 化される。リスト置換の O(変化行) スケーリングは維持される。

`createListDiff` は無改造。キー突合は書き込み経路で完結し、`for` に届く時点では
ハイブリッド配列になっているため、既存の値同一性 diff がそのまま正しく動く。

### 2.2 副次的な利得

無変化ポーリング（`s.items = JSON.parse(同じ JSON)`）は現状 1000 行すべてを再構築するが、
本方式では変化フィールドがゼロなので**書き込みゼロ・DOM 作業ゼロ**になる。

## 3. 宣言

state 側に置く。`$streams` / `$commandTokens` / `$eventTokens` と同じ族。

```js
{
  items: [],
  $listKeys: {
    "items": "id",                    // フィールド名
    "items.*.children": (row) => row.uid,  // 関数（複合キー用）
  },
}
```

**state 側に置く理由:**

- 書き込み経路（`setByAddress`）が view を参照せずに完結する。`for` 側の属性だと
  binding registry を引く必要があり、バインド確立前の書き込みでキーが未登録になる。
- 同一パスに複数の `for` があっても矛盾しない。
- ネストをワイルドカードパスで自然に書ける（§4）。
- SSR / hydration でも state 側にあるので一貫する。

### 3.1 バリデーション（宣言時 = `_state` セッター）

`processListKeysDeclaration` が以下を検査し、違反は `raiseError`。

- `$listKeys` はオブジェクト
- パスは非空文字列。空セグメント・先頭/末尾の `.` を禁止
- パス末尾が `*` であることを禁止（`items` がリストパスであって `items.*` ではない）
- キー指定は非空文字列か関数
- 文字列キーは `.` / `*` を含まないフラットなフィールド名
- `Object.prototype` 継承名（`__proto__` / `constructor` 等）を禁止

「そのパスが実際にリストか」は宣言時には判定できない（`listPaths` はバインディング
収集時に確定するため）。実行時に配列でなければ単に経路に入らない。

## 4. 展開の深さ: 宣言されたパスだけ再帰

未宣言のフィールドは値としてそのまま代入する（＝従来どおり参照置換）。宣言された
ネストパスは再帰的にキー突合する。

再帰は**自然に落ちる**。フィールド書き込みを `setByAddress` 経由で発行するため、
`items.*.children` への書き込みが再び本フックに入り、そのレベルのキー突合を行う。
親のハイブリッド配列は既に格納済みなので、`getByAddress` は旧 children 配列を返す。

段階導入が効く。宣言が必要なのは「オブジェクト配列 かつ 行内に非バインド DOM 状態が
ある」箇所だけで、`items.*.tags` のようなプリミティブ配列は参照置換されても
`for` 側の値同一性 diff が全行再利用するため実害がない。

## 5. 異常時は即エラー

opt-in で明示的にキーを宣言した以上、静かな劣化より即死を選ぶ。キー重複は実行時
データなので静的診断では捕まらず、黙って落とすと原因特定が困難になる。

| 条件 | 挙動 |
|---|---|
| 旧配列・新配列いずれかでキーが重複 | `raiseError` |
| キーが `undefined` / `null` | `raiseError` |
| 行が非 plain オブジェクト（class インスタンス、`Object.prototype` 以外のプロトタイプ） | `raiseError` |
| 行が `null` / 非オブジェクト | `raiseError` |

非 plain を拒否するのは、値展開が own enumerable データプロパティのコピーであり、
プロトタイプ・アクセサを持つオブジェクトでは意味論が保てないため。

## 6. その他の決定

- **フィールド差分の粒度** — `!==` で変化したフィールドのみ書き込む。全フィールド
  無条件書き込みにすると §2.2 の利得が消える。
- **消えたフィールド** — 新オブジェクトに無い旧フィールドは **`null`** を代入する。
  無視すると行の形が変わったことが DOM に伝わらず stale になる。`undefined` ではなく
  `null` なのは、この処理系では `undefined` が「状態が値を持たない＝無意見」であり
  `applyChangeToProperty` が書き込みごとスキップするため（明示的なクリアの語彙は
  `null`）。`undefined` を書くと state だけ更新されて DOM が旧値のまま残り、本機能が
  塞ごうとしている stale をそのまま再導入してしまう。既に `null` / `undefined` の
  フィールドは DOM 上も空なので、クリア書き込み自体を発行しない。
- **参照透過性** — 格納されるのはハイブリッド配列なので `s.items !== fresh` になる。
  これは受け入れる（README に明記）。
- **キー指定の値型** — フィールド名（文字列）と関数の両方を許す。
- **DCC の変更イベント** — `$bindables` に載せたリストに `$listKeys` を掛けると、
  per-path 書き込みが 1 本ずつサブパス発火を起こすため 1 回の代入で `1 + 変化行数` 回
  イベントが出る。値は要素から読む契約なので結果は変わらない。詳細は
  [architecture-hardening/15 §2.1](architecture-hardening/15-state-component-mechanism-consistency.md#21-dcc-の変更イベントは完全一致パスでしか出ない--修正済み)。
- **突合対象の旧配列** — `lastValue`（最後に適用された配列）ではなく**現在格納されて
  いる配列**と突合する。同一マイクロタスク内の連続書き込みでも、ハイブリッド構築が
  格納配列の参照を保存するため、適用時の `diff(lastValue, 最終配列)` と transitive に
  整合する。**per-path 書き込みに使う listIndex を引く diff も同じ基準**にする
  （§8.1 の台帳分裂を参照）。

## 7. 不変条件

1. `$listKeys` 未宣言時、書き込み経路の追加コストは `stateElement.listKeys` の
   `undefined` 判定 1 回のみ。挙動は完全に従来どおり。
2. 一致行の DOM ノード同一性・フォーカス・非バインド DOM 状態が保存される。
3. in-place 更新と構造変化（追加・削除・移動）が同一代入に混在しても、更新が
   取りこぼされない（§1.1 の穴を塞ぐ）。
4. `listExpansion: "diff"` の O(変化行) スケーリングを失わない。
5. 公式 isKeyed 全合格と `recycledOnRun` を維持する。

### 8.1 実装で確定した事実

- **`createListDiff` は無改造で済んだ。** キー突合が書き込み経路で完結し、`for` に届く
  時点ではハイブリッド配列なので、既存の値同一性 diff がそのまま正しく動く。
- **ネストの再帰は自然に落ちた。** フィールド書き込みを `setByAddress` 経由で発行する
  ため、`items.*.children` への書き込みが再びフックに入りそのレベルの突合が走る。
  親のハイブリッド配列は既に格納済みなので `getByAddress` が旧 children を返す。
- **消えたフィールドは `null` でなければならない**（§6）。当初 `undefined` で実装したが
  `applyChangeToProperty` が undefined を「無意見」として書き込みごとスキップするため、
  state だけ更新されて DOM に旧値が残った。本機能が塞ごうとしている stale の再導入。
- **`listExpansion: "diff"` の全行フォールバック抑止**（§2.2）は「キー突合が実際に
  成立した書き込み」に限定する。全行が既に同一オブジェクトのケース（生配列 in-place
  変異 + コピー再代入イディオム）は `mergeKeyedList` が null を返して通常経路に倒れ、
  従来のフォールバックがそのまま担う。
- **listIndex 台帳を分裂させてはならない。** per-path 書き込みの宛先 listIndex は
  当初 `diff(lastValue, ハイブリッド配列)` から引いていたが、`for` が未マウント
  （一度も描画していない／`if` で非表示）だと `lastValue` が空で**新しい台帳**が
  生まれる。一方で読み手（`applyChangeToFor` / `$getAll` / `resolve`）は現在格納
  されている配列の台帳（`listIndexesByList`）に収束し、ハイブリッド配列の要素は
  旧配列と同一オブジェクトなので `createListDiff` の `isSameList` 経路で**旧台帳**を
  返す。結果、書き込みが dirty 化・キャッシュするアドレスと読み手のアドレスが食い違い、
  行オブジェクトの値は正しいのにワイルドカード読みだけ旧値のまま残った（`$getAll`
  集計 getter が追随しない）。基準を「マージ相手にした配列 = 書き込み直前に格納されて
  いた配列」に統一し、その配列に台帳が無い場合は先に生やしてから引くことで、全経路が
  同一の listIndex 群に収束する。回帰テスト＝「for に描画されていないリストでも
  ワイルドカード読みが追随すること」。
- **非表示（deactivate 済み）の `for` 配下は本機能のスコープ外。** 行の同一性が保たれる
  更新は、非表示中に落ちた行内バインディングの適用を再表示時に取り戻せない。これは
  `$listKeys` 固有ではなく、行参照を保つ手書きマージ（§7.0 のイディオム）でも同じに
  壊れる既存の穴なので、別課題として
  [state-deactivated-content-stale-update.md](state-deactivated-content-stale-update.md)
  に切り出した（現行挙動は pin テスト「非表示中の行内更新は再表示で反映されない」で固定）。
  `$listKeys` は行同一性を保つ機能である以上、この組み合わせを踏む確率を上げる。
