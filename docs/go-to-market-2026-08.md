## 0. TL;DR（改訂版）

1. **初版の診断は維持**: 7 ヶ月の失敗は「作るのが足りなかった」ではなく「誰に何を売るかを決めないまま作り続けた」こと。フレームワークの土俵（エコシステム・事例・bus factor）では原理的に勝てない。
2. **「配線層に直接競合が存在しない」は事実誤認だった。** georapbox スイート（`<capture-photo>` 等、wcstack の I/O ノードとほぼ一対一）・GitHub 公式 `<clipboard-copy>`・`@ionic/pwa-elements`・awesome-standalones（66 収載）が実在する。しかも先行者の到達点は **~50 stars・被依存 0 件**＝これがこのカテゴリのベースレート。売りは「タグ単体」では成立せず、**「タグ + JS ゼロ配線（統一プロトコル）」のペア**に再定義する。仮説は「統一プロトコルによる合成可能性がこの ~50 stars の天井を破る」であり、これは検証可能な形で明示して張る。
3. **jsfb 公式提出は「最高レバレッジ」から降格。** ベンチ首位を 7〜10 年維持した mikado（star 852・週 DL 554）・ivi（star 799）が実証する通り、**jsfb は発見装置としては死んでいる**。Solid の実経路も「提出→発見」ではなく「提出→自分の記事の弾薬→読者の信頼」。提出は実行する（費用ほぼゼロ・引用元としての価値は本物）が、位置づけは**記事・比較表の弾薬製造**。提出物は signals のみ。
4. **買い手 1 位を差し替える。** 「既存アプリ持ちの個人開発者」はセグメントではなく属性（固有の生息地・クエリを持たない）。React 経路は VueUse / react-use-websocket（週 38 万 DL）に挟撃されている。配線層の自然な買い手は「**FW を持っていない・入れたくない人**」＝ htmx が地図を描いた市場。AI は買い手ではなく**チャネル**（新規コードの 1/4〜半分が既に AI 経由＝現在形）。
5. **今週の時限タスクが 2 つある**: TSKaigi Sendai 2026 CFP（**8/7 締切**）と npm Trusted Publishing (OIDC) 移行着手（**2026-08 の npm 2FA 変更前**・41 パッケージ）。
6. **R3 追加（08-02）**: 統合戦略案から主要 7 部品を移植（採否表は 9 行） — **4 層商品構造 + Land and Expand 導線**（§2-4）・**「2 ノード以上合成」指標**（§5）・**AI 収束ループ動画**（2-7）・**楔デモ配線版 intersect→fetch→state**（2-2 改）・**「package 数を KPI にしない」kill**（§7）・買い手①ピッチ素材（§2-3）・一文戦略（§2-4）。同案が独立に R2 と同じ核（FW として売らない・配線中核・AI=チャネル・jsfb=証拠製造装置）へ到達したことは診断の再現確認として価値がある。一方、**収益化 5 商品・「複数 FW チーム」市場・90 日成果目標（外部 10 件等）・Stable/Labs 分離は棄却**（検証済みの棄却理由は synthesis-review）。

## 2. 戦略の核 — 条件付きで維持する「配線層」

### 2-1. 維持: フレームワークの土俵では原理的に勝てない

初版 §2-1 の診断はレッドチーム 3 本の攻撃を通しても崩れなかった。「41 パッケージのフレームワーク」として提示する限り、star 5・作者 1 名・外部ユーザー 0 で判定が終わる。

### 2-2. 修正: 「配線層」再定義には 4 条件を付ける

1. **「直接競合が存在しない」の文言を全面削除。** 対外的には近縁（georapbox / Polymer iron / htmx / VueUse）を**自分から先に名指し**し、差分（単発の寄せ集め vs 統一プロトコルで合成可能）を言う。「競合不在」は HN・詳しい読者に一撃で刺される嘘であり、~50 stars というベースレートを直視した上で「プロトコルが天井を破る」を検証可能な仮説として張る。
2. **売り物は「タグ単体」ではなく「タグ + 無 JS 配線」のペア。** タグ 1 個の土俵は VueUse/georapbox が勝つ。差別化が成立する最小デモは「**タグ 2 個を data-wcs 1 行で JS ゼロ配線する**」（例: `<wcs-geo>` → `<wcs-ws>`）。state は「上位パスへ格下げ」ではなく「配線面として最初の 1 画面に出す」＝堀（プロトコルと reactive core）を店頭に戻す。
3. **jsfb ブリッジ文を LP に常設。** 「速い reactive core（jsfb 公式で vanilla/solid 級）は配線層の土台。オーバーヘッドの心配は不要」という**不安除去の一文まで**。性能を購入理由に昇格させない。これでベット(1)（配線層）とベット(2)（jsfb）の内部矛盾を解消する。
4. **配線層フレーミング専用の反証条件をゲートに追加**（§5）。

### 2-3. 売り文句（実物は評議会成果物 §コピー班に完備・ja/en 両方）

H1「What if the browser had these built in?」は維持。直下に:

> **WebSocket・カメラ・SSE・位置情報 — Web API の配線を、グルーコードではなく HTML タグ 1 個で。**
> **ビルド不要・ランタイム依存ゼロ。いま動いている React / Vue アプリにも、タグ 1 個から足せます。**

「useEffect ではなく」版は React 文脈の広告文（Zenn/HN/アダプタページ）用に温存し、LP 本体は「グルーコード」で買い手全域をカバーする。npm description（214 字制限内の実物）・README 冒頭 1 スクリーン・買い手別 30 秒ピッチ 3 種・Zenn タイトル 5 本・Show HN 本文は評議会成果物に完成品あり。**Show HN 本文は「最近縁は Polymer iron（終了済み）」の一文を georapbox 名指しに差し替えた版を使うこと**（監査 M2）。

**買い手①向けピッチ素材（R3 追加）**: 「**全面的な SPA 化はしたくないが、非同期処理だけ現代化したい**」— 評議会レッドチーム（買い手）の結論「配線層の自然な買い手は FW を持っていない・入れたくない人」を買い手自身の言葉に translate した一文。LP・記事③（Qiita 業務系）・0-5 節で使う。

### 2-4. 商品の説明構造 — 4 層モデル + Land and Expand（R3 統合）

R2 は施策リスト（Tier 表）であり「商品を一枚で説明する構造」を欠いていた。統合戦略案から以下を採用し、LP・README・登壇資料の**説明順序の規範**とする。

**4 層モデル**:

1. **Bindable I/O Nodes** — 1 タグから入れる Web API ラッパー群（入口。0-5「Add one tag」がここ）
2. **Wiring / Composition** — タグ 2 個以上を data-wcs 1 行で JS ゼロ配線（**中核差別化**。§2-2 条件 2 の実体。「複数ノードが組み合わさった瞬間に、便利タグ集からアプリケーション基盤に変わる」）
3. **Framework Interoperability** — 同じタグが React/Vue 等からも動く（**主戦場ではなく技術的証明**。買い手③の縮小位置づけを維持し、ここを核に昇格させない — synthesis-review IC-1）
4. **HTML-first Application Stack** — state / router / SSR まで拡張可能。**state と router は「格下げ」ではなく「このエコシステムを最も直接に使える純正ホスト」と語る**（レッドチーム S5「堀を裏に回す」問題への言語面の回答）

LP の語り順は **Compose → Reuse → Verify → Expand**（配線できる → FW 横断でも使える → lint/DevTools で検証できる → state/router/SSR へ拡張できる）。**Reuse を先頭に置かないこと** — 買い手①（FW 不在層）には存在しない痛みの訴求になる。

**Land and Expand 5 段階**（ドキュメント導線・記事末尾 CTA・デモ並び順の設計基準）: ①1 ノード使う → ②2 ノード以上を配線する（**ここで初めて固有価値を体験させる**） → ③複数画面・複数プロジェクトで同じノードを再利用 → ④必要なら state/router へ拡大 → ⑤独自ノード化。①→②の導線を LP・README・各記事の末尾に必ず張る。⑤は現時点で能動的に追わない（§7 の新規ノード凍結・エコシステム偽装禁止と整合。外部ユーザー >0 が前提）。

**一文戦略（対内の羅針盤・対外コピーではない）**: 「wcstack を新しいフロントエンドフレームワークとして売るのではなく、Web API を共通プロトコルで HTML ノード化し、複数ノードを配線・合成し、複数フレームワークからも共有できる『ブラウザ I/O エコシステム』として普及させる。単一ノードから導入させ、合成・再利用・state/router/SSR へ段階的に拡張する。AI は顧客ではなく、これを発見・生成・検証する流通チャネルとして組み込む。」

## 3. 買い手の再定義（優先順）

**構造の修正: 「買い手（人間）」と「チャネル」を分離する。AI は買い手リストから外す。**

1. **FW 不在ページ層** — サーバーレンダリング（Rails/Django/Laravel/PHP/CMS テーマ）＋「ちょい動的」層（htmx/Alpine 隣接）、および**社内ダッシュボード / キオスク / サイネージ**。実証済み市場（Alpine は 37 万サイト）・固有クエリあり・競合フック集不在・「タグ 1 個」が文字通り成立する唯一の環境。htmx はサーバ通信、Alpine は UI 状態で、**デバイス/ブラウザ API（camera/geo/ws/wakelock/…）は両者の空白＝競合ではなく補完で入れる**。キオスク系は wakelock/fullscreen/idle/network/sse/timer が「用品一式」になる。前提条件: LP/README の SPA 文脈をこの層向けに書き分けること・CDN 遮断環境向けに単一ファイル自己ホスト導線を明記すること。
2. **脱 jQuery 保守（日本）** — 初版の「日本の業務系」をこの細分に縮小。SIer の組織調達は bus factor 1 で審査落ちするため追わない。「jQuery を剥がしたいがビルドは入れられない保守案件」は業務系で唯一クエリが立つ細分市場（Zenn/Qiita 漏斗はここにのみ効く）。
3. **既存 React/Vue アプリ持ち** — 廃止しないが降格。競合（VueUse / react-use-websocket 週 38 万 DL）が強く、アダプタは第三者検証ゼロ。位置づけは主戦場ではなく**「複数 FW で同じタグが動く」ことの技術的証明**（デモ 1 本 + 記事 1 本に限定。比較対象は「手書き 200 行」ではなく react-use-websocket と正直に設定する）。

**チャネル横断要件（順位づけしない・全施策に焼き込む）**:
- **③-a AI 実装チャネル（今すぐ）** — 「人間が選定し AI が実装する」経路は新規コードの 26.9〜46% を占める現在形。9 ラン実測の 4/9 脱落は「長期の賭けの不発」ではなく「**買い手①の成約率を今日 44% 失っている**」。担当施策: npm README 最適化・AGENTS.md 配布スニペット・エラーメッセージ内誘導（§4）。
- **③-b AI 自律選定（長期）** — 学習データ収載は施策ではなく人間採用の遅行結果。corpus の種まき（examples・ロングテールページ・対訳ペア型比較記事）のみ。

**追わないリスト（拡張）**: 新規 SPA スタートアップ・欧米エンタープライズ（初版通り）＋ 教育市場・ノーコード脱出口・政府/自治体直販・SIer 組織調達・ブラウザ拡張専用対応（MV3 のリモートコード禁止で CDN の売りが死ぬ。vendoring 1 節のみ）。

## 5. 指標とゲート（再定義）

4 指標（jsDelivr 月間ブラウザヒット / stars / **外部発 issue・discussion** / LP ユニーク訪問）は維持。ただし:

- jsDelivr は**直近 8 週の週次中央値換算**で見る（Zenn バズ 1 回の単発スパイクと分離）。
- 中間マイルストーン: **90 日で月 500 相当**。

**合成指標（R3 追加・質的な最重要観測）**: 「**2 個以上の I/O ノードを配線している外部利用例**」の件数。1 タグ採用は「便利な Web Component の採用」、2 ノード以上の配線は「プロトコル思想の採用」であり、中核仮説「統一プロトコルが ~50 stars の天井を破る」を直接検証できる唯一の指標（4 指標はいずれも到達量であって仮説を測らない）。テレメトリでは測れないため**事例ベース**で観測する: 受け皿（0-8）への自己申告導線（issue テンプレに「使っている構成（タグ・組み合わせ）」欄を設ける）+ `metrics.mjs` に GitHub code search（`data-wcs` 使用の公開リポジトリ）の四半期スナップショットを追加。**ゲートの合否条件には入れない** — 観測面が受け皿依存で立ち上がるまで「起きていない」と「起きたが不可視」を区別できないため。ベット別反証条件の解釈材料として使う。

### 二層ゲート（初版の単層 6 ヶ月ゲートを置換）

1. **実行ゲート（2026-10-01）**: Tier 0 全消化 + jsfb 提出 + 記事 2 本公開。未達なら測っているのは「売り込みの失敗」ではなく「未実行」であり、成果ゲートは発動しない（先に実行計画を見直す）。
2. **成果ゲート（2027-02-01）**: 実行ゲート通過済みを前提に、外部発 issue が 1 件も立たず、かつ jsDelivr 週次中央値換算で月 1,000 未満なら、**「能動的売り込み」（記事・CFP・登録営業）のみ停止**して工芸ゲームに全振りする。**常設面（LP・npm README・カタログ掲載・jsfb 掲載・デモ）は撤退後も複利で働く資産であり撤去しない。** 事例研究の中央値（無風期間 2〜6 年: htmx 前身 6 年・Shoelace 5 年）に照らし、このゲートは「プロジェクト/カテゴリ価値の判定」ではないことを明文で固定する——そうしないとゲート発動自体が燃え尽きの引き金になる。

### ベット別反証条件（ゲートに追加）

- **配線層**: デモホスト + npm README 最適化後、jsDelivr ヒットの伸びが I/O タグでなく state/signals に集中したら、配線層フレーミングを逆転させる（signals 旗艦・I/O はエコシステム）。逆に**合成事例（2 ノード以上）の 0→1 が観測されたら配線層仮説の最初の実証**とし、Tier 3 発射判断の材料に加える。
- **jsfb**: 提出後 Chrome 2 バージョン分の公式ランで referral 流入・star・外部 issue に計測可能な変化がなければ「発見装置」期待を正式破棄し、以後は引用素材としてのみ扱う。維持コストが月 1 時間を超えたらアーカイブ受容。
- **日本チャネル**: 記事 5 本の型別 LP 転換率で、継続する記事型を 1 本に絞る（90 日時点）。

証跡は `scripts/metrics.mjs` の週次スナップショットで自動化（手動巡回をやめる）。
