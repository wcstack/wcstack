## 0. 一言で

4.x で極めるのは、エンジンの速さでも小ささでもなく、**パッケージ同士の継ぎ目の予測可能性** — 作者の意図どおりに動くか、そうでなければ必ず何かが知らせること。

## 1. 現状

| 項目 | 事実（2026-10-17） | 読み |
|---|---|---|
| エンジン | js-framework-benchmark の CPU の加重幾何平均 1.07（vanillajs 1.02・signals 1.22・3.5.4 1.44）。`core.min.js` 19,944 B（上限 20,480 B まで 536 B）。開いている Issue は #365・#401 の 2 件で、どちらも F26 の系統（[移行ガイド §5](./migration-v4.ja.md#5-既知の制限)） | 速さはほぼ天井。サイズは守るもので、伸ばすものではない |

| 外との接点 | GitHub の star 6・fork 0、外部の作者の Issue は過去 0 件、直近 2 週間の訪問 20 人。"wcstack web components framework" と "@wcstack/state" の検索はどちらも該当なし。npm の月間 DL は主要パッケージがどれも 4〜5 千でほぼ同じ | DL の一様さはミラーや自動取得と見るのが妥当（推測）。今の「初めての作者」はサブエージェントだけ |

## 2. なぜ継ぎ目か

- 3.x → 4.0 はパッケージの**中**（エンジン）を作り直した。その成果は 1.07 と 20 KiB に出ていて、残りの伸びしろは小さい。
- 4.0 の後の欠陥は、すべてパッケージの**間**（state × storage、state × fetch、router × レイアウト、signals × router）か、時間の経過（再読み込み、2 回目、ディープリンク）の後に出て、ほとんどが無言だった（[seam-apps.ja.md](./seam-apps.ja.md) の「なぜ」）。
- 継ぎ目はプロトコル（wc-bindable・command-token・event-token・binder・transition-runner）が支える場所で、エンジンを書き直しても残る資産でもある。

## 3. 4.x で極めること

### 3.1 沈黙をゼロにする — 誤りの目録

- 継ぎ目アプリの手順 5「よくある間違いをわざとする」を、アプリごとの使い捨てから常設の目録にする。項目ごとに「誤り → 何が知らせるか → 根拠」を持つ。正本は [mistake-catalogue.ja.md](./mistake-catalogue.ja.md)。
- 知らせる層の序列: **設計で消す ＞ 実行時に知らせる ＞ lint ＞ 文書**。lint だけが知らせるものは「条件付きの沈黙」として数える。
- 指標: 目録の項目数と、そのうち無言（文書だけ）の数・lint だけの数。サイズのゲートと同じく、数字で追う。

### 3.2 継ぎ目アプリを制度にする

- 最初の 4 本（router-auth・router-admin・state-collab-board・signals-shop。修正は 4.1）で 79 件の引っかかりが見つかった。今いちばん効く発見の手段である。
- 方法は [seam-apps.ja.md](./seam-apps.ja.md) のとおり。発見はそこの記録と目録の両方に入れる。

#### 1 巡目（2026-10-17 の候補。済み）

2026-10-17 に挙げた 4 つの継ぎ目は、4.3〜4.7 で 1 本ずつ越えた。どれも e2e の spec と一緒に `examples/` にある。

| 継ぎ目 | アプリ | 引っかかり | わざとした間違い（何も知らせなかった数） | 公開 |
|---|---|---|---|---|
| **SSR × router × state** — `@wcstack/server` のハイドレーション、版の門と `legacy()` | ssr-news | 27 | 12（9） | 4.3.0（残りは 4.4.0） |
| **デバイス系の I/O × 権限** — camera / recorder × upload、audio / midi。拒否・取り消し・タブが裏に回る | state-field-report | 18 | 15（12） | 4.5.0 |
| **フレームワークの中の `wcs-*`** — React / Vue から wc-bindable のアダプター越しに | fw-inventory | 14 | 19（12） | 4.6.0 |
| **本番の形** — 版の固定・SRI・厳しい CSP・分割エントリ | prod-booking | 29 | 40（配信の 20 件のうち、lint が知らせたのは 3 件） | 4.7.0 |

収穫は減っていない。最後の 1 本がいちばん多く、重さも落ちていない（prod-booking: 名前空間の外のタグ 1 つで autoloader がページの部品をすべて読まなくなる、どのブラウザでもページの読み直しが効かない）。`examples/` への取り込みでも、毎回もう 1 件見つかった。4 つの継ぎ目は 10-17 に思いついた候補で、継ぎ目が尽きた証拠ではない。

#### 2 巡目（2026-10-25、著者 — §5.6）

1 巡目が通っていない軸から選ぶ。すでに作った形のアプリを重ねても、見つかるものは減る（seam-apps の「わざと継ぎ目を越える」）。上から順に:

1. **長く開いたままのタブ** — 1 巡目の生活の出来事は、どれも数秒から数分だった。シフトの間や夜通し開いたままのページが通るもの: スリープからの復帰、隠れたタブのタイマーの間引き、ページの凍結と再開（Page Lifecycle）、bfcache からの復帰、破棄されたタブの復元、タブの複製、日付の変わり目と夏時間、トークンの期限、SSE / WS の再接続、伸び続ける一覧とメモリ。どのパッケージの README も bfcache・凍結・破棄に触れず、`<wcs-timer>` の README は隠れたタブとスリープに触れない。§3.4 のメモリとも重なる。
2. **スキルだけで書く作者** — 1 巡目の作者は公開文書をすべて読めた。実際の初めての作者（AI）はスキルを入口にし、lint を回さない（2026-07 の計測で 9 回中 0 回）。スキル × リリース（スキルがまだ知らない機能や規則）と、スキルが言わないことを通る。作者を変える回なので、作者のモデルも変える。
3. **アクセシビリティと言語** — ルートの遷移の後のフォーカス × router、`<wcs-view-transition>` × `prefers-reduced-motion`、ライブリージョン × 一覧の更新、ロケールの切り替え × 日付・通貨のフィルタ、`<html lang>`。目録の未確認の候補にもある。
4. **古いアプリの更新** — 4.0〜4.2 で書いたアプリ（警告と lint の規則が今より少なかった）を最新の minor へ上げる。増えた警告と lint の error がどう届くか、移行の文書が足りるか。確定申告ツールの評価が 3.x → 4.0 で見つけた型（未採用の入力の喪失）の、4.x の中での版。
5. **audio / midi** — 1 巡目のデバイス系に挙げたが、state-field-report は通らなかった。使う人が少ないので最後。

- 1 巡目のアプリが残した未決（レイアウトのルートの採用、`unsupported` の理由、一度失敗した部品を読み直さない autoloader）は、筋書きがそこを通る 2 巡目のアプリで確かめ直す。
- **1 本につき変える軸は 1 つ** — 継ぎ目か作者か。1 巡目の作者はすべて同じ系統のモデルのサブエージェントで、盲点が相関しうる。2 巡目の 1 本目は継ぎ目（時間）だけを変え、2 本目で作者を変える。両方を一度に変えると、発見がどちらから来たか分からない。

#### 止める目安（2026-10-25、著者 — §5.6）

2 本続けて次のどちらかになったら、継ぎ目アプリを止め、5.0 の議題（§3.3 の (a)）の準備に移る:

- 目録の harm が `data-loss`・`broken`・`wrong-place` に当たる実行時の欠陥が出ない。
- 新しい種類の発見（目録の既存の項目の言い換えではないもの）が出ない。

### 3.3 足さずに直す — 罠の目録を 5.0 の議題にする

- 目録の罠のうち lint か文書でしか知らせていないものを、3 つに分ける: (a) 既定や振る舞いを変えれば消える、(b) 実行時に知らせられる、(c) 静的にしか見えない。
- (a) の多くは正しいページにも影響する（破壊的）。4.x では入れずに目録に記録し、**5.0 の議題はエンジンの書き直しではなく、この (a) から作る**。互換を壊さない (a) は 4.x で入れてよい。
- (b) は 4.x で入れる。`@wcstack/state` の core は残り 536 B なので、原則として diagnostics の後付けに置く。
- 表面積（README の行数・lint の code の数・公開 API の数）は上限を設けず、リリースごとに増えた分を記録する。

### 3.4 最後の既知の穴を閉じる

- **F26（#365・#401）** — 同じオブジェクトが 2 か所にある形。唯一の既知の制限。core の残り 536 B と相談になる。
- **`data-wcs-ignore`（R10）** — CSTI への備え。4.x で足すと決めてあり、足すのは互換を壊さない。
- **メモリ** — js-framework-benchmark のメモリの幾何平均は 4.0 1.95・signals 1.41・3.5.4 4.40。測った軸で 4.0 が最良でないのはここだけ。
- **wc-bindable の applier profile** — 自分のプロトコルの A2（値の後の `undefined` を書く）と A3（完了を呼び手に返す）を、state は名乗っていない。名乗らないまま確定させるか、追いつくかを 4.x の間に決める。

## 4. 進め方

- **リリースの単位**: minor 1 回につき継ぎ目アプリ 1 本（1 巡目、4.3〜4.7）。patch はデータ損失と退行だけ。1 回のリリースごとに npm・provenance・SRI・拡張・skill・サイトを確かめるので、週に 8 回の頻度は続かない。
- **2 巡目のペース**（2026-10-25、著者 — §5.6）: 1 巡目と同じく、継ぎ目アプリ 1 本の修正がそろったら minor を出し、待たない。1 巡目の終わりの 8 日（10-18〜10-25）で 7 回リリースした（minor 5・patch 2）が、どの回も全数を確かめた（4.5.0 は push の失敗を手で直してから）。上の「続かない」は検証の手間を理由にしていたが、その手順は回るようになった。利用者がほぼいない今（§1）はリリースの速さの費用が小さく、発見を早く取り込むほうが品質に効く。確定申告ツールの評価が挙げたリリースの速さの費用は、外の作者が現れたら（外部の Issue、star や訪問の伸び）見直す。patch の規則は変えない。
- **core の予算**（2026-10-25、著者 — §5.6）: `core.min.js` は 20,163 B（4.7.0）で、上限まで 317 B。4.3〜4.7 の 5 回の minor で 219 B 使った（19,944 → 20,163 B）。2 巡目の修正は、原則として後付け（diagnostics ほか）に置く。core でしか直せないものは 1 件ごとにバイト数を添えて著者が決め、収まらないものは 5.0 の議題に回す。
- **4.3 の始め**: 目録の骨組みと、lint だけで拾っている検出の棚卸し（[mistake-catalogue.ja.md](./mistake-catalogue.ja.md)）。続けて、3.4 の F26 と `data-wcs-ignore`。継ぎ目アプリは SSR から。
- **4.x の完成の定義**（目安）:
  - 目録の無言の項目が 0（すべてが設計・実行時・lint のどれかで知らせる、または 5.0 の議題として記録されている）
  - §3.2 の 1 巡目の継ぎ目すべてに、意図を確かめる e2e 付きの継ぎ目アプリがある（2026-10-25 に満たした）。2 巡目は §3.2 の止める目安まで続ける
  - 既知の制限が 0
  - `core.min.js` が 20 KiB 以下のまま

## 5. 決めたこと（2026-10-17、著者）

1. 4.x の主題を「沈黙ゼロ（継ぎ目の予測可能性）」にする。
2. 5.0 の議題を、罠の目録の (a) から作る。
3. リリースの単位を「継ぎ目アプリ 1 本で minor 1 回」に寄せる。

### 5.1 ssr-news から決めたこと（2026-10-18、著者）

最初の継ぎ目アプリ（[seam-apps.ja.md](./seam-apps.ja.md) の ssr-news）が残した設計の問い。6 つとも推奨の案に決めた。

1. **束縛が始めた要求をサーバーが待つ。** 状態から `url` を受ける `<wcs-fetch>` の要求も、描画の時間切れ（`timeoutMs`）の範囲で待つ。待たないと「Loading…」が黙って配られる。
2. **`@wcstack/server` は `@wcstack/state` にちょうどの版で依存する。** 全パッケージを同時にリリースするので失うものは無い。描画するエンジンが server の版で決まる。
3. **`<wcs-state src>` をサーバーで描けるようにする。** `renderToString` に、`src` の URL をローカルのファイルへ解決する選択肢を足す（厳しい CSP の下で文書が勧める形）。
4. **ハイドレーションの前に入力した文字を勝たせる。** 採用のとき、フォーム部品の今の値がマークアップの既定値と違えば、状態から書かずに、その値を状態へ書き戻す。
5. **README の未リリースの機能は「4.3 から（未リリース）」と書き、リリースで「（未リリース）」を外す。** main の README は npm の `latest` より先に進むので、読者が版を見分けられるようにする。
6. **実行できない I/O コマンド**（状態が整っていないために拒んだもの: 未接続の `<wcs-ws>` の `send`、チャンネルの無い `<wcs-broadcast>` の `post`、worker の無い `<wcs-worker>` の `post`、ストリームの無い recorder の `start`）**は、1 要素につき 1 回 `console.warn` する**（`[wcs/command-not-ready]`）。（2026-10-25 に「不調 1 回につき 1 回」へ改めた — §5.7 の 3。）`error` の出力にも従来どおり流す。環境に API が無いもの（unsupported）は `supported` で検出する設計なので含めない。比べた案: `error` だけのまま＋lint、拒むたびに警告、貯めて整ったら送る（遅れて届く方が危ない送信がある）。

### 5.2 7GUIs の評価から決めたこと（2026-10-18、著者）

外部の評価（AI の作者が 7GUIs の 7 課題を 4.2.0 で作り、誤りを 34 件わざと入れた。何も知らせなかったのが 10 件）が残した設計の問い。3 つとも推奨の案に決めた。確実に直せるものは先に入れた: 外部 state（`src=`）へのスクリプトの規則、lint の規則 3 つと拡張 3 つ、`$postUpdate` のパスと宣言に無いキーへの書き込みの警告（PR #484〜#486）。

1. **購読者のいないコマンドの emit は、トークンごとに 1 回 `console.warn` する**（`[wcs/command-token-unbound]`、diagnostics の後付け）。要素の定義が遅れる間（autoloader、遅い CDN — Timer）、同じ更新で描かれる `if:` の枝の受け手（Cells）、受け手の無いトークンが、どれも黙って消えていた。隠れた枝へわざと emit する書き方にも 1 回は出る。比べた案: 一度も購読者を持たなかったトークンだけ（枝の描き直しを取りこぼす）、lint と DevTools のまま。貯めて後で送る案は §5.1 の 6 と同じ理由で採らない。
2. **委譲されたハンドラが throw したとき、そのハンドラのソースが `currentTarget` を含めば、ハンドラごとに 1 回 `#direct` を案内する**（`[wcs/delegated-current-target]`）。core に失敗を後付けへ渡すフックを 1 つ足す（33 B）。throw しない形（`currentTarget.value` が `undefined`）は黙ったままで、ハンドラの間だけ `currentTarget` を要素にする案は 5.0 の議題のまま。
3. **`$postUpdate` の「すべての行」の形は足さない。** `*` は getter と同じく今の行を指すと README に書き、目録で 5.0 の議題にした（`$getAll` の `[]` に当たる形を足すか、行の文脈が解決しない `*` を拒むか）。

### 5.3 state-field-report から決めたこと（2026-10-19、著者）

§3.2 の 2 本目の継ぎ目アプリ（デバイス系の I/O × 権限。[seam-apps.ja.md](./seam-apps.ja.md) の state-field-report）が残した設計の問い。3 つとも推奨の案に決めた。

1. **録画中に `<wcs-recorder>` が文書から外れたら、撮った分をクリップにして渡す。** 何も言わずに捨てていた。権限の取り消しでトラックが終わったときと同じく、止めて `recorded` で渡し、`recording: false` を知らせる。比べた案: 捨てて 1 回警告する。
2. **このページで使えない機能（安全でない origin・Permissions-Policy）は、見張り役も取りに行く側の `permission` も `unsupported` にそろえ、`errorInfo` は理由付きの `capability-missing` にする。** Chromium の Permissions API はポリシーで切られたフレームで `granted`、安全でない origin で `denied` を返し、利用者の拒否と区別できなかった。`denied` は「サイトの設定で変えられる拒否」だけになる。値は増やさない。比べた案: 5 つ目の値（`blocked`）と新しい code を足す、文書だけ。
3. **切断は、変える state の出力をすべてその場で知らせ、打ち切る操作は終わったと知らせる — I/O ノードのファミリー全体の規則にする**（[timing-and-firing-contract.ja.md](./timing-and-firing-contract.ja.md) §22）。router は離れたルートのノードを束縛ごと戻すので、無言のリセット（`speaking`・`listening`）や世代の守りが捨てた完了（`loading`・`connected`）は、戻った後も state の中で古いままだった。洗うと 13 パッケージにあった。§13.4 の「無音のリセット」は「戻して知らせる」に変わる。比べた案: 見つかった camera と recorder だけ直し、残りは目録に記録する。

### 5.4 fw-inventory から決めたこと（2026-10-20、著者）

§3.2 の 3 本目の継ぎ目アプリ（フレームワークの中の `wcs-*`。[seam-apps.ja.md](./seam-apps.ja.md) の fw-inventory）が残した設計の問い。3 つとも推奨の案に決めた。アダプター（`@wc-bindable/react` / `vue`）の側の発見は、提案の文書を添えた issue として @wc-bindable のリポジトリへ出す。

1. **`<wcs-storage>` に `key` の別名 `storage-key`（プロパティは `storageKey`）を足す。** React と Vue は `key` を自分のものとして取り、要素に渡さない。README 自身の両方の例が、key の無い要素になっていた。`key` は残し（互換を壊さない）、両方書いたときは `key` が勝つ。5.0 で `key` を外すかは誤りの目録の議題。比べた案: 文書だけ（ref で `el.key` を代入する）。
2. **自動送信の `<wcs-upload>` は、url より先に来たファイルを、url が来たときに送る。** React 19 は props を書いた順に、要素を文書に入れる前に当てるので、`files={files} url=…` は送られなかった。`trigger` の順（`url` の後に書く）は警告のまま。比べた案: 挙動は変えず、警告の文を JSX の props の順にも当てはまる形に書き直す。
3. **型は `/auto` のものだけ今出す。** どの `/auto` にも `dist/auto.d.ts`（`export {};`）を出し、統合の手引きが勧める遅い読み込み `import("@wcstack/<pkg>/auto")` を型検査に通す。タグの JSX 宣言（`IntrinsicElements`）は、属性・プロパティ・イベントをどこまで表すかの設計が要るので記録に残し、手引きが手書きの宣言を示す。比べた案: JSX の型も今出す（`wcBindable` から React / Vue 向けに生成する。大きい）、どちらも記録だけ。

### 5.5 prod-booking から決めたこと（2026-10-25、著者）

§3.2 の 4 本目で最後の継ぎ目アプリ（本番の形。[seam-apps.ja.md](./seam-apps.ja.md) の prod-booking）が残した設計の問い。5 つとも推奨の案に決めた。確実に直せるもの（router の読み直し・`<wcs-head>`、autoloader の名前空間の外のタグ、lint の 2 件、文書）は先に入れた。

1. **エンジンが報告するエラーは `reportError()` を通す。** 初期化の失敗、`$errorCallback` が受けないバインディングの失敗、ページの getter・フィルタ・ハンドラ・コールバック・`$watch`・トークンの購読者の throw、打ち切った更新のループ。ページのエラーハンドラ（`window.onerror`）が受け取り、コンソールにも 1 回出る。エンジンの文面に元のエラーを続け、元のエラーは `cause`。`reportError()` の無い環境（happy-dom・Node・`@wcstack/server`）では従来どおり `console.error`。本番では `diagnostics` を外すのが自然なので、届く文面は番号と値になる — それで足りる（[state-errors](./state-errors.md) で引ける）。比べた案: 要素からイベントを出す、文書に手順を書くだけ。
2. **別のエンジンのコピーのアドオンは `installFeatures` が拒む**（`[wcs/feature-foreign]`）。どのアドオンも自分のビルドの `hooks` を持ち、core が自分のものか比べる。混ざったアドオンは決して動かないので、警告で済ませる理由が無い。1 と合わせて core に 61 B（20,163 B、残り 317 B）。
3. **日付の族（`date`・`time`・`datetime`・`ymd`・`hms`）は値が無いとき素通しする。** 後から届く日付は、届くまで何も描かない。別の型は今も拒む。formats の後付けの中の変更で、壊れるページは無い。
4. **リリースの `sri.json` とリリースノートが、分割エントリのすべてのファイルのダイジェストと import map のブロックを載せる。** 一覧を手で書くと、別のビルドの名前が混ざっても何も言わずに何も守らない。比べた案: 文書に「tarball から算出する」と書くだけ。
5. **module のスクリプトの無い `<wcs-guard-handler>` は閉じる側に倒す**: 読み込めなかったハンドラと同じく、ルートへのナビゲーションはすべて guard のパスへ。`guard` 属性の無いルートも同じ（「ハンドラはそれ自体で guard を有効にする」という既存の規則と一貫させた。以前は守らずに開けた — バンドラがスクリプトを取り去ると、守るページが見えた）。比べた案: 文面だけ直す。

### 5.6 2 巡目について決めたこと（2026-10-25、著者）

1 巡目の 4 本を終えた時点で、著者が「毎回新しい発見が複数あるので続けたい」とした。その続け方として 5 つを決めた。2 は推奨と違う案に、ほかは推奨の案に決めた。

1. **2 巡目の候補と順** — 長く開いたままのタブ → スキルだけで書く作者 → アクセシビリティと言語 → 古いアプリの更新 → audio / midi（§3.2）。比べた案: 1 巡目の継ぎ目を別の題材で深める（同じ形を重ねるので収穫が減る）。
2. **リリースの単位** — 1 巡目と同じく 1 本で minor 1 回、修正がそろったらすぐ出す（§4）。利用者がほぼいない今は、速く回して取り込むほうが品質に効く。外の作者が現れたら見直す。比べた案: minor をおよそ 2 週間に 1 回にする（推奨として出した案。リリースの速さが利用者の費用になる前提だった）、本数で区切る（2 本で 1 回）。
3. **core の予算** — 修正は原則として後付けに置き、core の変更は 1 件ごとに決める（§4）。比べた案: 予算を決めず、尽きたときに考える（尽きる直前の 1 件が、要るかどうかではなく順番で決まる）。
4. **止める目安** — 2 本続けて重い実行時の欠陥が出ないか、新しい種類の発見が出ない（§3.2）。比べた案: 本数で決める、決めない。
5. **1 本につき変える軸は 1 つ** — 継ぎ目か作者か（§3.2）。

### 5.7 shift-desk から決めたこと（2026-10-25、著者）

2 巡目の 1 本目の継ぎ目アプリ（長く開いたままのタブ。[seam-apps.ja.md](./seam-apps.ja.md) の shift-desk）が残した設計の問い。5 つとも推奨の案に決めた。確実に直せるもの（`<wcs-head>` のノードの漏れ、lint の 2 件、文書）は先に入れた。

1. **閉じられずに死んだ接続には、任意の `stale-after` で気づく**（`<wcs-sse>`・`<wcs-ws>`）。開いている間にその時間何も届かなければ、失われたとみなして `connected: false` と理由を知らせ、開き直す（ws は `auto-reconnect` の規則で）。比べた案: 文書に見張りの作法を書くだけ。既定で見張るのは、すべてのサーバーに定期的な送信を求めるので 5.0 の問いとして目録に置いた。
2. **`<wcs-ws>` は back/forward cache のために自分で閉じて開き直す**: `persisted` の `pagehide` で閉じて終わりをその場で知らせ、`persisted` の `pageshow` で、接続していたならつなぎ直す。比べた案: 文書だけ（ページが閉じると、閉じた知らせが復元の後に届いた）。`<wcs-sse>` は変えない（SSE だけのページは復元され、ストリームも続いた）。
3. **`[wcs/command-not-ready]` は不調 1 回につき 1 回**: 要素がまた整ったら（接続した・開いた・起動した・キーがある・許可された…）言い直す。§5.1 の 6 の「1 要素につき 1 回」は、一日中生きるルートの要素ではページの寿命で 1 回だった。比べた案: 今のまま README に「ページの寿命で 1 回」と書く、一定時間ごと。ページのコードの誤りを言う警告（`[wcs/input-as-attribute]` ほか）は要素ごとに 1 回のまま。
4. **接続時の仕事は、1 つのマイクロタスクで、そのときの入力で決める — I/O ノードのファミリーの規則**（[timing-and-firing-contract.ja.md](./timing-and-firing-contract.ja.md) §23）。router が入れ直すルートの同じノードは、state が次のルートの入力を書く前に接続する。17 パッケージ。同じタスクで結果を使う最初の接続（storage・broadcast・worker）はその場のまま、明示のコマンドは判断を引き取る。比べた案: 外に見える ws と storage だけ直す。
5. **ページの可視性は、出力にせず作法を書く**（[long-lived-pages.ja.md](./long-lived-pages.ja.md)）。state-field-report に続いて 2 本目の要望で、§6 の「新しい I/O のパッケージを増やさない」に従い、3 本目の要望で Page Lifecycle と Page Visibility のノードを見直す。

### 5.8 family-ledger から決めたこと（2026-10-27、著者）

2 巡目の 2 本目の継ぎ目アプリ（スキルだけで書く作者。[seam-apps.ja.md](./seam-apps.ja.md) の family-ledger）が残した設計の問い。4 つとも推奨の案に決めた。確実に直せるもの（lint の 3 件、診断の文面の 2 件、fetch の文書、testing の `mount()`）は先に入れた。§3.2 の止める目安には当たらない: 重い実行時の欠陥（`leaveConfirm` の真偽値、ルートが 2 つの `<wcs-state>`）が出て、新しい種類の発見（スキルと lint の食い違い、作者の道具の穴）もあった。

1. **`<wcs-upload>` は子要素 `<wcs-upload-header name value>` でヘッダを送る**（`<wcs-fetch-header>` と同じ形）。アップロードを始めるときに読むので、state から束ねたトークンはそのときの値で出る。比べた案: `headers` 入力（オブジェクト。タグは増えないが fetch と形が違う）、文書だけ（`UploadCore` を使う）。
2. **`leaveConfirm` は真偽値も受ける: `true` は英語の既定の文言で聞き、`false` は聞かない。** ページの言語で聞くなら文字列を束ねる。比べた案: 真偽値は聞かずに 1 回警告する（汚れたフォームが確認なしに離れうる）、聞いたうえで 1 回警告する。
3. **ルートの `<wcs-state>` が 2 つあるときは、診断の後付けが両方を名指す**（`[wcs/second-root]`）。どちらがルートを取るか（状態が先にそろった方）は変えず、core は 0 B。比べた案: core で文書の順に決める（数十 B。README が言っていたとおりになる）、両方。
4. **`<wcs-sse>` に `auto-reconnect` / `reconnect-interval` / `max-reconnects` を足す**（`<wcs-ws>` と同じ名前と意味、opt-in）。ブラウザが諦めたストリームだけを、試すときの `url` で開き直す。継ぎ目アプリ 3 本が同じタイマーを自前で書いていた。比べた案: 文書の作法のまま。

## 6. やらないこと

- 新しい I/O ノードのパッケージを増やすこと（量産の候補は尽き、パッケージ数は KPI にしない — [go-to-market-2026-08.md](./go-to-market-2026-08.md) §7）。
- 速さの追い込み（CPU は vanillajs と 5 % の差）。
- `data-wcs` への式の追加（配線であって DSL ではない）。
- 4.x の中での破壊的変更（49 のパッケージが同じ版で動くので、major の費用は大きい）。
- 普及のための施策（目的関数は工芸）。ただし、予測可能性を最後に判断するのは自分以外の作者で、人の目に触れる経路が無い状態（検索の該当なし）は、これとは別に判断する価値がある。
