# @wcstack/lint

> 🤖 **AI coding agents**: This README is a package-level reference, not the primary entry point for building a wcstack application. If you have not already done so, first read the repository [README](https://github.com/wcstack/wcstack#readme) and [AGENTS.md](https://github.com/wcstack/wcstack/blob/main/AGENTS.md), then use the [wcstack-app skill](https://github.com/wcstack/wcstack-skill).

Static-contract validator CLI for [wcstack](https://github.com/wcstack/wcstack): checks HTML `data-wcs` bindings and `wcstack.manifest.json` sidecars headlessly, with the **same validator core** as the WcStack IntelliSense VS Code extension — the IDE and this CLI report identical diagnostic codes and ranges.

[日本語版 README はこちら](./README.ja.md)

## Usage

No install required:

```bash
npx @wcstack/lint --errors-only index.html wcstack.manifest.json
```

Or install and use the `wcs-validate` command:

```bash
npm i -D @wcstack/lint
npx wcs-validate --errors-only src/**/*.html
```

Since 4.20, the CLI expands a pattern itself when the shell has not: an argument that names no existing file and holds `*`, `**`, `?`, `[…]` or `{a,b}` is matched against the files, as a shell does — `*` stays in one directory and skips names that start with `.`; `**` crosses directories, but not `node_modules` or one whose name starts with `.`. cmd.exe and PowerShell pass a pattern through as it is, and npm runs a package's scripts with cmd.exe on Windows, so up to 4.19 `wcs-validate templates/*.html` in an npm script failed there with `cannot read templates/*.html`. A pattern that matches no file is an error (`no file matches <pattern>`, exit code `2`). Quote the pattern (`"src/**/*.html"`) to have the CLI expand it on every shell: a POSIX shell without `globstar` reads `**` as `*`.

Files ending in `.manifest.json` are validated as sidecar manifests; everything else is validated as HTML with `data-wcs` bindings, except a framework's components and script files (`.js`, `.ts`, `.jsx`, `.tsx`, `.vue`, `.svelte`), which are not read (since 4.6; before, they were read as HTML and reported clean).

External state referenced via `<wcs-state src="...">` (`.json` / `.js` / `.ts`) is resolved relative to the HTML file and included in path validation. URLs are never read, and a path from `/` only under `--root` (below), unreadable files are skipped, and unresolved paths stay warnings. Note that once external state *does* resolve, the full validation surface applies to those pages — error-severity findings (e.g. `for:` bound to a non-array) can fail a build that was previously silent because the paths could not be checked. Since 4.4 that includes the script rules (`wcs/nested-assign`, `wcs/array-mutation`, `wcs/on-handler-this`, `wcs/updated-callback-unbound` and the rest) on a `.js` / `.ts` state: a finding in the file is reported in the file (`state.js:12:5 error wcs/nested-assign …`), once however many pages load it, and the IDE shows it on the page's `src` value. Up to 4.3 only the paths of an external state were checked. Since 4.10, a key written as a name — a shorthand (`export default { lang, t }`, the dictionary volume `<wcs-state mount="i18n" src="./i18n/state.js">` of `examples/router-i18n`) or `items: ITEMS` — has the shape of what the name is bound to: a `const` of the module, or an import from a relative path, which is read relative to the file that imports it (and the module it re-exports from) — since 4.17 a member of a namespace import too (`sound: M.DEFAULT_SOUND` with `import * as M from "./lib/music.js"`). Up to 4.9 a shorthand key was not read at all, so every `i18n.t.*` binding was a false `wcs/binding-path-missing`. A name whose value is computed (the dictionary merged from the locale catalogs at run time), or that it cannot follow (a bare specifier, a URL, a file that is not there), leaves the paths under that key unchecked, and says so once at the key when the page binds under it (`wcs/path-dynamic-unknown`, info); a JSDoc `@type {typeof import("./en.js").default}` on the key or on the declaration has them checked against that file's literal.

Since 4.20, `{{ }}` is read as a binding only where the runtime binds it: in text — not in an attribute value (`aria-current="{{ x }}"`) or an HTML comment — and outside the document's `<head>`, which a `<wcs-state>` does not bind (a `{{ }}` or a comment binding there is a `wcs/template-syntax` warning). When the page's state declares `$behavior: { enableMustache: false }`, no `{{ }}` is read as a binding at all — a CMS's or a server template's braces beside an island — while comment bindings are still checked. The setting is read where the state is: inline, `json=`, `state=`, or an `src=` file the lint can read (with `--root` for a path from `/`); a state it cannot read leaves `{{ }}` checked as before. Up to 4.19 each such brace pair was a false `wcs/binding-path-missing` and a FOUC info, and every comment binding printed a `wcs-text binding: …` info, which 4.20 no longer does.

```
wcs-validate [--attr=data-wcs] [--state-tag=wcs-state] [--lang=ja|en] [--root=<dir>] [--errors-only] [--strict] <file> [<file> ...]
```

| Option | Description |
|---|---|
| `--attr=<name>` | Bind attribute name (default `data-wcs`) |
| `--state-tag=<name>` | State custom-element tag name (default `wcs-state`) |
| `--lang=ja\|en` | Diagnostic message language. Defaults to the environment locale (`LC_ALL` / `LC_MESSAGES` / `LANG`, then the OS locale); codes and ranges are language-independent |
| `--root=<dir>` (also `--root <dir>`) | Since 4.10: the site's root directory, where a path from `/` is read — a `<wcs-state src="/app.js">` under `<base href="/ja/">` (the form of `docs/csp.md` and `examples/router-i18n`) and an import from `/…` in a state file are read as `<dir>/app.js`; a path that leaves the directory (`/../x.js`) is not. Without it a path from `/` is not read (`wcs/state-src-unread`, info). A finding in such a file is reported under the directory (`public/app.js:12:5 …`) |
| `--errors-only` (alias `--quiet`) | Print only error-severity lines; warning/info counts and the exit code are unchanged |
| `--strict` | Exit `1` on warning-severity diagnostics too. Severities are unchanged (the IDE shows the same thing); only the exit-code threshold moves from error to warning. The summary line ends with `(strict)`. Use it to fail CI on a path typo (`wcs/binding-path-missing` is a warning) — but resolve every `<wcs-state src>` first (an unresolvable external state leaves warnings that would now fail the build). Combines with `--errors-only`: output stays error-only, the exit code still reflects warnings. Since 4.30 the infos that say a whole state was not read — `wcs/state-src-unread`, and `wcs/path-dynamic-unknown` for a `...spread` at the top of a state — count like warnings too, and are printed with `--errors-only` |

## Output & exit codes

One line per diagnostic, in a stable order:

```
index.html:12:8 warning wcs/path-nonexistent Path "user.nam" does not exist ...
app.manifest.json:1:3 error wcs/manifest-broken Broken manifest JSON: ...

1 error(s), 1 warning(s), 0 info
```

| Exit code | Meaning |
|---|---|
| `0` | No error-severity diagnostics (warnings/info may exist); with `--strict`, no error or warning |
| `1` | At least one error-severity diagnostic; with `--strict`, at least one error or warning |
| `2` | Usage error or unreadable file; since 4.20, also a pattern that matches no file |

After the counts, two notes name the files the counts say nothing about (since 4.6; printed with `--errors-only` too, and they do not change the exit code):

```
0 error(s), 0 warning(s), 0 info
not read: src/App.tsx — wcs-validate reads HTML pages (data-wcs, <wcs-*> tags), not a framework's components or script files
nothing to check: index.html — no data-wcs binding, <wcs-*> tag or wcstack script in them
```

A framework app (React, Vue) that uses the `<wcs-*>` elements has neither: its page holds the root element and its components are not read. Exit code `0` does not mean such an app was checked; [the framework integration guide](../../docs/framework-adapter-integration.md) lists what to look for instead.

Since 4.20, a file with bindings — a `data-wcs` attribute or a comment binding — and no `<wcs-state>` gets one `wcs/state-absent` info, at its first binding: a CMS's partial template, a route's content in a file of its own, or a page whose state a script makes has no state to check the paths against, so they are not checked. Up to 4.19 such a file printed nothing and was not listed under `nothing to check:` either, so it looked checked while a typo (`booking.totl`) passed. Check the page that holds the state, or declare the paths in a `stateSchema` (below), which silences it. A file whose only text bindings are `{{ }}` is not reported (braces alone may be another template engine's).

## Declaring a state contract (`stateSchema`)

Without a contract, a path the validator cannot resolve is only a **warning** (`wcs/binding-path-missing`): `count` may well exist at runtime even when the inline script cannot be read statically. Note that a list starting as `[]` does not need a contract just to name its row fields — the analyzer reads them from the row literals in the assignments that add or replace rows (`this.items = this.items.concat({ id, kind: "general" })`, `.toSpliced(i, n, { … })`, `.with(i, { … })`, `[...this.items, { … }]`); only a row passed as a variable (`concat(row)`) is invisible to it. Since 4.9 it also reads an assignment that rebuilds the rows with `map` — `this.rows = [...this.items].map((c) => ({ id: c.id, label: c.name }))`, `.filter(…).map((c) => { return { … }; })` — the way it reads a getter that does, and the keys of an object literal assigned to a key seeded `{}` (`this.fieldErrors = { date: "…" }` gives `fieldErrors.date`; a spread inside the literal is not followed). Since 4.17 the mapper of `Array.from({ length: n }, (_, i) => ({ … }))` and `Array.from(source, (x) => ({ … }))`, and a `map` after `[...Array(n).keys()]`, give the rows the same way, in a getter and in an assignment; up to 4.16 each binding under such rows was a false `wcs/binding-path-missing`. Since 4.11 a seed that spreads a constant of the module — `draft: { ...EMPTY_DRAFT }` with `const EMPTY_DRAFT = { title: "", body: "" }`, or one imported from a file it reads — has that literal's keys (nested ones too; a later key of the same name wins, as when the object is built), and so does a list seed's first row (`[{ ...ROW, id: 0 }]`); since 4.17 so does a member of a namespace import of a file it reads (`sound: { ...M.DEFAULT_SOUND }` with `import * as M from "./lib/music.js"`), which up to 4.16 left the keys unchecked. Up to 4.10 every binding under such a key was a false `wcs/binding-path-missing`, and a typo (`draft.titel`) the same warning. A spread it cannot read — a call, a `let`, an import it cannot read — leaves the keys under that key unchecked, said once at the key when the page binds under it (`wcs/path-dynamic-unknown`, info). A list that arrives from outside — `null` until `<wcs-fetch>` or `<wcs-storage>` fills it — has no such literal: declare its shape with a JSDoc `@type` before the property (`/** @type {{ id: number, name: string }[] | null} */ catalog: null`), or name the row type with a `@typedef` in the same script and write `@type {Product[] | null}`. A getter whose result it cannot read from the body (`get keyRows() { return buildRows(this.sound); }`) is declared the same way, before the getter: a getter takes `@returns` or `@type` — `/** @returns {{ label: string }[]} */ get keyRows() { … }` — as its result type, as TypeScript does. `@type` counts on a getter since 4.17; up to 4.16 only `@returns` did, and a getter's `@type` was ignored without a word. Since 4.20, an index signature in such a type — `Record<string, T>`, `{ [key: string]: T }`, Closure's `Object<string, T>` — on a getter's `@returns` / `@type` or a key's `@type` leaves the paths under it open, as a `stateSchema`'s open object does: `/** @returns {Record<string, boolean>} */ get soldOut()` with `class.full: soldOut.e12` is not reported, where up to 4.19 each such binding was a false `wcs/binding-path-missing`. `Record<"open" | "closed", T>` has the fields `open` and `closed`. Put an `application` sidecar next to (or above) the HTML and the same typo becomes an **error**:

```json
{
  "schemaVersion": 2,
  "kind": "application",
  "manifestExtensions": {
    "wcstack.application": {
      "version": 2,
      "stateSchema": {
        "type": "object",
        "properties": {
          "count": { "type": "number" },
          "users": { "type": "array", "items": { "type": "object", "properties": { "name": { "type": "string" } } } }
        }
      }
    }
  }
}
```

- **Discovery**: the nearest `wcstack.manifest.json` walking up from the HTML file is used automatically — nothing to pass on the command line. Passing `*.manifest.json` arguments that contain an `application` artifact replaces discovery for the whole run. The VS Code extension discovers the same file, so IDE and CLI agree.
- **Which pages a schema is for** (since 4.26): a manifest that names the state file its schema was generated from — `wcstack.application.stateSource`, relative to the manifest, which `wcs-schema emit` writes — is the contract only of a page whose root `<wcs-state src>` loads that file (`.js` and `.ts`, `.mjs` and `.mts` of one path being one file). A page whose state is inline, or another file, is checked as if there were no manifest, whether the manifest was discovered or passed on the command line. Up to 4.25 the app's schema was applied to every page under it, so a page with its own inline state beside the app got `wcs/path-nonexistent` errors for its correct paths. A manifest without `stateSource` (hand-written, or generated by an earlier `wcs-schema`) applies to every page as before.
- **Effect**: when a `stateSchema` is declared, a bound path that the schema definitely lacks is `wcs/path-nonexistent` (**error**, exit `1`); `for:` on a non-array is `wcs/path-type-mismatch` (**error**). Paths the schema leaves open (a bare `{}`) are checked as they are without a schema — since 4.31; they were silent — and methods / getters / `$listKeys` from the inline script still count as existing. Without a `stateSchema`, behavior is unchanged.
- **When a contract is needed**: a state the validator cannot read in full needs one for its paths to be checked at all. A top-level spread is the common case — `export default { ...defaults(), get total() { … } }` brings in keys no static reader sees, so the validator checks no path of that state, and since 4.4 it says so once, at the spread (`wcs/path-dynamic-unknown`, info). With a `stateSchema` the bindings — and, since 4.4, the paths the getters read (`wcs/read-path-missing`) — are checked against it. A `<wcs-state src>` it cannot read — a path from `/`, a URL, a file that is not there — leaves that state unchecked as well; since 4.7 it says so once, at the attribute (`wcs/state-src-unread`, info), where up to 4.6 it said nothing. It reads a `src` relative to the page: keep the files laid out as on the server, and since 4.10 pass `--root=<dir>` for a path from `/`.
- **Where the schema comes from**: write it by hand (only the JSON-Schema subset `type / properties / required / items / enum / const / anyOf / $defs / $ref` is accepted), or generate it from a TypeScript state file — or a JavaScript one with JSDoc types — with `wcs-schema` (`@wcstack/typescript`). The manifest is a derived artifact — keep it in sync with `wcs-schema check` in CI.

## The page's wcstack scripts and the lint's version

Since 4.11, two findings look at the wcstack scripts a page loads, and since 4.20 a third. Since 4.21, `wcs/tag-package-missing` is an error, so `--errors-only` fails on it too (up to 4.20 it was a warning, which `--errors-only` hid); the other two are warnings: `--strict` fails on them, `--errors-only` does not.

- **`wcs/tag-package-missing`** — a `wcs-*` tag of a wcstack package (`<wcs-upload>`, or its helper `<wcs-upload-header>`; `<wcs-state>`, `<wcs-router>` …) on a page that loads wcstack itself but no script of that package. The element is never defined, its bindings wait and nothing happens, and the console says nothing. Reported once per package, at its first tag, with the `/auto` to load. A script counts when a `<script src>`, an import map entry, or an import or a string in an inline script names `@wcstack/<pkg>` (any version, any CDN, a local path) or the `wcstack` bundle (state, router, fetch, storage, autoloader); a local script (`./app.js`) is read, with the relative modules it imports, for what it names. Not reported on a page that names no wcstack script itself (a fragment, a bundler's page), for a tag an `@components/` import map entry covers while the autoloader is there, or when a local script cannot be read.
- **`wcs/link-router-missing`** (since 4.20) — a `<wcs-link to="/…">` on a page that loads the router (or the `wcstack` bundle) but has no `<wcs-router>`: the link throws `[@wcstack/router] wcs-link is not connected to a router.` when it connects, and stays hidden (`display: none`). On a page without the router — a page a server renders, with islands in it — write `<a href>`, or add the `<wcs-router>`. Reported once per page, at the first such link, where `wcs/tag-package-missing` would look (a page that loads wcstack itself): a fragment — a route's content, a layout file the router page includes — loads no wcstack script and is not reported, nor is a page that names `wcs-router` anywhere outside an HTML comment (a `<wcs-router>`, in a `<template>` too, or a script that makes one), nor a `to` that is a URL or a query (`?page=2`), which renders without the router.
- **`wcs/lint-version-behind`** — a URL on the page pins a newer minor than this lint: `@wcstack/state@4.11.0` checked with `@wcstack/lint@4.10.1`. The lint carries the rules of its own version (it is released with `@wcstack/state`, in lockstep), so it does not check what the newer minor added, and it can report the newer minor's correct syntax as an error (4.2.0's lint gives `wcs/filter-arity` for 4.10's `datetime(ja-JP,short,Asia/Tokyo)`). Said once per page, at the newest pin: upgrade `@wcstack/lint` to that version — keep the lint in `package.json` at the version the page pins. A URL without a version, a major-only pin (`@4`) and a lint newer than the page are not reported.

## What a maintainer fixing a page is told

Since 4.21, from the ledger-repair seam app — a maintainer fixing a household-budget app with ten catalogued mistakes put in, with the console, this lint, the DevTools overlay and the documents:

- **`wcs/submit-without-prevent` and `wcs/tag-package-missing` are errors.** Where they are reported they are always bugs — a form that also submits itself (with the router, a GET that puts the password in the URL), an element that is never defined — and as warnings `--errors-only` hid them. `wcs/binding-path-missing` stays a warning: without a `stateSchema` the value may arrive from outside.
- **`wcs/session-read-at-module-top`** — a `localStorage` / `sessionStorage` / `document.cookie` read at the top level of a `<wcs-guard-handler>`'s module (an error) or of a `<wcs-state>`'s module, inline or `src=` (a warning). The router evaluates a guard's module once and runs its exported function on every navigation, so a guard that reads the session outside the function keeps the session there was when the page loaded: after the login, every guarded page went back to /login, and nothing said so. Read it inside the function; a read inside any function (a helper it calls, a getter, a method) is not reported.
- **`wcs/event-token-unbound`** (warning) — the mirror of `wcs/command-token-unbound`: a name `$eventTokens` declares that no `eventToken.<member>: <name>` binding on the page emits, so its `$on` handler never runs (the page had removed the binding and watched `deleteFetch.status`, which a second 204 does not change). Not reported where a binding the lint does not see can emit it: a page with a `<wcs-layout src>`, or a script that writes `eventToken.` bindings.
- A row field the rows lack, beside a near one they have, is named — `Path ".amountLabl" does not exist in the state definition (expanded: rows.*.amountLabl). Did you mean "amountLabel"?` — wherever the rows were read from: a data list, a getter's mapped literal, a JSDoc type.
- `wcs/array-index-assign` on a value not known to be an array (`budgetErrors: {}` with `this.budgetErrors[id] = …`) says it assigns an object's key, not "an array index".
- The rows of a list the script changes in place (`this.budgetRows.splice(0, n, ...rows)`, reported as `wcs/array-mutation`) are not checked when no literal or JSDoc type gives their fields. Up to 4.20 each such row field was a false `wcs/binding-path-missing`, the same code as a real typo.

## What a data-entry form is told

Since 4.23, from the ekiden-entry seam app — an entry wizard for a relay race, heavy on input: an IME, autofill, rows of inputs, form-associated custom elements. On its page the lint had said nothing about 21 mistakes made on purpose, and had given 91 false warnings about a state it could not read:

- **A key whose value the lint cannot read is unknown, not missing.** `team: init.team` beside `const init = emptyEntry()`, `errs: emptyErrs()`, a conditional, `[1, 2].map(…)`, the rows of `[newRunner()]`: the paths under such a key are not checked, and one `wcs/path-dynamic-unknown` info at the key says so — with the number of paths bound under it (a row's `.name` under the key's `for:` is one) and what has them checked: a JSDoc `@type` on the key, or a `stateSchema`. Up to 4.22 each of those paths was a false `wcs/binding-path-missing`, the same code as a real typo. A member of a `const` bound to an object literal (`team: DEFAULTS.team`, in the module or imported) is read, and the paths under it are checked.
- **`wcs/radio-name-shared`** (warning) — radios in a `for:` row with a literal `name` and a binding of the row's (`<input type="radio" name="sex" data-wcs="radio: .sex">`). Every row's radios get the same name, so the browser makes one group of all the rows: only one radio on the whole page stays checked, and the page disagrees with the rows' values from the first render. Bind a name that differs per row (`attr.name: .<a row field>`), or drop the name — `radio:` keeps the radios bound to one path in step without it. Not reported when the name is bound, when the bound path is not the row's (`value: .id; radio: selectedId` — one choice over the rows), or when each row holds its own `<form>`.
- **`wcs/radio-before-value`** (warning) — `radio:` / `checkbox:` written before the binding that gives the control its value (`<input type="radio" data-wcs="radio: theme; attr.value: .value">`). Bindings are applied in the order written, and `radio:` compares the element's `value` when it is applied — still the browser's `"on"`: no radio is checked at the first render, and nothing at run time says so (a later write of the state checks the right one, which hides it where the value arrives after the page is drawn). Write the value first: `attr.value: .value; radio: theme`. Silent when the value binding comes first and when the value is only in the markup (`value="red"`). Since 4.29.
- **`wcs/number-written-as-string`** (warning) — a two-way `value:` with no conversion on the way in, bound to a path the state holds as a number: `<input type="number" data-wcs="value: count">` with `count: 0` (a JSDoc `@type {number}`, a `stateSchema` and a row field `value: .qty` count too). An element's `value` is a string, so after the user enters 5 the state has `"5"` and `count + 1` is `"51"`. Write `valueAsNumber: count`, or an input filter on the left side: `value|number: count` (`|int`, `|float`).
- **`wcs/two-way-output-filter`** (warning) — an output filter on a two-way `value:` / `valueAsNumber:` (`value: code|upper`, `value: price|locale`). In a field the user types in, the filter formats what the state holds on every keystroke: the field is rewritten while the user types — the caret jumps to the end, an IME composition is cut — and the state receives the field's formatted text, since an output filter is not undone on the way back. Show the formatted text in another element, write back when the field is committed and format in a setter (`value#onchange:`), or make the binding one-way (`value#ro:`). A binding that writes back a committed value (`#onchange`, a `<select>`, a slider) is reported only when no input filter undoes the output: `value#onchange|number: price|toFixed(2)` is not. Nor are the filters that give back what the element wrote: `string`, `nullIfEmpty`, `coalesce(…)`, `defaults('')`.
- **A boolean given to `attr.*`** (`wcs/binding-type-expectation`) is told what happens to it: the runtime writes `String(value)` — `"true"` / `"false"` — and only `null` / `undefined` remove an attribute. Where those words are the attribute's values — the ARIA states (`attr.aria-invalid: flag|truthy`), `contenteditable`, `draggable`, `spellcheck` — nothing is reported any more (it was a false warning: `"attr.aria-invalid" requires a string`). A boolean attribute of a native element (`attr.disabled: flag`) is told that `disabled="false"` still disables, with the property to bind instead (`disabled: flag`). Any other attribute (`attr.data-open: flag`) is told that it is written as the text and never removed, with `|defaults(null)` to remove it while false and `|string` where the text is meant.

The three new rules are warnings: `--strict` fails on them, `--errors-only` does not print them.

## What a long list's page is told

Since 4.24, from the town-archive seam app — an archive of 12,000 photos: a long list with infinite scroll. What its page got wrong and this lint did not say:

- **`wcs/body-binding`** (error) — `data-wcs` on `<body>` or `<html>` (`<body data-wcs="onkeydown: onKey; class.dark: dark">`). `<wcs-state>` binds what is inside `<body>`, not `<body>` or `<html>` themselves, so nothing written there does anything: the handler never runs, `class.` and `attr.` are never written. Move the binding to an element inside `<body>` (a wrapper, `<main>`), or write the value from `$connectedCallback` or a `$watch` handler (`document.documentElement.lang = …`).
- **`wcs/link-handler`** (error) — an `on*:` binding on a `<wcs-link>` (`<wcs-link data-wcs="attr.to: .href; onclick: openPhoto">`). The link's host is `display: none`, and what the user clicks is the `<a>` the link generates beside itself, so the handler never runs. Put it on an element inside the link (its children move into the `<a>`) or on one around it; to navigate from a handler, write the router's `navigateUrl`.
- **`wcs/root-margin-unit`** (warning) — a literal `root-margin` on `<wcs-intersect>` or `<wcs-infinite-scroll>` that the browser refuses: `root-margin="200"`, `"0 0 900 0"`. `IntersectionObserver` takes one to four values, each a number with `px` or `%` — a `0` needs its unit too, so `"0 0 900px 0"` is refused as well (`rootMargin must be specified in pixels or percent`). `<wcs-intersect>` then observes nothing (`observing` stays `false`) and `<wcs-infinite-scroll>` loads no page. The message gives the value with `px` added (`root-margin="0px 0px 900px 0px"`). A bound `rootMargin:` is not checked.
- **`wcs/getter-untracked-read`** also reports a getter that reads the window or the document: `innerWidth` / `innerHeight` / `outerWidth` / `outerHeight`, `devicePixelRatio`, `scrollX` / `scrollY` / `pageXOffset` / `pageYOffset`, a call of `matchMedia(…)`, `navigator.onLine`, the `clientWidth` / `clientHeight` / `scrollTop` / `scrollLeft` of `document.documentElement` / `document.body` / `document.scrollingElement`, `document.visibilityState` / `document.hidden` — with or without `window.` / `globalThis.`. None of them is state, so the cached getter keeps its first value (a column count computed from `innerWidth` does not change on a resize). The message names what to bind instead: `<wcs-resize>`'s `width` / `height`, `<wcs-media-query>`'s `matched` (for `matchMedia`, a breakpoint, a resolution threshold), `<wcs-network>`'s `offline`. No element gives the scroll position or the page's visibility: keep the value in state and write it from an event handler. A name the getter or the module binds (`const innerWidth = …`, a parameter) and a state key of the same name (`this.innerWidth`) are not reported.
- **`wcs/delegated-current-target`** also reads the functions nested in the handler: `openPhoto(event) { return this.photos.find((p) => String(p.id) === event.currentTarget.closest(".card").dataset.id); }` is reported like a read in the handler's own body. Not a function that shadows the parameter, nor one handed to `setTimeout`, `requestAnimationFrame`, `.then(…)` or `addEventListener`, nor one stored on an object (`img.onload = () => …`): such a function runs after the dispatch, when `currentTarget` is `null` either way.
- **Every `@typedef` of a JSDoc block is read.** Up to 4.23 only the first one of a block was (`/** @typedef {…} Photo` and `@typedef {…} Area */` in one comment), and a list typed with the second (`/** @type {Area[]} */ areas: []`) got a false `wcs/binding-path-missing` for each field of its rows.

`--errors-only` prints the two new errors; `--strict` also fails on the new warning.

## What a page of screen and sensor elements is told

Since 4.25, from the stamp-rally seam app — a stamp rally on the screen and sensor elements: fullscreen, the screen's orientation, tilt and the sensors, share, contacts, credentials, the wake lock. Its author made 20 mistakes on purpose, and this lint reported none of them for what it was. What it says now:

- **`wcs/path-readonly`** (error) also reports a member a custom element writes, bound to a getter without a setter — `<wcs-wakelock data-wcs="held: keepAwake">` with `get keepAwake() { … }`. An output-only member is written when it is bound, so the state fails to initialize and the whole page is dead (`[wcs/path-readonly] "keepAwake" is a getter without a setter`); the lint said 0 errors. Read as the runtime wires it: `#ro` does not change that, `#init=none` moves the failure to each time the element reports a value, and only `#ro,init=none` makes the element write nothing. A member that is an input too (`value` on `<wcs-storage>`, `trigger`) is written each time the element reports a value — bind a getter that only feeds the element one way, `value#ro:` — and when it is bound with `#init=element`. A spread's members are read the same way. For the built-in `wcs-*` tags and an element the page defines with a literal `static wcBindable`.
- **`wcs/token-undeclared`** also reports a token used in a state that has no `$commandTokens` / `$eventTokens` at all — the one case where no token can exist, and the one the lint was silent on (a Quick Start copied with its declaration left out): `command.select: $command.select` (error — the state fails to initialize), `this.$command.select.emit(…)` in the script (error), `on*: $command.x` and `eventToken.<member>: name` (warning — reported each time the event fires). A `$on` entry whose name `$eventTokens` does not declare is an error too: the runtime refuses the state when it loads. "The state has none" is said only of a state read in full — an `export default { … }` literal with no top-level spread, or JSON, where the key is absent or an empty list. An undeclared `on*: $command.x` now carries this code; it used to be a `wcs/binding-path-missing`.
- **`wcs/command-event-argument`** (warning) — `on*: $command.x` wired straight to a command that takes data: `<button data-wcs="onclick: $command.share">` with `<wcs-share data-wcs="command.share: $command.share">`. A token emitted from an event carries the event as its first argument, and the command is called with it: `<wcs-screen-orientation>`'s `lock(event)` and `<wcs-share>`'s `share(event)` end as the browser's TypeError in `error`, `<wcs-credential>`'s `get(event)` resolves `null` without a word. Emit from a state method instead: `onclick: share` with `share() { this.$command.share.emit({ … }) }`. For a built-in tag's command whose method declares parameters. Not for a command with none (`start`, `requestFullscreen`: a button wired straight is the short form), nor for the four that ignore a first argument that is not theirs — `<wcs-fetch>`'s `fetch`, `<wcs-ws>`'s `close`, `<wcs-idle>`'s `start`, `<wcs-notify>`'s `close` — nor for a native element's command.
- **`wcs/frequency-invalid`** (warning) — a literal `frequency` on `<wcs-accelerometer>`, `<wcs-gyroscope>`, `<wcs-magnetometer>` or `<wcs-ambient-light-sensor>` that is not a positive number: `frequency="60hz"`, `"0"`, `"-5"`. The element reads it as "none", and the sensor runs at the browser's default rate without a word. The message gives the number the value starts with (`frequency="60"`). A bound `frequency:` is not checked.
- **`wcs/target-selector`** (warning) — a literal `target` written as a bare word on `<wcs-fullscreen>`, `<wcs-pip>`, `<wcs-pointer-lock>`, `<wcs-intersect>` or `<wcs-resize>`, where the document has an element with that id and none with that tag name: `target="viewer"` is a CSS selector for `<viewer>` elements, and `#viewer` was meant. The command then fails with only the element's `error` saying so; the two observers observe nothing.
- **`wcs/output-path-written`** (warning) — a script assigns `true` to a path bound to an element's output: `this.viewerFs = true` with `<wcs-fullscreen data-wcs="active: viewerFs">`. An output is the element's to write, so nothing becomes fullscreen — and what shows the flag (`class.fullscreen: viewerFs`, a button's label) now says it did. Ask the element with its command. Narrow on purpose: only `= true` (putting a consumed output back to `false` or `null` is normal), and not a path that an input of a custom element or a native two-way binding (`checked: flag`) also takes.
- **A slot an element's output writes is unknown, not missing.** `picked: null` with `<wcs-contacts data-wcs="value: picked">`, `users: []` with `<wcs-fetch data-wcs="value: users">`, the `value` a spread puts under its path: the slot holds whatever the element gives, so the paths bound under it (`picked.0.name.0`, a row's `.name`) are not checked, and one `wcs/path-dynamic-unknown` info at the key says so. Each used to be a `wcs/binding-path-missing`. A JSDoc `@type` on the key has them checked.
- **`wcs/input-nested-write`** names the forms to bind instead: an accessor pair, `value#init=element: <getter>`, or one way, `value#ro: <getter>`. A getter with neither a setter nor `#ro` saves, and then has what the element reports written back to it and refused.

`--errors-only` prints the wider `wcs/path-readonly` and `wcs/token-undeclared` errors; `--strict` also fails on the four new warnings.

## What a TypeScript team is told

Since 4.26, from the lending-desk seam app — an equipment-lending desk written by a team that writes TypeScript: a `.ts` state, a generated `stateSchema`, page-defined elements in `.ts` modules, API types in one shared file. Its pages passed this lint with 0 errors and 0 warnings while it had made, among others, a misspelt status in a comparison, a binding to a member a stepper does not have, a getter that tracks only half of what it reads, and three renamed keys the manifest still had; and to get there it had taken the return types off its handlers. What it says now:

- **A `.ts` state's return types are read.** `get total(): number {`, `submit(e: Event): void {`, `count(cur: number): void {` in `$watch` — and object types, unions, `Promise<…>`, type parameters, type predicates — no longer hide the member. Up to 4.25 such a member was not read: a getter or a method bound in the page was `wcs/binding-path-missing` (with a `stateSchema`, `wcs/path-nonexistent` — methods are not in the schema), a handler's parameter `cur:` was read as a `$watch` key (`wcs/watch-path-missing "cur"`), and the script rules (`wcs/getter-untracked-read`, `wcs/nested-assign`, `wcs/array-mutation`, …) skipped the typed getters. A body with TypeScript syntax (`x as T`, `y!`, a typed local), a `.ts` module the state imports, and a page's `.ts` modules are read with their types erased, through Node's `module.stripTypeScriptTypes` (Node 22.13 or later; on an older Node they stay unchecked, as before). No package is added: `@wcstack/lint` keeps zero dependencies.
- **`wcs/tag-member-unknown` reads elements defined in TypeScript.** `<script type="module" src="./main.ts">` and the `.ts` modules it imports (an import of `./x.js` reads `./x.ts` when there is no `.js`; one without an extension, `./x.ts` then `./x.js`): `static wcBindable = { … } as const satisfies Decl` is the literal. Up to 4.25 only `.js` / `.mjs` modules were read, and `maximum:` on a stepper that declares `max` passed — the stepper was never limited.
- **`wcs/filter-arg-enum`** (warning) — a comparison filter (`eq` / `ne`) whose literal argument the compared value never takes: `class.st-approved: .status|eq('aproved')` where the type is `"pending" | "approved" | "denied"` (a `stateSchema` `enum` / `const` / `anyOf` of consts, a JSDoc literal union — through a `@typedef` or an imported type too). `eq` is never true (`ne` always), and the badge's colour silently never shows. The message names the values and a near one. Only for a filter applied first to the path.
- **`wcs/filter-input-type` uses the types it has.** A row's path (`.label|toFixed(0)` under `for: rows`) is typed as the row field it expands to — a literal row's, a JSDoc type's, a `stateSchema`'s (a getter's too: `.depositLabel|toFixed(0)` where the schema says string). The date filters (`date`, `time`, `datetime`, `ymd`, `hms`) take a `Date` only, as the runtime does (it throws for anything else but null): `.at|date` on an ISO string is reported. Up to 4.25 only a path written in full with a literal seed was checked.
- **A JSDoc type from another module is read.** `/** @type {import("./api.ts").Reservation[]} */`, a getter's `@returns {import("./api.ts").Reservation[]}`, a `@typedef {import("./api").Reservation} Reservation`: the type is read from that file — an `interface` or a `type` of a `.ts` / `.d.ts`, a `@typedef` of a `.js` — and the rows bound under it are checked. A type it cannot read (no such file, no such name) leaves the paths under the key unchecked and says so once (`wcs/path-dynamic-unknown`, info) — unknown, not missing. Up to 4.25 each field bound under such a list was a false `wcs/binding-path-missing`.
- **A getter that falls back to `[]` does not make its rows "missing".** `get pickups() { return this.counter ? this.counter.pickups : []; }` (also `X ?? []`, `X || []`, an early `return []`) where `X`'s shape is not known: the rows are unknown, said once at the getter (`wcs/path-dynamic-unknown`). Up to 4.25 the `[]` made every row field a `wcs/binding-path-missing`. A list whose rows are known (`this.items ?? []`) is checked as before.
- **`wcs/watch-path-missing` consults the `stateSchema`**, as the bindings do: a key the schema has is not reported, only one it definitely lacks.
- **`wcs/drift-state-key`** (warning) — the `stateSchema` applied to the page and the page's root state script disagree on the top-level keys: `get displayName()` renamed in the `.ts` while the manifest still says `headerName`. A stale schema wins over the script — the binding left on the old name passed (0 errors, 0 warnings), and a key added since was `wcs/path-nonexistent`. Said once, at the `<wcs-state>` start tag, naming the keys on each side, with `wcs-schema emit` to regenerate it — run `wcs-schema check` before this lint in CI. Only where both sides are known: a root state script read in full (no top-level spread, no computed key, no `$stream` / `$scan`) and the schema's top-level properties; a volume's mount root is not counted.
- **A schema applies to the pages of its state** — see *Which pages a schema is for* above.

`--errors-only` prints the errors now found in TypeScript (`wcs/tag-member-unknown` on an element defined in a `.ts` module, `wcs/getter-untracked-read` on a typed getter, …); `--strict` also fails on the two new warnings and on the wider `wcs/filter-input-type`.

## What a page assembled from parts is told

Since 4.29, from the garden-plots seam app — a console assembled from a city's shared parts: designers' parts in HTML alone (Declarative Custom Components), developers' parts as classes mounted on the page's data. Up to 4.28 the lint knew nothing of a part: of the 45 mistakes its author made on purpose it caught 2.

**A Declarative Custom Component** (`<my-pager data-wc-definition><template shadowrootmode="open"> … <wcs-state> … </wcs-state></template></my-pager>`):

- **A definition is a scope of its own.** The markup in its template is checked against the definition's own `<wcs-state>`, and the page's markup against the page's. Up to 4.28 the two were one set of keys: a page's binding passed on a key only a part had, and a part's on a key only the page had. A part's file (`parts/my-pager.html`) is checked the same way when it is named on the command line.
- **`wcs/dcc-declaration`** (error) — a definition the runtime refuses when it defines the tag, by the same conditions: `$bindables` / `$commands` that is not a list; an entry that is empty, starts with `$`, is written twice or is not a member of the state; a method in `$bindables`; a value in `$commands`; a `<wcs-state bind-component>` in a definition; a second `<wcs-state>` of the definition's own. The refused definition defines nothing, so every instance on every page stays an unknown element. Only what is certain is said: a list that is not a literal, a state that is not an `export default { … }` literal and a state file the lint cannot read are left alone.
- **`wcs/tag-member-unknown`** (error) now covers a DCC: `<my-pager data-wcs="totl: n">` and `command.nxt:` are checked against the part's `$bindables` and `$commands`, with the near name. The definition is read where the page says it is — in the page, or in the file the import map names for the autoloader's `dcc` loader: an eager key whose file ends in `.html` or that says `|dcc`, a namespace that says `|dcc/`. A file the lint cannot read gives no contract, and the tag's bindings are not checked: a path from `/` is read only with `--root=<dir>`.
- **`wcs/dcc-attribute`** (warning) — an instance that carries one of the part's `$bindables` as an attribute (`<my-pager total="120">`). A DCC's inputs are properties: the attribute is not read, and the part shows its default. The runtime warns with the same code since 4.28. Once per tag and name.


**A class part** (`class XCard extends HTMLElement` with `<wcs-state bind-component="state">` in its template and `state = { … }` on the instance, mounted with `<x-card data-wcs="state: user">`):

- **The class is read where the page says it is** — the file the import map names for the autoloader (`"@components/x-card": "./parts/x-card.js"`, or a namespace: `"@components/x/": "./parts/"` and `<x-card>` → `./parts/card.js`), or a module the page loads that calls `customElements.define("x-card", XCard)`. A part's own template is read for the parts it mounts in turn. `.ts` files are read with their types erased.
- **The getters a part exports are paths of the page.** A getter of the part's state is readable at the path the part is mounted on — `user.display`, and `.display` in the rows a part is mounted on, a part inside a part included. Up to 4.28 a page that read one was told the path does not exist (`wcs/binding-path-missing`), and the way round it — declaring the getter by hand in the JSDoc type of the page's data — hid a later rename. A getter the part no longer has is reported as any missing path.
- **A part's methods are checked like a page's**: `this.tenant.name = v` (`wcs/nested-assign`) and `this.plots.push(p)` (`wcs/array-mutation`) are errors in a part too. The finding is in the part's file, at its line.
- **A path of a part's template whose first key nothing gives** is `wcs/binding-path-missing` (warning), in the part's file: the key is not one of the part's own state, the page does not hand it over (`state.view:`), and the object the part is mounted on does not have it — `nmae` in the template, `view.x` where the page wrote `state.veiw:`, a path of the page read inside the part (`pageTitle`: hand it over). Inside a part such a read falls through and fails nothing; the runtime reports it since 4.28, and this is the same test. The mounted object is judged only where its shape is known (a seed, a JSDoc type, a schema): rows of a list that starts empty say nothing. Deeper than the first key nothing is said.
- Only what is certain is read: `state = { … }` as an object literal (a field, or `this.state = { … }` in the constructor) with no spread and no computed key, and a template that is one string of the module. A file the lint cannot read (a path from `/` without `--root`), a state built by a call, a class it cannot find: nothing is said about the tag, as before.


## What a page written from another framework's habits is told

Since 4.30, from the street-reports seam app — a React app ported to wcstack by a first-time author. The habits a React (JSX) author brings ran without a word, or the lint described them as something else: an expression was "a path that does not exist", and a template literal or a quoted string on the right of a binding was not reported at all. What the runtime refuses or silently drops is an error, the rest a warning, and only what is certain is said.

- **`wcs/binding-expression`** (error) — the right side of a binding is a path and filters, not an expression: `hidden: !loading`, `textContent: count + 1`, `class.active: status === 'new'`, `class.is-new: .status === 'new'`, `textContent: done ? '完了' : '未完了'`, `` attr.href: `/reports/${id}` ``, `textContent: '件数: ' + count`, `textContent: formatDate(reportedAt)`, `if: items.length > 0`, `{{ count + 1 }}`, `<!--@@: count + 1 -->`. An expression is a right side (before the first `|`) with whitespace in it or one of `` ! ? = < > + ( ) ' " ` & , ``, none of which a path can hold. The message names the filter where the form has one — `!x` → `x|not`, `x > 0` → `x|gt(0)`, `x === 'new'` → `x|eq(new)`, `x + 1` → `x|add(1)` — and a getter otherwise. On an event binding with arguments or an arrow function (`onclick: remove(.id)`, `onchange: () => toggleRow(.id)`) it says that a handler is a method name, called with `(event, ...loopIndexes)`. One finding per text: the missing-path report of the same text (`wcs/binding-path-missing`, `wcs/path-nonexistent`) is not added. Filters with arguments, modifiers, row paths, wildcard and index paths, spreads, `else:`, `state.key:`, `command.x:` and `eventToken.x:` are not expressions; `a || b` is already an error (`wcs/binding-syntax`, an empty filter). `{{ }}` in a file without a `<wcs-state>` is another template engine's (`{{#each}}`) and is not read.
- **`wcs/attribute-mustache`** (warning) — `{{ }}` in an attribute other than the bind attribute: `href="/reports/{{ id }}"`, `class="row {{ kind }}"`, `alt="{{ title }}"`, `<wcs-link to="/reports/{{ .id }}">`. `{{ }}` is read in text only, so the attribute keeps the braces; bind it (`attr.href: <path>`, with a getter that builds the string). A warning, since a server-side template that fills it before the page is served is fine. Only in a file (or a DCC definition) with a `<wcs-state>`, not where the state declares `$behavior: { enableMustache: false }`, not in a `data-wcs-ignore` subtree; once per attribute.
- **`wcs/structural-element`** (error) — `if:` / `elseif:` / `else:` / `for:` alone in the `data-wcs` of an element that is not a `<template>` (`<p data-wcs="if: open">`, `<li data-wcs="for: items">`): the runtime sets a property of that name and does nothing else — the element is always shown, the list is one element. Put the element inside `<template data-wcs="if: …">`. Beside another binding, `wcs/template-syntax` says it as before.
- **`wcs/collection-mutation`** (error) — in a state's methods, setters, `$watch` and `$on` handlers (where `wcs/array-mutation` looks): `this.selected.add(id)`, `.delete(…)`, `.clear()`, `this.byId.set(k, v)` on a key whose initial value in the state literal is `new Set(…)` / `new Map(…)`. The state does not see it. Assign a new one (`this.selected = new Set([...this.selected, id])`), or keep an array / an object. Not said when the method assigns the key again.
- **`wcs/row-id-shared`** (warning) — a literal `id="…"` on an element of a `for:` row that no binding gives (`attr.id:` / `id:`): every row gets the same id, and a `<label for>` or `aria-labelledby` reaches the first row only. Bind it (`attr.id: .domId`, with a row getter that builds it from the row's key). Once per loop and id. Not under an `if:` branch in the row (it may be drawn for one row at a time) nor in a shadow root.
- **`wcs/event-name-case`** (warning) — `onSubmit:`, `onClick:`, `onChange:` (JSX's spelling): the listener is added for an event named `Submit`, which nothing dispatches. Write `onsubmit:` for a DOM event; a callback "prop" of a part is an event the part dispatches, bound with `eventToken.<member>:`.
- **`wcs/inline-import`** (error) — a static `import … from "./x.js"` (`../`, `/`) in an inline `<wcs-state>` or `<wcs-guard-handler>` script: it is evaluated from a `blob:` URL, and the import does not resolve. Use a `src=` file, a full URL, or an import-map name. Not for a full URL, a bare specifier or a `src=` state.
- **`wcs/key-binding`** (warning) — `key:` on a native element (React's `key`): it sets a property named `key` and does nothing. No key is needed: rows are matched by the row object, and `$listKeys` keeps rows across refetched data. A custom element's `key` may be an input (`<wcs-storage>`) and is not reported.
- **`--strict` counts a state that was not read.** `wcs/state-src-unread` (a `<wcs-state src>` the lint cannot read) and the `wcs/path-dynamic-unknown` of a `...spread` at the top of a state — after either, none of that state's paths is checked — stay info, but under `--strict` they count like warnings (exit `1`). A key whose value the lint cannot read (a dictionary imported from another file, `team: init.team`) leaves the rest of the state checked: it stays an info that `--strict` passes. For those two, the summary line says how many (`(strict; 2 unchecked counted as warnings)`) and a `strict:` note follows it. Up to 4.29 `--strict` exited `0` with such a state unchecked.

The new errors are printed with `--errors-only` too; the new warnings fail `--strict`.

## What a page with a generated schema and a total over its rows is told

Since 4.31, from an outside evaluation — the record of a 25-day Advent Calendar series that builds a buildless tax-return draft tool on wcstack 4.28.0:

- **A `stateSchema` never weakens the check.** Where the schema says nothing — a list whose rows have no type (`items: {}`, what `wcs-schema` writes for a list that starts empty), a value typed `null`, `any` — a path is checked as it is without a schema (`wcs/binding-path-missing`, a warning). A misspelt `.deductio` under such a list was reported without the schema and passed once it was added. `wcs-schema emit` also names each such list now.
- **`wcs/getter-untracked-read` reads a list's rows too.** A getter that reads `this.incomes` and a field from its row objects — `this.incomes.reduce((t, row) => t + row.amount, 0)`, `this.todos.filter((t) => !t.done).length`, also after `filter` / `slice` / `toSorted`, on `[...this.list]`, and in `for (const row of this.list)` — when that field is written by path: only the list is tracked, so the total follows rows added and removed and keeps its value when an amount is edited. An **error** when a binding on the page writes it (`valueAsNumber: .amount` in the rows, `checked: .done`, a built-in tag's output); a warning when the write is a custom element's `value:` / `checked:` the lint has no contract for (`<yen-input data-wcs="value: .amount">`) or the script's (`this["incomes.0.amount"] = …`, `$setAll`). Not reported without such a write of that field — a page that replaces the list, a `#ro` binding, `<option data-wcs="value: .id">`. Read the field by path: `this.$getAll("incomes.*.amount", [])`.
- **A did-you-mean for any missing path.** A misspelt top-level key or getter (`dependentsDeductio`) and an object's member (`user.nmae`) name the near one, as the runtime does; only a row's field did.

The new warnings fail `--strict`; the new error shows with `--errors-only`.

## Use in generate–validate–fix loops

Stable diagnostic codes, `source:line:col` ranges, and the exit-code contract make this CLI a drop-in gate for CI and for AI code-generation flows: generate HTML → `npx @wcstack/lint --errors-only` → read the diagnostics, fix, and re-run until exit code `0`. The gate covers `data-wcs` pages: when the output ends with `not read:` or `nothing to check:`, those files were not checked.

## Relationship to the VS Code extension

This package is a thin distribution wrapper: it ships the self-contained CLI bundle built from the [`wcstack-intellisense`](https://github.com/wcstack/wcstack/tree/main/packages/vscode-wcs) validator core (zero runtime dependencies). The sidecar manifest is tooling-only and never changes runtime behavior; the normative schema lives in [`docs/wcstack-manifest-schema.md`](https://github.com/wcstack/wcstack/blob/main/docs/wcstack-manifest-schema.md).
